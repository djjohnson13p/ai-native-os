# 80 — v0.1 Crash Consistency, Recovery, and Commit Protocol

## Purpose

AIOS is explicitly designed for long-running Tasks, provider crashes, process restarts, device reboots, revoked authority, staged Artifact publication, and eventually remote/irreversible operations.

The system therefore needs a single recovery model that ties together:

- Task state/revision;
- semantic program/validation identity;
- Execution Bindings/attempts;
- Authority Grants;
- Artifact output allocation/publication;
- provenance;
- provider/result certainty;
- future external side-effect operations.

The central rule is:

> **After a crash, AIOS reconstructs what is provably durable and what remains uncertain; it does not guess success, erase failure history, or blindly replay consequential work.**

## Failure model

v0.1 assumes crashes can occur between any two externally visible/durable steps:

```text
process crash
control-plane crash
provider crash
OS reboot/power loss
SQLite transaction rollback
filesystem write partially completed
response lost after durable commit
provider result lost
local secure-store temporarily unavailable
```

The first prototype does not need Byzantine distributed recovery. It does need deterministic local crash consistency.

## Durable truth sources

Recovery consults these durable sources rather than model recollection:

```text
Task current record + revision
Task transition/idempotency records
validated semantic-program records
semantic registry snapshot identity
Execution Binding + attempt records
Authority policy/grant/approval records
Artifact allocations/publication metadata/blob hashes
provenance journal/hash chain
provider supervisor durable attempt metadata
external operation/idempotency evidence when relevant
```

A model may help explain or propose recovery only after deterministic reconciliation establishes the facts.

## Ordering principle

Before admitting a protected/observable operation, persist enough **intent identity** to recognize it after restart.

Before claiming success, persist enough **result evidence** to prove it.

Conceptually:

```text
persist intent/attempt identity
→ perform bounded operation
→ persist result/publication evidence
→ transition Task/step state
```

Do not publish success first and invent provenance/state afterward.

## Local database transaction groups

Where records live in one SQLite database, use one transaction for logically inseparable state changes.

Examples:

### Task transition

```text
Task CAS + provenance event + transition result
```

### Artifact metadata publication

```text
Artifact metadata + lineage + publication result + provenance attachment
```

### Grant lifecycle update

```text
grant consume/revoke state + authority provenance/audit metadata
```

Filesystem/blob operations require a recoverable protocol because they are not part of SQLite ACID.

## Exclusive store ownership and durable fencing

Recovery is itself a mutating trusted operation, so a newly opened database is
not proof that the prior daemon is dead. Each writable local store has one
operating-system kernel-held exclusive owner lock. Startup MUST acquire that
lock before migrations, provenance verification that may quarantine records,
recovery discovery, or any other mutation. Lock contention leaves the second
process read-denied for recovery/migration and prevents it from changing live
Tasks owned by the first daemon.

The kernel lock is bound to the database file object (or an identity-bound stream
of that object), never to a path-derived sidecar or process-selected lock
directory. Symbolic links, hard links, case variants, short-path forms, and
other aliases of the same file therefore contend on one owner lock even across
processes with different environment or temporary-directory settings. If an
identity-bound lock cannot be acquired, writable open fails closed before
migration or recovery.

After acquiring the lock, startup atomically advances a durable monotonic
`store_fencing_epoch` and keeps the acquired value in its private store handle.
Every mutating transaction checks that handle value against durable store
metadata before writing and at commit. A stale/missing epoch, wraparound, or
failed comparison aborts the transaction. Migrations, recovery assessments,
repair/quarantine, Task/provenance changes, and ordinary runtime mutations all
use this check; no maintenance bypass exists.

The kernel lock provides live exclusion and crash release. The durable epoch
fences a stale process/handle after ownership changes. SQLite's own write lock,
a PID/daemon string, heartbeat, or actor identity is not a substitute for either
mechanism.

## Recovery epoch

On control-plane startup, allocate a `recovery_epoch_id` for the reconciliation pass.

Each recovered uncertain record may be assessed once or repeatedly under an explicit assessment identity.

The epoch provides attribution; it does not redefine historical attempt IDs.

`recovery_epoch_id` groups assessments. It is distinct from and grants no rights
in the monotonic `store_fencing_epoch` used to authorize store mutation.

## Startup sequence

Recommended v0.1 startup order:

```text
1. acquire the kernel-held exclusive store-owner lock
2. open bootstrap store metadata conservatively and advance store_fencing_epoch
3. run application migrations and integrity checks under that fence
   and latch time uncertainty if any external-effect time marker is unresolved
4. load active semantic/policy/component identities needed for interpretation
5. verify provenance heads for nonterminal/recovery-relevant Tasks
6. find Tasks in nonterminal or uncertain states
7. inventory each STARTING/RUNNING/UNKNOWN attempt and every other recovery subject
8. reconcile Artifact staging/publication state and grant/credential-use evidence
9. classify every subject independently from evidence bound to that subject
10. move affected RUNNING/VERIFYING/PAUSED Tasks through the private RECOVERING entry
11. compute safe actions and conservative Task state from all assessments
12. resume scheduling only after reconciliation and fencing gates pass
```

The system can later optimize boot by checking only active/relevant records rather than scanning all history.

## Canonical recovery certainty

For one operation/attempt, distinguish:

```text
NOT_STARTED
STARTED_NO_EFFECT
COMPLETED
FAILED_NO_EFFECT
FAILED_PARTIAL_EFFECT
OUTCOME_UNKNOWN
```

Additional local state such as `output staged` or `artifact finalized` supplies evidence used to choose the certainty class.

`OUTCOME_UNKNOWN` is not equivalent to failure and is not retry permission.

### Evidence is per subject

Recovery creates an assessment for every relevant subject identity rather than
assigning one optimistic certainty to the whole Task. Subject-bound evidence
includes, as applicable:

```text
attempt/binding       exact attempt + binding record and provider-supervisor receipt/status
external operation    exact operation/idempotency identity and authoritative external status
Artifact publication  exact allocation/publication transaction and verified blob identity
authority grant       exact grant/consumption/revocation ledger entry
credential use        exact brokered-use receipt without secret material
```

Classification rules are fail closed:

- `NOT_STARTED` requires affirmative trusted evidence that the exact subject was
  never dispatched/consumed; a missing result or missing row alone is not proof;
- `STARTED_NO_EFFECT` and `FAILED_NO_EFFECT` require evidence that the exact
  protected/observable effect did not occur;
- `COMPLETED` requires the subject's contract-defined durable success evidence,
  including publication/integrity evidence where applicable;
- `FAILED_PARTIAL_EFFECT` requires evidence of partial observable effect and
  preserves the affected resource identities; and
- conflicting, absent, stale, cross-subject, or insufficient evidence yields
  `OUTCOME_UNKNOWN`.

An unreachable provider is not proof of failure, a present blob is not proof of
committed publication, a committed Artifact does not prove an unrelated
external operation, and Task state does not prove every child attempt. Evidence
for subject A cannot classify subject B even when both belong to the same node.

Each consequential subject receives its own `safe_action`. A Task-level recovery
record may summarize/inventory these assessment IDs, but it cannot replace them.
The Task leaves `RECOVERING` only when all consequential subjects have compatible
evidence-backed actions and the normal completion/retry/authority gates pass. If
any one remains unknown, the aggregate decision preserves that uncertainty and
does not admit blind retry or completion.

## Crash-point matrix

### A — binding persisted, provider not launched

Evidence:

```text
binding exists
attempt = STARTING/PENDING
no provider start acknowledgement/runtime evidence
no output writes/external operation start
```

Safe recovery:

```text
classify NOT_STARTED
invalidate stale attempt/binding as appropriate
create fresh binding/grant if retry budget permits
```

Never assume old time-limited grants remain valid.

### B — provider launched, deterministic local operation, no output finalized

Evidence:

```text
attempt RUNNING
provider gone after restart
output allocation not PUBLISHED
no external-effect class
```

Safe recovery:

```text
classify FAILED_NO_EFFECT or FAILED_PARTIAL_EFFECT for staging-only bytes
quarantine/clean staging
retry only through normal failure budget with new attempt/binding
```

Staging bytes alone are not a published effect.

### C — provider output staged, Artifact publication never committed

Safe recovery:

```text
staging/orphan bytes are not Task output
reconcile allocation/publication idempotency
if no committed publication exists, do not expose downstream
```

Depending on the provider/failure contract, rerun/finalize can occur only after deterministic integrity/revision checks.

### D — immutable Artifact blob durable, metadata publication not committed

Treat blob as orphan/unreferenced bytes.

Do not infer a published Artifact from its existence.

A future idempotent finalize may reuse identical blob bytes after recomputing identity.

### E — Artifact publication committed, response/task transition lost

Evidence:

```text
publication record + Artifact metadata committed
blob exists/hash verifies
provider result/Task state may still look RUNNING
```

Recovery:

```text
return prior publication result by publication_id
append/repair missing subsequent state transition/provenance through normal transaction
DO NOT rerun provider solely because response was lost
```

### F — Task transition committed, caller did not receive response

Stable `transition_id` returns previous result.

No duplicate provenance event or revision increment.

### G — grant decision committed, token/handle response lost

The durable grant record is source of truth.

If raw opaque token material itself cannot be safely reconstructed, mint/rotate a new opaque runtime token reference bound to the same still-valid grant record rather than broadening authority or duplicating policy approval.

### H — grant consumed at protected operation, response lost

A one-shot grant remains consumed if the trusted resource broker committed the protected operation/usage transition.

Do not reset use count because provider did not receive a response.

If the protected operation has uncertain external outcome, route to reconciliation.

### I — deterministic policy decision created, approval pending, crash

Persisted approval request remains pending only while:

- Task/program/node/provider/destination/resource facts still match;
- request has not expired/revoked;
- policy snapshot rules permit continued pending state.

Otherwise mark stale and re-evaluate.

### J — credential broker delegated token/injection interrupted

Invalidate/revoke ephemeral delegated material whose state cannot be proven.

Source credential remains broker-managed. Reissue only after current grant/handle/binding checks.

Never reconstruct secret from logs.

### K — external/opaque operation started, response lost

If there is no authoritative idempotency/status evidence proving completion/no-effect:

```text
OUTCOME_UNKNOWN
```

Recovery must query/reconcile through the external system/provider where possible.

Do not blind retry a send/payment/order/publish/delete operation that may already have taken effect.

## Trusted entry to `RECOVERING`

Startup and live uncertainty use the same private recovery-coordinator
operation. It is not a serialized transition variant and is unavailable to
users, providers, planners, or ordinary workers. The coordinator accepts an
exact Task identity/revision through a private capability-bearing store handle,
then derives the subject inventory and evidence from trusted durable records and
authorized provider/status adapters.

The operation may enter `RECOVERING` only from `RUNNING`, `VERIFYING`, or
`PAUSED`. It performs the standard CAS, provenance append, and fencing checks.
The public transition API rejects every requested target of `RECOVERING`, even
when the request uses `system-service`, a recovery-looking actor/internal ID, a
reserved transition-ID prefix, or an `internal=true` flag. Caller-supplied
certainty/evidence booleans are never credentials and never replace derived
evidence.

Live entry is used when response loss, provider failure, or contradictory
durable status becomes uncertain before daemon restart. Requiring a restart to
reach recovery would leave a live Task in a false `RUNNING`/`VERIFYING` state.

## Recovery assessment record

Each assessment should state:

```text
assessment_id
recovery_epoch_id
Task
attempt/binding/operation
pre-crash durable state
observed evidence[]
certainty classification
safe action
reason codes
new binding required?
external reconciliation required?
created_at
```

This is durable recovery evidence, not AI narration.

## Safe recovery actions

Closed v0.1 set:

```text
NO_ACTION
RECONCILE_STATE
CLEAN_STAGING
MARK_ATTEMPT_FAILED
CREATE_NEW_ATTEMPT
RESUME_EXISTING_ATTEMPT
REVOKE_GRANTS
WAIT_FOR_INPUT
WAIT_FOR_AUTH
REQUIRE_EXTERNAL_RECONCILIATION
FAIL_TASK
BEGIN_COMPENSATION
```

`RESUME_EXISTING_ATTEMPT` is allowed only if the provider/runtime explicitly supports reliable reattachment/checkpoint semantics and binding/grants remain valid. The initial local provider can simply use new attempts instead.

## Retry gate

A new attempt requires all of:

- validated semantic program still current;
- node failure policy permits retry/fallback;
- attempt budget remains;
- previous outcome is safe to retry (`NOT_STARTED`, `STARTED_NO_EFFECT`, or explicitly idempotent/reconciled state);
- inputs/revisions still valid;
- output allocation/publication state reconciled;
- provider/resource candidate currently eligible;
- fresh/current authority evaluation/grants;
- no required approval has become stale.

Failure of any gate blocks retry rather than asking the AI to take a chance.

## Exactly-once claims

AIOS should avoid claiming global exactly-once execution.

What v0.1 can provide is a combination of:

```text
unique attempt/operation IDs
idempotent local state transitions
idempotent Artifact publication
at-most-once grant consumption where required
external idempotency keys when provider supports them
outcome reconciliation when certainty is lost
```

For arbitrary external systems, exactly-once effects are impossible to guarantee universally.

## Provenance requirements

Recovery does not rewrite pre-crash history.

Append material events for:

```text
recovery.started
attempt.reconciled
artifact.reconciled
operation.outcome-reconciled
recovery.action-selected
grant revoked/expired
Task RECOVERING transitions
recovery.completed
```

If the existing provenance enum is too narrow, extend it through explicit schema migration rather than dumping critical recovery facts into untyped logs.

## Filesystem durability assumptions

For local v0.1 Artifact Store:

- write staged bytes;
- flush/fsync according to durability mode;
- atomically rename/place immutable blob where supported;
- fsync parent directory where required;
- then commit/verify metadata protocol.

Implementation tests should simulate failures around these boundaries where practical.

Do not assume `write()` completion means power-loss durability.

## Database durability assumptions

Use SQLite transactions with foreign keys and appropriate journal/durability settings.

The first implementation should prefer correctness/recovery clarity over maximum throughput.

Database corruption is distinct from ordinary process crash and should enter maintenance/recovery mode rather than allowing AI-generated repair commands automatically.

## Recovery and model independence

The deterministic recovery engine decides:

- what durable facts exist;
- what certainty class applies;
- whether automatic retry is mechanically safe;
- which grants/artifacts/bindings are valid.

AI may later help the user understand a failure or propose a new Task/plan when human judgment is needed, but it does not overwrite certainty classifications.

## v0.1 acceptance tests

1. crash before provider launch yields `NOT_STARTED` and safe fresh-attempt option;
2. provider crash with only staging bytes publishes no Artifact;
3. orphan blob without metadata never becomes user-visible output automatically;
4. publication committed/response lost returns idempotent prior result;
5. Task transition committed/response lost does not duplicate revision/provenance;
6. one-shot grant consumption survives caller-response loss;
7. expired/revoked grant is never resurrected after reboot;
8. Task cancellation before reboot blocks new protected provider operations after restart;
9. finalized Artifact + stale RUNNING Task reconciles without duplicate computation;
10. corrupt/missing published blob prevents completion and enters recovery/failure path;
11. external opaque timeout becomes `OUTCOME_UNKNOWN` and is not blindly retried;
12. external idempotency/status proof can deterministically reconcile unknown outcome;
13. recovery actions append new provenance and preserve original failure/uncertainty events;
14. simultaneous recovery workers cannot both commit contradictory actions for the same revision/attempt;
15. recovery runs without model/network access for purely local deterministic Tasks;
16. secure-store outage does not cause credentials to be reconstructed from persisted logs;
17. stale approval after provider/destination/program change is rejected;
18. retry always creates a new attempt/binding when provider/runtime facts change;
19. a second daemon cannot migrate or recover a store while the owner lock is live, even through an alternate path alias to the same file;
20. stale fencing epochs fail every mutation class, including migration and recovery writes;
21. public `RECOVERING` requests fail regardless of trusted-looking actor strings, IDs, prefixes, or booleans;
22. private live recovery accepts exactly `RUNNING`/`VERIFYING`/`PAUSED` and derives evidence internally;
23. two subjects under one Task can receive different certainty/actions from their own evidence;
24. absent/conflicting evidence produces `OUTCOME_UNKNOWN`, never `NOT_STARTED` or `FAILED_NO_EFFECT` by inference;
25. one unknown consequential subject prevents an otherwise completed sibling from enabling Task completion or blind retry.

## v0.1 non-goals

- distributed consensus/quorum recovery;
- cross-datacenter transaction recovery;
- arbitrary process checkpoint/restore;
- universal exactly-once SaaS semantics;
- automatic AI repair of database corruption;
- rolling cluster upgrades.

## Principle

> **Recovery is the process of proving what happened well enough to choose the next safe action—not the process of making the Task look successful again.**
