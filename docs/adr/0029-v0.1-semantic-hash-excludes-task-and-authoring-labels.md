# ADR 0029 — v0.1 Semantic Hash Excludes Task and Authoring Labels

- Status: **Accepted for the v0.1 / Issue #17 spike**
- Date: 2026-09-15
- Amended: 2026-09-19 (JCS exact-integer boundary)
- Clarified: 2026-09-19 (R17-02 exact decimal/exponent integer authoring)

## Context

AIOS needs a semantic program hash that remains stable across formatting, Task instances, provider placement, hardware, runtime grants, and explanatory metadata.

The earlier IR draft contained an optional `task_id` field and required `program_id`, but the architecture distinguishes durable Task identity, logical program labels, and exact semantic program identity.

Leaving these fields ambiguous would force the first validator implementation to guess what participates in canonical semantic hashing.

## Decision

For AIOS IR v0.1:

1. `task_id` is removed from the semantic IR schema entirely. Task/program linkage belongs to Task records/Execution Bindings/provenance.
2. `program_id` remains required as a logical authoring/diagnostic/program-family identifier but is excluded from the semantic hash.
3. `metadata`, `description`, and authority-request `reason` prose are excluded from the semantic hash.
4. `kind`, typed inputs, graph nodes/data flow, capability/operation identity, execution class, authority action/resource, egress, constraints, failure policy, cache policy, and program outputs are semantic and included.
5. Node authoring order and unordered semantic-set order are normalized; fallback order remains significant.
6. The normalized semantic value is serialized with RFC 8785 JCS semantics and hashed using a centrally defined domain-separated SHA-256 profile for the v0.1 spike.
7. Runtime/provider/grant/device/path/network/cloud/component binding data remains outside the semantic hash.
8. Every semantic integer is limited to the interoperable I-JSON exact-integer range `0..=9007199254740991` (`2^53 - 1`) before JCS serialization. Values outside that range are invalid and never receive a semantic hash.
9. Integer acceptance uses the exact mathematical value of the original JSON number token, not its binary64 approximation. Equivalent integral decimal/exponent spellings normalize to the same bounded integer. Exact negative zero normalizes to zero. Nonintegral values never become integers through rounding; tighter field-specific bounds still apply.

The exact profile is documented in `docs/66-aios-ir-v0.1-canonicalization-and-semantic-hash-profile.md`.

## Consequences

### Positive

- the same semantic graph can be invoked by many Tasks without hash churn;
- logical program renames do not invalidate compiled/cached semantic identity;
- runtime placement/provider changes remain separate;
- descriptions/metadata can improve without invalidating semantic identity;
- the validator has deterministic testable hash inputs before implementation begins.

### Costs

- `program_id` cannot be used as exact executable identity;
- databases/provenance must store both logical program ID and semantic hash where useful;
- node renames still change v0.1 semantic hash because node IDs remain part of the graph representation;
- future IR versions may need migration if a more sophisticated graph-isomorphism identity is ever justified.

## Security impact

Authority actions/resources, egress, verification/data flow, constraints, execution classes, and failure behavior remain semantic-hash inputs.

Changing explanatory authority `reason` text cannot change permission meaning.

An invalid program receives no executable semantic hash.

## Compatibility impact

This is a pre-implementation clarification. The IR schema and canonical Demonstration A fixture have been updated to remove `task_id` from semantic IR.

Future semantic-hash consumers must record the hash/profile/IR version rather than assuming `program_id` uniquely identifies executable meaning.

The Issue #17 implementation exposed a concrete RFC 8785 interoperability problem: adjacent Rust `u64` values above `2^53 - 1` can collapse to the same ECMAScript number representation. The schema, canonicalization profile, validator, and regression vectors now close that collision boundary together.

Authoring documents that used larger constraint integers must choose a value in the
exact range or migrate under a future numeric profile. No previously issued trusted
v0.1 semantic identity is reinterpreted because the boundary was closed while the
first validator and generated hash vectors were being introduced.

## Revisit condition

Implementation may propose a change only if the reference validator demonstrates a concrete correctness/interoperability problem with this profile. Any change must update this ADR/profile, schema/fixtures, and hash test vectors together.
