# 91 — v0.1 Protected Operation / Point-of-Use Broker Contract

## Purpose

AIOS deliberately keeps providers unprivileged and moves protected resources behind trusted services such as:

```text
Artifact Store
Credential Broker
Network Broker
Object Store
Device Broker
System-change service
```

That architecture only works if a trusted broker does **not** accidentally become a confused deputy that uses its own broad service privilege on behalf of any caller that asks.

This document defines the common point-of-use contract:

> **Every protected operation is authorized as the effective Task/provider/workload principal against the exact current resource/action/binding/grant—not merely because a trusted system service can physically perform it.**

## Why launch-time checks are insufficient

A provider may be launched legitimately and later:

- ask for a different Artifact;
- attempt an extra write;
- use a credential not in its Task;
- continue after cancellation/revocation;
- substitute a destination;
- replay an old request;
- invoke a trusted broker from another process/channel;
- exploit a stale grant/binding.

Therefore the resource broker itself validates the protected operation at the moment it is performed.

## Effective principal vs broker principal

Example:

```text
provider://fixture-artifact-hash
        ↓ IPC
system-service://artifact-store
        ↓ filesystem read
blob storage
```

The operating system may see the Artifact Store process as the filesystem reader.

The **authorization principal** remains the provider/workload acting through the Artifact Store:

```text
provider://fixture-artifact-hash
Task T91
Execution Binding B7
Attempt A1
```

The Artifact Store's own service privileges are mechanism authority. They do not automatically delegate to the provider.

## Protected operation context

A protected call must resolve an authoritative context containing at least:

```text
operation_id
Task ID
semantic program hash
node ID
Execution Binding ID
attempt ID
caller/effective principal
requested action
concrete resource kind/ID
Authority Grant ID(s)
request timestamp / runtime session facts
```

`specs/protected-operation-context.schema.json` is the interchange/audit shape.

## Trust source for context fields

The provider may transmit identifiers in the RPC message, but a trusted broker MUST NOT trust them merely because they are syntactically valid.

Authoritative sources:

### Caller/workload identity

Derived from the authenticated local IPC/runtime channel or supervisor-created workload identity.

Provider-supplied `principal_id` is only a claim to compare against the channel identity.

### Execution Binding / attempt

Loaded from trusted control-plane state and matched to the authenticated caller/provider identity.

### Task/program/node

Derived from the immutable Execution Binding/attempt, not accepted as a way for the provider to choose a different Task.

### Resource

Resolved by the trusted broker from the handle/resource identifier under its namespace.

The provider cannot reinterpret `artifact://A` as a host path of its choice.

### Authority Grant

Loaded from the Authority Coordinator's durable grant record by opaque grant/token reference.

The provider cannot supply a self-authored scope blob.

## Validation algorithm

For each protected operation:

```text
1. authenticate IPC/workload caller
2. locate immutable Execution Binding + attempt
3. verify caller principal == bound provider/workload principal
4. verify Task/program/node/binding/attempt still match
5. resolve concrete resource under broker namespace
6. load current Authority Grant record(s)
7. verify grant principal/Task/program/node/binding/action/resource scope
8. verify grant ACTIVE + not expired/revoked/consumed
9. verify Task/attempt cancellation/recovery state permits use
10. verify broker-specific invariants (Artifact integrity, credential exportability, egress destination, etc.)
11. atomically consume/increment grant use where required
12. perform protected operation
13. persist operation/result/provenance as required
```

Any mismatch fails closed.

## Do not trust provider-supplied authority context

Forbidden patterns:

```text
provider says: {"user":"DJ","permission":"all-files"}
trusted broker accepts it
```

```text
provider passes serialized AuthorityGrant object it authored
broker validates only JSON shape
```

```text
provider chooses host path after receiving broad `artifact.read`
```

```text
broker checks grant once when provider process launches but never again
```

## Resource-specific examples

### Artifact read

Provider call:

```text
artifact.read(artifact://A17)
```

Broker proves:

```text
caller provider P
binding B
Task T
Grant G
G permits artifact.read A17 for P/B/T
Artifact A17 is current/integrity-valid
```

Then returns a bounded stream/descriptor/bytes interface.

It does not return the Artifact Store root path.

### Artifact output write

Provider receives:

```text
allocation://T91/node/report
```

Artifact Store validates the allocation is bound to the current Task/node/attempt and returns only that staging writer.

The store durably binds the allocation to the exact grant that admitted that
writer. Later publication revalidates the same grant and operation tuple before
blob placement and at metadata commit without consuming a second use. Canonical
consumption by that writer is accepted; expiry, revocation, approval invalidation,
Task cancellation, binding/attempt supersession, or grant substitution is not.

### Credential use

Provider calls Credential Broker with:

```text
credential://mail/account-A
operation = mail.send
```

Credential Broker independently validates current `credential.use` grant plus service/scope/exportability before performing/delegating the exact operation.

### Network connection

Network Broker validates:

```text
network.connect -> exact service/destination
```

If Task data will cross the trust boundary it separately validates matching:

```text
data.egress -> exact data resource/projection + destination
```

### Device access

A camera/microphone/device handle does not become direct `/dev` access unless the selected execution profile and Device Broker explicitly grant it.

## Operation identity / replay

Protected calls that consume limited authority or cause effects SHOULD include a stable `operation_id`.

For idempotent broker operations, repeated identical `operation_id` after response loss returns/reconciles the prior result rather than consuming another grant/use.

For non-idempotent/opaque external operations, the broker/runtime follows docs80 `OUTCOME_UNKNOWN` rules.

An `operation_id` is not itself permission.

## Grant consumption atomicity

For one-shot/bounded grant use:

```text
validate current grant
→ reserve/consume use in trusted transaction
→ perform/commit protected operation according to resource protocol
```

The exact ordering depends on the operation's reversibility/idempotency.

If the effect can become externally uncertain, persist operation identity before effect and use docs80 reconciliation.

For a filesystem or external callback whose fresh time observation cannot commit
atomically with the effect, also persist a subject-bound in-flight time marker
before callback entry. Reacquire the serialized authority fence and revalidate
after preparation; resolve the marker atomically with the exact entry-time
observation after the callback. An unresolved marker denies subsequent protected
work pending trusted recovery. The admission point is callback entry, not an
unprovable claim that an uninterruptible callback finished before expiry.
An ArtifactReader may stage file bytes only in broker-private memory while it
holds the serialized authority fence, then commit the fresh time observation
and first-delivery receipt before copying bytes into the caller's buffer. In
that case the protected delivery has no precommit external effect and needs no
in-flight marker. The broker must not expose the raw file handle, staged bytes,
or a callback that can publish them before the commit; failed admission or
commit leaves the caller buffer untouched. The private file cursor may be
rewound after failure, and a later read revalidates current authority.
For staging, the marker's subject is the allocation. A pending marker
quarantines the entire allocation, including later writer generations. The
marker records missing time evidence; it does not itself authorize an effect
or prove which writer completed one. Recovery must not clear it merely because
a replacement writer session exists.
Creating the private staging file, setting its permissions, and syncing the
file and directory are separate marked effects before writer admission. A
failed or uncertain setup leaves ALLOCATED residue for trusted reconciliation;
live retry must not adopt or delete it. The file must be private at creation,
including if a crash precedes the later permission step.

Writer flush, finish, and live finish-retry likewise admit each filesystem
creation, permission change, write, sync, rename, or removal with its own fresh
allocation-bound marker and locked authority check. The retry writer generation
is durably fenced before any repair effect. A pending marker preserves staging
and both seal names and blocks live retry; trusted startup recovery follows its
separate reconciliation path only after the time evidence is complete.

Pending seal files are private at creation in both live finish and trusted
recovery, so a crash before later permission hardening cannot expose them.

The v0.1 in-process export destination adapter is a trusted, non-reentrant
leaf: its constructor, primitive write, flush, finalize, and destructor must
not call back into the same store or wait for a worker that does. The trusted
core retains the serialized authority fence through each callback, and a
store-scoped guard must reject reentry before it waits for SQLite. Provider or
model code is not an in-process destination adapter. Third-party adapters need
an isolated execution protocol; releasing the fence around an arbitrary
callback would change the admission point and requires a separate durable
admission contract. A callback error or timeout after invocation remains a
possibly effectful outcome.

Do not implement:

```text
perform protected operation
→ best-effort increment uses_consumed afterward
```

because a crash can restore apparent authority.

## Cancellation / revocation

Point-of-use checks observe current:

```text
Task state
attempt state
grant state
credential/resource state
```

After Task cancellation or grant revocation:

- new protected operations fail;
- an already-running uninterruptible external effect may still have uncertain outcome and enters reconciliation;
- revocation does not rewrite earlier successful operations.

## Broker availability vs fail-open

If the trusted broker or Authority Coordinator state required for validation is unavailable, the protected operation fails/deferred.

Providers do not receive a broad raw-resource fallback merely to preserve availability.

For example:

```text
Artifact Store unavailable
```

must not become:

```text
here is /home/user, open the file yourself
```

## Local IPC / transport neutrality

The semantic security contract is independent of whether v0.1 transport is:

- direct trusted-library call;
- Varlink over Unix socket;
- another typed local RPC;
- Wasm host import.

Transport authentication must still provide the broker a trustworthy caller/workload identity.

## Relationship to sandboxing

Broker checks and sandboxing are complementary:

```text
sandbox prevents ambient bypass
broker validates intended protected accesses
```

If the provider can simply open the raw file/socket/credential itself, the broker contract is not an enforcement boundary.

Therefore Stage-1 provider tests must prove the raw bypass paths are unavailable.

## Audit/provenance

Material protected operations record/associate:

```text
Task/program/node
principal/provider
binding/attempt
operation ID
action/resource
grant/policy decision
result/outcome certainty
Artifact/external receipt where applicable
```

High-volume streaming may aggregate data reads rather than emitting one provenance event per chunk; the protected operation identity remains attributable.

## v0.1 acceptance tests

1. provider with valid Artifact-A grant requests Artifact-B -> denied;
2. provider spoofs another Task ID in RPC -> broker uses authenticated binding Task and denies mismatch;
3. provider passes another provider's grant -> denied;
4. system-service broker's own OS file privilege cannot be borrowed without matching grant;
5. expired/revoked/consumed grant -> denied;
6. Task cancellation -> subsequent protected operation denied;
7. one-shot grant concurrent use -> at most permitted number commits;
8. operation response lost after durable one-shot consumption -> replay does not restore/use grant twice;
9. Artifact handle cannot be changed into arbitrary host path;
10. Network connect cannot imply data egress;
11. Credential handle cannot imply secret export;
12. broker unavailable -> fail closed; provider receives no raw fallback resource;
13. local IPC caller identity mismatch -> denied before resource operation;
14. trusted provenance identifies effective provider principal, not only broker service process.

## Non-goals

- one universal broker implementation for all resources;
- replacing kernel DAC/MAC/sandbox enforcement;
- per-byte provenance;
- distributed authorization consensus;
- making provider code trustworthy.

## Principle

> **A trusted broker may have broad mechanism privilege; every request through it is still authorized as the narrowly scoped caller on whose behalf it acts.**
