# 76 — v0.1 Semantic Registry and Provider Registration Lifecycle

## Purpose

AIOS must keep two fundamentally different registries separate:

```text
Semantic Registry
  what types/capabilities mean

Provider Registry
  which implementations claim/test/execute those semantics
```

Issue #17 needs a read-only immutable semantic snapshot loader. Phase I extends that into a durable local registry/registration subsystem without turning a package catalog or provider manifest into semantic authority.

## Core separation

### Semantic Registry

Stores immutable:

- Semantic Type Contracts;
- Semantic Capability Contracts;
- Registry Snapshots selecting exact active contract versions/content hashes.

It answers:

> What does `table.import@1` mean under this snapshot?

### Provider Registry

Stores implementation records/evidence:

- Provider Manifest identity/version;
- component/package digest/build provenance where available;
- semantic capability families claimed;
- exact contract hashes/full versions tested against;
- conformance-suite evidence;
- isolation/runtime requirements;
- trust/review/revocation/enablement state;
- runtime-health observations separately.

It answers:

> Which installed implementation(s) are eligible to satisfy the resolved semantic contract?

A provider cannot create/change semantic meaning merely by registering.

## Semantic contract store

Contracts are persisted by semantic content hash/profile under ADR 0034.

Suggested logical keys:

```text
CapabilityContractHash
TypeContractHash
RegistrySnapshotId
```

Contract source filenames/URLs/catalog positions are metadata only.

Historical contracts/snapshots referenced by retained Task validation evidence, Skills, compiled targets, provider conformance, or provenance are not rewritten/deleted merely because a newer default snapshot is activated.

## Registry Snapshot activation

The local system may have many installed/known Registry Snapshots, but a user/org/system profile can identify one **default current snapshot** for new planning/validation.

Activation is a control-plane/configuration action separate from semantic content creation.

Conceptually:

```text
installed snapshot S1
installed snapshot S2
current default -> S2

Task created earlier:
  validation evidence -> S1

new Task:
  default validation context -> S2
```

Changing the default does not rewrite old Task semantics.

## Snapshot admission pipeline

Before a snapshot can become eligible for activation:

1. strictly validate snapshot schema;
2. load every referenced local contract;
3. validate contract schema/semantic consistency;
4. compute/verify semantic contract hashes;
5. enforce one active `(ID, major)` contract per class;
6. compute/verify Registry Snapshot ID;
7. apply publisher/signature/trust policy where available;
8. run required compatibility/conformance checks for critical namespaces according to current policy;
9. persist as immutable admitted snapshot;
10. only then permit default activation.

Hash/signature validity is not semantic correctness/trust by itself.

## Snapshot states

Suggested local lifecycle:

```text
DISCOVERED
STAGED
ADMITTED
ACTIVE_DEFAULT
DEPRECATED
QUARANTINED
REVOKED
```

Multiple snapshots can be `ADMITTED`; only policy/configuration chooses the default for new work.

A `REVOKED`/security-bad snapshot can remain retained for historical provenance interpretation while being ineligible for new execution.

The durable admission table enforces restrictive state transitions even for direct SQL writers: a quarantined or revoked admission cannot return to an activatable state, and replacing the row cannot reset that history. Duplicate-insert guards also protect admitted snapshot records, contract content, and snapshot entries from SQLite `INSERT OR REPLACE` rewriting immutable history. Additive migration `0014` records an immutable semantic repair-fence generation, terminal admissions, and re-attestation receipts. An intact earlier `0012` store bootstraps generation zero without losing its admitted snapshots or healthy defaults. If an existing stamped `0012` store is missing an additive guard, Task Manager appends a repair generation under its ownership fence before restoring the guard. The ADMITTED/DEPRECATED projection and immutable snapshot, contract, entry, identity, and migration stamps remain intact, but those snapshots cannot activate, register or enable a provider, become candidates, bind, or launch until a current-generation receipt exists. Existing provider binding markers are permanently quarantined and require new attempts. Every pre-repair activation scope is also permanently invalidated so a rolled-back revision cannot regain CAS authority through snapshot re-attestation; new scopes can be activated after recovery. `RegistryStore::initialize` only verifies an already migrated store. The provider migration `0013` requires complete stamped `0012` state; a partial or missing semantic store is not a valid provider registry.

An explicit owner-bound `RegistryStore::reattest_snapshot` operation strictly reopens all persisted snapshot and contract projections, requires a still ADMITTED or DEPRECATED state, and writes an immutable current-generation receipt with a new decision ID, decision source, and verification profile. This is prospective Stage-1 local-writer authority, not reconstruction of historical transitions or Issue #3 policy-engine authentication. A repeated repair rotates the generation and invalidates earlier receipts. New strictly verified imports after a repair publish their own current-generation receipt atomically with admission. The independent terminal marker always denies a snapshot that reached QUARANTINED or REVOKED, even if its admission projection was later forged back to ADMITTED. When the one-way or reinsert guard was already missing before `0014` first bootstrapped, every pre-existing admission is marked historically unprovable and cannot be re-attested; Stage 1 has no evidence to distinguish a formerly terminal row. New admissions after that bootstrap may be admitted normally. `0014` also keeps an append-only history of activation scope identities from healthy bootstrap onward, including later inserts and key updates. Repair invalidates every recorded identity even if its current activation row was deleted or renamed. If an activation guard was already missing before the first `0014` bootstrap, lost identities cannot be reconstructed, so the store enters a durable global activation quarantine; no new default can be created until an explicit future migration establishes fresh authority. A stamped `0014` store with missing or malformed fence, terminal, receipt, activation-history, or containment objects fails closed for operator quarantine rather than silently returning to generation zero.

## Provider registration identity

Provider identity is implementation-specific and separate from capability semantics.

A registration binds:

```text
provider ID/version
component/package/build identity
runtime kind/entrypoint/interface
implemented semantic major families
exact semantic contract full version/hash tested against
conformance evidence
required runtime/sandbox/network/device resources
trust/review/revocation state
```

Provider registrations are versioned/immutable enough to reconstruct what historical Tasks used.

Reusing the same registration identity must verify its stored immutable admission receipt and original snapshot linkage before attaching a missing legacy manifest payload. A corrupt historical receipt is a conflict, not a successful registration retry.

The durable provider store blocks replacement of existing registration, manifest payload, and conformance evidence identities, including SQLite `INSERT OR REPLACE`. Revocation and historical test results cannot be reset by replacing a row. A healthy provider ledger treats any recorded revoked epoch as terminal even if a registration row presents a non-revoked state.

The original trust status must match the immutable registration receipt. A later authenticated review of the same exact build appends a distinct, immutable trust-admission decision receipt with its own decision identity and revision. Decision times cannot precede registration or an earlier decision. Enablement, candidate lookup, and Task launch verify the complete original registration receipt and appended decision history before using the latest trust scope effective at the relevant time; a binding pins that source in both its receipt and a durable marker when an enabled provider is bound. Trust scopes are explicit decisions, not an inferred ranking; a registration originally denied or revoked cannot be promoted. Disablement and terminal revocation change lifecycle state without rewriting trust history. Legacy rows with a mismatched trust projection remain available for audit but cannot authorize execution.

Existing stamped `0013` stores retain their migration stamp, binding rows, and original immutable trust markers. When provider guards need repair, Task Manager may replace only the exact earlier canonical binding trust guard definitions under its fenced startup transaction; malformed or no-op definitions remain quarantined. The same transaction quarantines all existing binding trust markers because admission history under an incomplete guard set cannot be proven, even if only one binding guard was absent. Those bindings remain auditable but cannot become launch eligible after the upgrade; a new attempt is required.

The bounded automatic upgrade recognizes only the explicitly listed earlier canonical guard definitions. The changed `0013` and `0014` definitions on unmerged PR heads do not create an external compatibility promise: a store stamped by an unsupported earlier PR-head build fails strict preflight and requires an explicit, audited operator migration. Startup must not silently reinterpret a mismatched stamped guard as current.

Provider state changes append a per-registration revision to an immutable state-epoch ledger, including disable and re-enable transitions at the same timestamp. Each new binding gets an immutable internal marker for the current enabled revision; launch requires that revision to remain current. The marker is a durable control-plane sidecar, so the public binding JSON and semantic identity do not change. A stamped `0013` store whose registration or epoch-history guards or ledger definition are missing or malformed cannot prove earlier enablement or terminal revocation: Task Manager fails closed for explicit operator migration before any automatic repair. A missing binding-only guard may be repaired under the ownership fence while prior bindings are permanently quarantined. First-time migration from an unstamped baseline disables pre-existing registered rows before seeding the ledger; their earlier enablement was never proven. New binding admission also checks that the latest exact-suite passing evidence existed and had not expired at the binding creation time, using the full RFC 3339 instant, including nanoseconds and offsets.

At binding insertion, the durable receipt must match its indexed identity, policy, grant, placement, execution-profile, and creation-time projections before the immutable attempt ID is consumed. Its pinned passing evidence must name the suite declared by the registration's immutable manifest. The binding's selected snapshot must be currently ADMITTED at every repair generation and re-attested after a semantic guard repair; a provider's historical origin snapshot may remain DEPRECATED when its own re-attestation is valid. These checks enforce the existing binding and lifecycle contracts rather than changing semantic program identity.

The SQL admission clocks normalize RFC 3339 offsets to UTC seconds before comparing nanosecond fractions, including offsets outside SQLite's built-in `strftime` range. An exact earlier canonical non-history guard definition is replaced only under Task Manager's fenced upgrade; same-name malformed definitions fail preflight. State-epoch revisions near the signed 64-bit limit fail closed before an enabled transition can exhaust the last containment transition. A stamped partial or exhausted ledger requires operator quarantine without rewriting the registration or ledger.

File-backed semantic and provider registry mutations use a Task Manager writer handle bound to the identity-locked store connection and current durable lease. The writer becomes available only after Task Manager startup migration, verification, and recovery complete on that connection. Read-only registry initialization and a newly claimed lease do not grant write authority; a stale handle must fail before mutation and again before commit. Direct SQL access to the control-plane database is privileged and remains outside this safe API boundary; providers never receive it.

Idempotent conformance evidence retries compare the immutable indexed columns with the canonical evidence receipt. A legacy row whose status, suite, contract, capability, or test time differs from its receipt is rejected rather than silently treated as the same evidence.

Replacing/updating provider code creates a new provider package/build/version registration rather than silently mutating the old record's implementation identity.

## Provider lifecycle

Suggested states:

```text
DISCOVERED
QUARANTINED
REGISTERED
TEST_PENDING
TESTED
ENABLED
DISABLED
REVOKED
```

`ENABLED` means eligible for broker consideration when all other Task/policy/resource constraints pass.

It does **not** grant authority or guarantee selection.

## Conformance evidence

A provider should not be called interchangeable merely because its manifest claims the same capability ID.

A conformance result binds at least:

```text
provider registration/package/build
semantic capability major ref
exact semantic contract hash/full version
conformance suite ID/version/hash
harness version/build
test environment profile/result
result: pass/fail/partial
executed_at
```

The result should be machine-readable and retained for provider eligibility/provenance.

The local executable provider registry requires an exact conformance suite version
and hash for each registered claim. The contract and manifest schemas permit
omitting this metadata for declarative records, but those records cannot be
registered for runtime eligibility until the suite identity is supplied.

## Conformance freshness

A provider conformance result can become stale when:

- provider package/build changes;
- semantic contract hash changes;
- conformance suite hash/version changes materially;
- runtime/isolation behavior changes;
- security revocation invalidates prior eligibility.

A change to unrelated registry contracts does not invalidate every provider test automatically.

## Provider eligibility boundary

For Phase I, provider eligibility requires at minimum:

1. semantic contract resolved by current Task's Registry Snapshot;
2. provider claims the same major semantic family;
3. tested contract evidence is exact or explicitly compatible with the resolved contract under project policy;
4. provider registration is enabled/not revoked;
5. provider's declared required effects/authority/isolation do not exceed the semantic node/current execution envelope;
6. concrete Task policy/grant/resource checks still pass later.

Provider selection/ranking belongs to the Resource/Capability Broker. This registry only supplies verified candidate metadata.

## Provider trust vs conformance

Keep separate:

```text
publisher/signature trust
code/package integrity
semantic conformance
security review/reputation
runtime health
Task-specific authorization
```

A cryptographically known provider can fail conformance.

A conforming provider can still be untrusted/disabled.

A trusted+conforming provider still receives only Task-scoped authority.

## Runtime health is ephemeral

Do not mutate immutable provider registration to represent temporary facts such as:

```text
process alive
gpu queue busy
remote service unavailable
last latency
memory pressure
```

Those belong to provider-health/resource snapshots.

## No automatic code loading in semantic validation

The Semantic Registry loader never executes provider code.

Provider manifests/registrations are inspected as data.

Conformance tests run providers only through the provider test/sandbox boundary, outside semantic IR validation.

## Namespace/governance

The core project eventually needs namespaced semantic registries, but v0.1 bootstrap IDs remain fixtures.

A registry namespace authority says who may publish/update semantic contracts for that namespace under governance. It does not grant runtime Task authority.

Future community/organization registries can coexist if collision/trust/version rules are explicit.

## Offline behavior

The local system retains:

- active/default admitted semantic snapshot(s);
- contracts needed by installed providers/Skills/retained Tasks;
- provider registrations/conformance evidence;
- revocation state already known.

Core deterministic execution remains possible offline for locally available providers/contracts.

## Update/revocation behavior

A registry/provider update never silently rewrites an executing Task's exact validation/binding evidence.

For new attempts after security revocation:

- current policy may forbid the old provider/snapshot;
- Task can revalidate/replan against a current allowed snapshot/provider when semantics permit;
- historical provenance remains attributable to what actually ran.

## v0.1/Phase-I acceptance tests

At minimum:

1. import valid semantic contract fixtures and compute generated contract hashes;
2. reject malformed/duplicate-major snapshot;
3. admit valid generated Registry Snapshot;
4. atomically switch default snapshot pointer without rewriting retained Task validation evidence;
5. validate same IR against two compatible admitted snapshots and retain distinct snapshot evidence;
6. register two providers for one semantic capability family;
7. provider registration cannot redefine contract ports/effects;
8. conformance pass binds exact provider package/build + contract + suite;
9. provider update invalidates old conformance evidence for the new build;
10. contract/suite change marks evidence stale according to compatibility policy;
11. disabled/revoked provider is not eligible despite passing old conformance;
12. registration/conformance does not grant Task authority;
13. semantic validation does not execute/load provider code;
14. offline registry/provider metadata remains usable without remote catalog;
15. historical contract/snapshot records remain resolvable after default update.

## Relationship to Issue #17

Issue #17 implements the pure read-only semantic loading/index/validation primitives first.

Phase-I Issue #2 builds persistence/admission/activation/provider-registration/conformance around those primitives rather than replacing them.

The validator library should remain usable with an explicitly supplied immutable snapshot in tests/offline contexts even after the persistent registry service exists.

## Principle

> **Semantic registries define meaning; provider registries describe implementations; policy decides whether an implementation may act for this Task.**
