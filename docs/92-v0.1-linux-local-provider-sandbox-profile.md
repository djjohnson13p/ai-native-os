# 92 — v0.1 Linux Local Provider Sandbox Profile

## Purpose

The Stage-1 Provider Supervisor needs a concrete answer to a simple question:

> **What does “no ambient provider authority” mean on the first Linux reference implementation?**

This document defines the first local deterministic provider isolation target. It is intentionally narrower than a universal sandbox system.

The reference target is a small local provider such as `artifact.hash@1` that needs:

```text
one bound Artifact read stream/handle
small CPU/RAM budget
bounded stdout/stderr diagnostics
one structured result channel
no network
no credential
no GUI/device access
```

## Profile designation

Working profile:

```text
P2-LOCAL-BROKERED-v0.1
```

`P2` is the existing architecture's ordinary untrusted local-provider isolation class. This document defines the first reference implementation expectations; it does not freeze P2 forever across every OS.

## Security objective

A compromised provider process should not be able to use ordinary ambient host interfaces to access resources outside its Execution Binding/grants.

The provider should perceive something much closer to:

```text
provider executable/runtime
private scratch
bounded broker/invocation IPC
explicit inherited/brokered Artifact input/output interfaces
minimal runtime libraries
clock/random primitives as needed
```

than:

```text
logged-in user's desktop session
home directory
network
SSH/GPG/cloud agents
all environment variables
all mounted disks
session bus
clipboard/display/audio/devices
```

## Defense in depth

No single Linux primitive is the whole boundary.

Candidate v0.1 stack:

```text
unprivileged provider identity
+ no_new_privs
+ Linux capabilities dropped
+ filesystem/mount namespace or equivalent constrained root
+ Landlock where supported/useful
+ private /tmp/scratch
+ network namespace/no raw network
+ bounded IPC allowlist
+ cgroup v2 / rlimits
+ seccomp restriction after measuring provider runtime needs
+ no session/desktop agent sockets
+ disabled core dumps / ptrace restrictions where practical
+ Provider Supervisor lifecycle control
+ point-of-use trusted brokers
```

Implementation may use established tools/libraries such as namespaces/bubblewrap/container primitives rather than reimplementing Linux isolation machinery. The architecture cares about the effective boundary and tests.

## Process identity

Provider runs:

- non-root;
- with no Linux capabilities required for normal fixture operation;
- with `no_new_privs`/equivalent preventing privilege gain through exec;
- under a Supervisor-created workload/provider principal bound to the Execution Binding.

Do not run the generic provider path as root because the provider is “trusted enough.”

## Filesystem view

### Required visibility

Only what the provider runtime needs, for example:

```text
read-only provider package/runtime/library files
private scratch/tmp directory
explicit broker/IPC endpoints
optional proc subset if runtime requires it
```

### Must not be ambiently visible

```text
/home/*
/root
user Downloads/Documents/Desktop
SSH keys/config
GPG keyrings/agents
cloud CLI config/credentials
browser profiles/cookies
Git credential stores
host /tmp shared with user processes
removable media
other Task Artifact store roots
system secrets
```

If a runtime needs a shared library, expose the packaged/system runtime library—not the whole user's filesystem merely for convenience.

## Artifact access

Preferred provider input forms:

```text
broker RPC stream
read-only inherited FD/memfd
capability-safe Artifact handle that must be dereferenced by Artifact Store
```

The provider should not receive:

```text
/mnt/aios-store/all-artifacts/...
```

as a broad path root.

If an implementation uses a read-only projected path for compatibility, that projection contains only the explicitly bound Artifact and remains attempt-scoped.

Output uses `ArtifactOutputAllocation`/trusted staging writer, not arbitrary path selection.

## Network

For the first deterministic provider:

```text
raw provider network = none
```

Preferred enforcement:

- separate network namespace with no usable external interfaces; or
- equivalent sandbox primitive proving outbound sockets cannot reach host/LAN/internet.

Do not rely on "the provider promises not to use network."

Future providers that semantically require networking should use the Network Broker / explicitly granted service interfaces rather than automatically receiving unrestricted internet.

## Environment

Start from a small allowlist built by the Supervisor.

Never inherit the daemon/user environment wholesale.

Exclude, among others:

```text
AWS_*
AZURE_*
GOOGLE_*
OPENAI_*
ANTHROPIC_*
GITHUB_TOKEN
SSH_AUTH_SOCK
GPG_AGENT_INFO
DBUS_SESSION_BUS_ADDRESS
WAYLAND_DISPLAY
DISPLAY
XAUTHORITY
KUBECONFIG
HOME pointing at real user home
language/package-manager credential variables
```

If a provider needs locale/timezone/path/runtime variables, construct explicit safe values.

Provider configuration that contains authority/security meaning belongs in typed binding/profile data, not hidden environment convention.

## IPC

Allow only Supervisor/broker endpoints necessary for this binding.

For the first Artifact hash provider this may mean:

```text
one invocation/result channel
Artifact-read broker channel/FD
bounded log/progress channel
```

Do not expose by default:

```text
D-Bus session/system bus
Wayland/X11 sockets
Docker/Podman socket
containerd socket
SSH/GPG agents
browser automation/debug ports
random host Unix sockets
```

Future GUI/legacy providers use different, explicitly stronger profiles.

## Devices

No generic `/dev` pass-through beyond runtime essentials.

The first provider does not receive:

- camera;
- microphone/audio;
- input devices;
- raw block devices;
- GPU;
- USB;
- TPM/HSM;
- serial ports.

A later capability requiring a device must use a typed Device/resource binding and appropriate profile/broker.

## Seccomp

Seccomp is defense in depth, not the sole capability system.

The implementation should build the minimum practical syscall profile from the actual Rust/provider runtime and tests rather than guess a brittle permanent allowlist in architecture prose.

High-risk operations to deny unless explicitly needed include categories such as:

```text
mount/pivot/root namespace manipulation after setup
kernel module operations
ptrace of unrelated processes
BPF/perf interfaces not needed by provider
keyring interfaces not needed by provider
raw privileged sockets
reboot/kexec
process-vm access to unrelated processes
```

Exact syscall names/profile are an implementation artifact and must be regression-tested on supported reference kernels.

## Landlock / filesystem MAC

Where supported, Landlock can add a provider-side filesystem access layer after setup.

Do not make v0.1 correctness depend on silently assuming Landlock exists on every machine.

If required isolation primitives are unavailable, the Resource/Provider eligibility path should choose among:

```text
alternate supported sandbox mechanism
stronger container/VM habitat
provider ineligible on this machine
```

not:

```text
run unsandboxed because the old kernel lacks a feature
```

unless an explicit high-trust provider/profile and user/policy decision permits that separate execution class.

## Namespaces / process tree

Provider should have a bounded process view/lifecycle where practical.

Supervisor remains able to:

- terminate the provider subtree;
- detect child process creation;
- apply resource limits to the subtree;
- prevent daemonization/escaping supervision.

A provider spawning arbitrary host subprocesses should fail the Stage-1 sandbox tests.

## Core dumps / debugging

Provider crashes must not casually dump sensitive bound Artifact data or delegated secrets into a globally readable core-dump location.

Reference profile SHOULD:

- disable unrestricted core dumps;
- restrict dumpability/ptrace where practical;
- route bounded diagnostics through Supervisor.

Developer debug modes can intentionally relax some behavior, but must be visibly distinct from production-style profile and never used to claim sandbox conformance.

## Resource limits

At minimum bound:

```text
wall/monotonic deadline
memory
CPU share/time as practical
process/thread count
open file descriptor count
output/staging bytes
stdout/stderr/log bytes
```

Limit violation maps to structured Provider Supervisor reason code and must not publish partial final output.

## Randomness / time

Provider may use safe OS time/random primitives required by its semantics/runtime.

It cannot use wall-clock changes to extend Supervisor deadline/grant lifetime.

Security-sensitive bearer material is generated by trusted runtime/Broker, not by asking the provider/model for randomness.

See docs89.

## Dynamic loading / plugins

Provider package/build identity must cover the code actually eligible to execute.

Avoid loading arbitrary user-controlled plugins/config from:

```text
HOME
current working directory
language package paths
environment-defined library/plugin paths
```

after provider conformance/build identity was established.

If dynamic extensions are needed later, they become explicit package/dependency identity, not invisible ambient code.

## Sandbox bootstrap ordering

Conceptual launch:

```text
1. validate immutable Execution Binding + provider/build identity
2. create sandbox namespaces/resource limits
3. construct minimal filesystem/runtime view
4. establish only required broker/IPC endpoints
5. construct allowlisted environment
6. drop capabilities / set no_new_privs / apply MAC/seccomp defenses
7. launch provider entrypoint without shell interpolation
8. authenticate provider/workload channel identity
9. service protected broker calls under ADR 0043
10. supervise deadline/cancellation/children/resources
11. collect bounded structured result/diagnostics
12. finalize output only through Artifact Store
```

Exact ordering may vary due to Linux primitive requirements, but final provider authority must not be wider because setup was convenient.

## Graceful hardware/OS degradation

A constrained/old device is not rejected merely for lacking GPU/NPU.

However missing **security mechanism required by the selected provider profile** affects provider eligibility.

This is consistent with the hardware-adaptation principle:

```text
hardware/security facts change available providers/placement
not the conceptual Task semantics
```

## Stage-1 malicious-provider acceptance test

Create a test provider that intentionally attempts:

1. read `/etc/shadow` or an equivalent protected host fixture;
2. read synthetic secret in user-home fixture;
3. read another Task's Artifact;
4. open outbound TCP/UDP connection;
5. read cloud/token environment variable planted in parent process;
6. connect to session bus/SSH-agent fixture;
7. write outside output allocation;
8. spawn unsupervised child that persists after provider cancellation;
9. write excessive logs/output;
10. use wrong Artifact/grant/binding IDs in broker call.

Pass criteria:

- every unrelated access fails;
- the legitimate `artifact.hash@1` operation still succeeds;
- failures are attributable without leaking the planted secret;
- no final Artifact/public success appears for failed attempts.

## Conformance vs sandbox

Semantic provider conformance proves output/contract behavior for tested cases.

Sandbox enforcement constrains what the provider can actually reach.

Neither substitutes for the other:

```text
signed + conforming provider
```

may still be malicious/compromised and remains sandboxed unless an explicit stronger trust profile says otherwise.

## Non-goals

- permanently choosing bubblewrap vs OCI vs custom namespace launcher;
- supporting GUI/3D/GPU providers in the first P2 profile;
- proving security against hostile kernel/root;
- implementing a generic Linux desktop application sandbox;
- full syscall formal verification.

## Principle

> **The first provider sandbox should expose exactly the tiny world the provider needs—and tests should prove the rest of the user's computer is not accidentally part of that world.**
