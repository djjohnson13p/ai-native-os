# 11 — v0.1 Prototype

## Purpose

Prove the architecture, not the marketing claim.

The first prototype must demonstrate that task-first capability orchestration provides a materially different experience from launching applications manually.

## Host platform

Initial target:

- Linux host;
- x86_64 first for development speed;
- container/sandbox support;
- one local model provider and one optional remote model provider;
- no kernel modifications required.

This is a prototype constraint, not a permanent architecture restriction.

## Demonstration A — “Understand these numbers”

### User request

> “Understand these numbers, identify important changes, create a chart and a concise report, and save the result.”

### Inputs

- CSV and/or XLSX test dataset.

### Required system behavior

1. Intent service creates a task.
2. Planner decomposes it into typed steps.
3. Capability broker selects providers for:
   - table import;
   - calculation;
   - anomaly/change detection;
   - chart rendering;
   - report composition;
   - export.
4. Policy engine grants read access to the input and write access only to a task output directory.
5. Resource broker decides local vs model execution.
6. Executor runs the graph.
7. Verifier checks report numbers against deterministic calculations.
8. Provenance records every step.
9. Final artifacts are normal interoperable files.

### Critical constraint

The prototype UI must not require the user to manually open a spreadsheet or word processor.

## Demonstration B — Legacy application routing

Provide one legacy application/package and demonstrate:

1. package inspection;
2. habitat classification;
3. transparent launch through the appropriate compatibility environment;
4. sandbox policy application;
5. recording the launch in provenance.

For the first proof, Windows-on-Linux compatibility is a practical target because a mature ecosystem already exists.

## Prototype services

Suggested initial components:

```text
aiosd                 task/control-plane daemon
intent-service        text → structured intent
planner               intent → task graph
capability-registry   provider discovery
policy-engine         authorization decisions
executor              graph execution
resource-broker       placement/routing
provenance-store      append-only task event log
legacy-broker         package → habitat routing
shell                 task-first user interface
```

## Implementation strategy

Use boring technology wherever possible.

Candidate split:

- Rust for long-running privileged or security-sensitive services;
- Python for rapid planner/provider experiments;
- JSON Schema initially for interchange contracts;
- Unix domain sockets or a typed RPC system for local service communication;
- SQLite or another embedded transactional store for prototype state/provenance;
- OCI/container primitives for provider isolation;
- existing compatibility projects rather than reimplementation.

Language choices are provisional and should be converted into ADRs after prototype benchmarking.

## Definition of done

v0.1 is complete when:

- the end-to-end task demo runs repeatedly;
- every action has provenance;
- provider substitution works for at least one capability;
- local/remote model routing can be changed by policy;
- one repeated task can be converted into a reusable skill prototype;
- one legacy application launches through the broker;
- failure of the AI planner cannot bypass deterministic authorization.
