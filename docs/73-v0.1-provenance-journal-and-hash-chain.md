# 73 — v0.1 Provenance Journal and Tamper-Evident Hash Chain

## Purpose

AIOS provenance is not a debug log. It is the durable explanation of what a Task materially did, under which semantic program/provider/authority, with which inputs/outputs and external transfers.

The v0.1 implementation needs a small local journal that is:

- append-oriented;
- transaction-friendly with Task state changes;
- deterministically ordered;
- tamper-evident under normal integrity checking;
- privacy-aware;
- usable without AI/cloud;
- extensible to later signed/distributed checkpoints.

## Security claim

The v0.1 local hash chain is **tamper-evident**, not tamper-proof.

A privileged attacker able to rewrite the entire local database and every trusted checkpoint can construct a different chain.

Later stages may add TPM/key-backed signatures, remote transparency checkpoints, organizational audit sinks, or append-only storage.

Do not market a local hash chain as immutable proof against a fully compromised administrator.

## Stream model

v0.1 uses one primary provenance stream per AIOS Task:

```text
stream_id = task:<task_id>
```

Each event has a monotonically increasing integer `sequence` beginning at 1.

This gives deterministic local ordering without relying on timestamp ordering.

System-wide non-Task events can gain separate streams later.

## Event identity

Each event has:

```text
event_id     stable unique event identifier
stream_id    task provenance stream
sequence     monotonic within stream
event_hash   canonical hash-chain identity
```

`event_id` is useful before/independent of hashing and as a database reference.

`event_hash` establishes ordered content integrity.

Neither one is a capability grant.

## Append rule

For sequence `N`:

```text
previous_event_hash = hash(event N-1)
```

For genesis:

```text
sequence = 1
previous_event_hash = null
```

The journal rejects:

- duplicate `(stream_id, sequence)`;
- append with stale/wrong previous head;
- update/delete through normal API;
- sequence gaps unless an explicit import/recovery protocol says otherwise.

## Canonical event hash

The event hash includes the complete provenance record that is meant to be integrity-protected, excluding only the `event_hash` field itself and future detached signatures/checkpoint records.

Included examples:

```text
schema version
event_id
stream_id
sequence
task_id
semantic program hash/node when present
event type
timestamp
actor
provider/component/model identifiers
capability
authority/policy/approval refs
input/output artifact refs
execution binding/attempt refs
external-transfer record
status
previous_event_hash
bounded structured details
```

Canonicalization:

1. validate typed provenance event record;
2. construct canonical hash view excluding `event_hash`/detached signatures;
3. serialize with RFC 8785 JCS semantics;
4. hash with domain-separated SHA-256.

Conceptual prefix:

```text
AIOS-PROVENANCE-EVENT\0v0.1\0<JCS bytes>
```

Stored form:

```text
sha256:<lowercase hex>
```

The exact byte prefix/test vectors are centralized in the implementation.

## Timestamp semantics

Timestamp is part of the event hash but **not** the sole ordering source.

Rules:

- trusted control-plane code assigns/normalizes event timestamp;
- model/provider prose cannot choose authoritative timestamps merely by returning a string;
- Task stream sequence establishes order;
- wall-clock anomalies are possible and should be represented rather than rewriting history.

Later distributed provenance may need monotonic/logical clocks.

## Atomicity with Task transitions

A material Task-state transition and its provenance event should be committed in one SQLite transaction when both live in the same local state database.

Conceptually:

```text
BEGIN IMMEDIATE
  check expected Task revision
  validate state transition
  allocate/verify next provenance sequence/head
  insert provenance event
  update Task state + revision + event reference
COMMIT
```

This prevents:

```text
Task says COMPLETED
but no completion provenance exists
```

or:

```text
provenance says COMPLETED
but Task record remained RUNNING
```

The provenance append API SHOULD therefore support caller-owned database transactions rather than requiring a separate daemon/RPC round trip for every local state transition.

## Transaction ownership

Suggested v0.1 library boundary:

```text
aios-provenance
  append_in_tx(tx, event_without_hash)
  verify_stream(tx/read_conn, stream_id)
  get_head(stream_id)
  list_events(stream_id, cursor/limit)
```

The control-plane state owner coordinates the SQLite transaction.

This is a library/service boundary decision, not permission for arbitrary code to mutate provenance tables.

## Event immutability

After append, normal APIs do not edit event content.

If a prior fact needs correction, append a new event that references/corrects the prior event.

Example:

```text
operation outcome initially UNKNOWN
later reconciled as COMPLETED
```

Do not rewrite the original uncertainty out of history.

## Material event threshold

Do not emit provenance for every internal function call.

Events should capture facts users/security/recovery/debugging need, including:

- Task creation/state transitions;
- semantic plan/IR validation/revision;
- provider/resource placement decisions;
- authorization/approval decisions;
- execution attempts/start/completion/failure;
- model invocation/provider attribution;
- external egress/transfers;
- Artifact import/create/verify/integrity failure;
- irreversible/compensating external effects;
- verification start/result;
- recovery/reconciliation/rollback;
- Skill proposal/creation/execution;
- component/provider version/security-relevant activation when it materially affects execution.

Every material Task state transition uses the generic `task.transitioned` event
type. Its required typed `task_transition` object records the transition ID,
previous/new state, previous/new revision, and structured reason code. These
security- and recovery-relevant identities are not hidden in free-form details.

High-volume tracing belongs in a separate observability/telemetry subsystem.

## Privacy rule

Provenance should record **what happened without unnecessarily copying the user's private content into the audit log**.

Prefer:

```text
Artifact/Object IDs + hashes
provider/model IDs
capability IDs
semantic program/node IDs
transfer byte counts/destination classes
policy/grant/approval references
structured reason/status codes
```

over:

```text
full document contents
full prompts/responses
raw credentials
auth headers
private message bodies
secret values
arbitrary provider debug dumps
```

`details` is not a dumping ground for private payloads.

The provenance schema/implementation should set size limits and future field-level sensitivity rules.

## Model provenance

For a model call, record enough to attribute/reconstruct the runtime decision without automatically storing complete private prompt text.

Candidate fields/refs:

```text
model provider identity
model/version/deployment descriptor
request schema/version
input Artifact/Object refs and sensitivity class
local/peer/remote placement
egress transfer reference when remote
structured-output result Artifact/hash when retained
token/latency/cost accounting if available
policy decision/grant refs
verification linkage
```

Exact prompts may be retained only under explicit Task/debug/retention policy.

## External transfer provenance

Material transfer records should identify:

```text
source semantic refs
destination service/trust identity
destination class
purpose
authority/policy decision
bytes/content IDs as appropriate
started/completed/failed/partial state
```

Network endpoint details can appear as runtime diagnostics but do not replace stable service identity.

## Execution/provider attribution

A material execution event SHOULD identify exact available versions/immutable IDs such as:

```text
semantic program hash
registry snapshot ID
node ID
Execution Binding ID
provider ID/version
provider package digest/build provenance
execution profile/sandbox reference
placement decision/device/service identity
attempt number
```

This lets a historical Task answer not just "what capability?" but "which implementation actually ran?"

## Artifact linkage

Provenance events reference Artifact IDs; final/create/verify events SHOULD include content hash/version evidence when available.

Artifact content remains outside provenance JSON.

A later Artifact GC/archive operation must preserve enough metadata to interpret historical provenance according to retention policy.

## Stream verification

`verify_stream` walks events in sequence and checks:

1. sequence starts/continues correctly;
2. each `previous_event_hash` matches prior computed hash;
3. each canonical event hash recomputes exactly;
4. final computed head matches stored stream head/checkpoint if one exists;
5. schema/version is supported.

It returns structured verification diagnostics, not a boolean only.

## Checkpoints

v0.1 MAY persist a stream-head table:

```text
stream_id
last_sequence
last_event_hash
updated_at
```

This improves append performance/recovery but is not independent tamper proof.

Later signed checkpoint record:

```text
stream_id
sequence
event_hash
signer trust identity
signature profile
signature
```

belongs outside the individual event hash.

## Recovery

On control-plane startup:

- verify stream heads needed for active/nonterminal Tasks;
- detect database/task revision/event-head mismatch;
- transition uncertain Tasks into recovery rather than guessing;
- append recovery/reconciliation events after the prior durable head;
- never rewrite failed/partial history to look clean.

A full database-wide chain scan need not block every boot if integrity checkpoints/targeted verification provide equivalent evidence; v0.1 can start conservatively.

## SQLite guidance

Suggested constraints/indexes:

```text
UNIQUE(stream_id, sequence)
UNIQUE(event_id)
UNIQUE(event_hash) where non-null/appropriate
INDEX(task_id, sequence)
INDEX(event_type, timestamp) for inspection
```

Append should use transactions that prevent two writers from allocating the same next sequence.

For v0.1 a single control-plane writer / serialized append path is preferable to distributed locking complexity.

## Export

Users/developers should be able to export a Task provenance stream in a portable format such as JSONL plus a verification manifest.

Export SHOULD include enough profile/version information to verify hashes offline.

An export is a copy, not the authoritative mutable journal.

## Retention

Retention is policy-dependent.

Potential classes later:

```text
ephemeral-debug
standard-task
security-audit
organization-retained
legal/compliance
```

Never silently delete provenance required to explain a still-retained Task/Artifact/irreversible external effect.

## Failure modes

The provenance subsystem itself can fail.

For operations requiring durable provenance before effect:

- inability to append the prerequisite event MUST block the effect;
- do not perform an irreversible action and hope the audit write succeeds later.

For non-consequential observability-only events, a bounded degraded policy may differ, but core material provenance is part of correctness.

## v0.1 acceptance tests

At minimum:

1. genesis event sequence/hash validates;
2. 100-event chain validates;
3. changed historical event field breaks verification;
4. changed previous hash breaks verification;
5. deleted/missing middle event breaks sequence/chain;
6. reordering events breaks verification;
7. concurrent append attempts cannot allocate same sequence;
8. stale Task revision transaction writes neither Task transition nor provenance;
9. successful Task transition writes both atomically;
10. failed transaction writes neither;
11. event correction uses new event rather than update;
12. provenance export re-verifies offline;
13. event size/diagnostic bounds enforced;
14. secret fixture strings are rejected/redacted according to future schema policy rather than intentionally persisted by normal test APIs;
15. no model/network/provider invocation is required to verify a local stream.

## Relationship to system logging

Provenance ≠ system logs.

```text
provenance   durable material Task facts/audit/recovery
logs         developer/operator diagnostics
metrics      aggregated performance/health
traces       detailed execution timing/path
```

These can reference common Task/Binding IDs but have different privacy/retention/integrity semantics.

## Principle

> **Provenance is part of Task state correctness: append material facts before claiming or performing the state/effect they justify.**
