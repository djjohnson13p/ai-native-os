# V0.1 trusted local export coordinator entry

Status: bounded implementation contract for Issue #3, PR #47. The ordinary
external-crate integration test exercises this entry point; the wider Issue #3
case matrix remains separate work.

## Boundary

The daemon or other trusted host owns the Task Manager store and its writer
lease. Provider code never receives the manager, a coordinator handle, a
service-registration handle, or a destination writer factory. A public,
opaque trusted-host coordinator must provide one reachable path from raw
semantic program and imported source bytes to a mediated local provider
export. Merely making existing crate-private helpers public is insufficient:
the production path must construct their prerequisites without fixture SQL.

The first profile supports one Task, one validated node, one imported source,
one declared Task output allocation, and one exact mediated export. The output
is required by the current candidate finalizer; the coordinator must reserve
it from the validated `artifact.write` request rather than seed it through SQL.
The host supplies the registry, provider trust
and conformance evidence, policy, owner authentication, and exact service
configuration. The provider can propose an operation but cannot supply the
resolved service identity, approval result, grant, adapter ID, byte ceiling,
or writer factory. This first public profile releases bytes only into a sealed,
crate-owned process-local memory sink. It proves exact export authorization
and replay, but does not deliver data to an external network destination. A
future transport requires an independently mediated `network.connect` grant
and a separate point-of-use check before any network delivery.
The sink hashes and counts bytes incrementally; it retains no complete
payload in memory and exposes no payload retrieval API. Its process-local
observation describes the latest completed operation for that service.

## Evidence map

| Entry | Required admission | Rejection evidence |
| --- | --- | --- |
| Trusted host bootstrap | Live Task Manager writer lease, strictly admitted registry and provider, trusted policy, exact service catalog and sealed memory sink | No public writer, callback, or stream setter; malformed or disabled registration cannot be selected |
| Program and source admission | Raw IR is validated by the real validator against the admitted snapshot; Task, plan, program, validation result, active pointers and transition provenance commit coherently; source import is keyed and verified | Invalid IR or stale snapshot leaves no executable program, candidate, or writer call |
| Candidate and policy | Reservation seals source content revision, exact service, adapter, operation, purpose, sensitivity and whole-operation byte limit; policy evaluates that tuple | Changed source/service, undeclared egress, local-only Task, missing source read, or hard deny produces no executable grant |
| Approval and finalization | Every requiring decision has a persisted canonical prompt and authenticated owner decision; all one-shot approvals are rechecked under the finalization lock; read and egress grants issue atomically | Stale, missing, denied, or withdrawn approval, or provider/build/program/policy/binding change leaves no runnable export authority |
| Cancellation | An authenticated Task owner requests ordinary guarded cancellation by durable Task ID and stable transition ID, or through a retained handle | Unknown or active effects refuse cancellation; accepted cancellation revokes eligible grants and fences retained handles |
| Export use | An opaque execution context first enters `RUNNING` through the guarded transition, then resolves a finalized pin, obtains the authenticated source scope, and invokes the existing destination issuer and byte-transfer path into crate-owned memory | Unauthorized use never opens the sink or releases bytes; expiry, revocation and retained handles are rechecked at use |
| Replay and recovery | Operation ID binds the complete tuple and historical receipt; uncertain external effects remain fenced | Replaying an operation cannot invoke a second writer or infer exact authority from legacy class-only evidence |

Task creation now commits the host-chosen privacy constraints in the genesis
row and `task.created` event. The provenance event contract accepts the same
typed constraint fields as the Task record; old null-constraint events remain
valid. This is additive for old journals and does not rewrite their hashes.
The first Task plan must satisfy the Task Plan schema and match the Task,
revision, node, and capability admitted from the validated program. A source
import must carry a stable import ID so retry cannot create a second source.

Finalization returns a handle while the Task is `RUNNABLE`. The owner may
cancel at this point, which revokes the issued grants before any export begins.
The first export call performs the ordinary guarded `RUNNABLE → RUNNING`
transition only after preflighting the current service and exact candidate
pin. A disabled service or withdrawn grant denies while the Task remains
`RUNNABLE`, so the owner can still cancel. After admission starts an attempt, cancellation refuses
until the attempt and any effect have a contained outcome. A restarted host
can request cancellation by authenticated Task ID without retaining a
process-local handle.

The host may persist a prepared export's serializable replay reference before
opening the destination. A reopened coordinator checks its Task, candidate,
binding, exact source and destination pins, operation, purpose, and ceiling
against immutable store rows and the authenticated completion receipt. The
reference itself grants no authority and cannot start or repeat the export.
Historical replay does not require a current grant or a live destination
adapter, including when the service was later disabled. This historical
receipt does not recover transient memory sink contents after restart.

An external integration test must compile the ordinary library and use only
the production coordinator API for Task creation, raw IR admission, source
import, reservation, evaluation, approval, finalization, and export. It may
read the database to inspect durable evidence, but must not insert validation,
program, plan, approval, or grant rows directly. Positive export and denied
substitutions must assert the authenticated byte count and SHA-256 digest,
sink-open count, typed denial, and durable operation/grant state. In-crate
protected-path tests can additionally compare literal bytes. The public API
exposes only sink metadata and never returns the payload or a writer handle.

## Program admission and replay

Admission is one serialized Task transition, not a committed pre-transition
pointer update. The transition's idempotency identity binds raw program and
plan digests, registry snapshot, Task revision/state, and operation kind. The
validator result, plan/program revisions, active pointers, old-authority
retirement where applicable, and `task.transitioned` provenance commit in
one transaction. Replays with the same identity and different content
conflict. A historical successful admission replays its original receipt,
even after a later revision supersedes it.

The initial `CREATED → PLANNING` admission is sufficient to make the first
exact-export path reachable. Later `WAITING_FOR_AUTH → PLANNING` replacement
must permanently retire pending approvals and old authority, including an
A→B→A semantic-hash return; it must not rewrite finalized historical
receipts. `RUNNABLE → PLANNING` also requires a complete no-effect fence for
all Task operations and retained handles before it can be admitted. A test
that seeds these states through SQL cannot establish this production contract.
