# 89 — v0.1 Trusted Time, Expiry, and Randomness Semantics

## Purpose

AIOS uses time and randomness in security-sensitive places:

```text
Authority Grant expiry
Approval validity
Credential/token lifetime
Provider deadlines/timeouts
Task scheduling/retry windows
package/signature/revocation metadata
network/service sessions
idempotency/nonces/opaque bearer handles
provenance timestamps
```

A naive implementation that trusts wall-clock time blindly can resurrect expired authority after clock rollback, while an implementation that requires network time would violate offline recovery goals.

This document defines the v0.1 boundary.

## Time concepts are distinct

Do not use one timestamp primitive for every purpose.

### Wall-clock / civil time

Used for:

- user-visible event timestamps;
- absolute grant/credential expiry across reboot;
- policy effective dates;
- audit/provenance ordering evidence between sessions/devices (with limitations).

Wall-clock can jump because of manual changes, NTP, RTC errors, VM snapshots, suspend, timezone changes, or malicious configuration.

### Monotonic time

Used inside one boot/process session for:

- provider deadlines;
- timeouts;
- rate windows where appropriate;
- measuring duration/latency;
- ensuring a 30-second grant does not become 3 hours because wall clock moved backward during the process.

Monotonic clocks do not survive reboot as one universal timeline.

### Logical/revision ordering

Used for:

- Task revisions;
- provenance sequence numbers;
- Artifact/Object revisions;
- operation/attempt ordering.

Do not infer durable causal ordering solely from wall-clock timestamp order.

## Authority Grant lifetime

A persisted grant has absolute `issued_at` / `expires_at` metadata.

When issued in a running daemon, runtime should also retain a monotonic deadline derived from the grant lifetime for point-of-use checks during that boot/process session.

Effective validity is the stricter of:

```text
persisted absolute expiry
current monotonic session deadline (when available)
revocation/consumption/current Task/binding validity
```

A clock jump forward can expire a grant early; it must not silently reactivate later if wall time moves back.

## Last-seen wall-clock anchor

Persist a trusted-core `last_observed_wall_time` / boot-time assessment periodically or at relevant shutdown/commit points.

At startup:

```text
current_wall_time
vs
last_observed_wall_time
vs
RTC/system time source metadata where available
```

If current time is materially earlier than the trusted last-seen value beyond a configured tolerance, the system enters:

```text
TIME_UNCERTAIN
```

for security-sensitive expiration decisions.

The exact tolerance is an implementation/configuration value, not semantic-program identity.

## TIME_UNCERTAIN behavior

In `TIME_UNCERTAIN`:

- do not resurrect grants/approvals/credentials that may have expired;
- deny or require deterministic recovery/revalidation for time-limited protected actions;
- keep local non-time-sensitive recovery/read-only operations available;
- surface the clock problem through trusted UI/diagnostics;
- allow an authenticated administrator/user or trusted time source to restore normal time confidence according to policy;
- record the event in provenance/system audit.

The model may explain the problem but cannot declare time trustworthy.

## Offline behavior

Network time is **not mandatory** for normal offline boot/recovery.

A machine with reasonable RTC/last-seen consistency can operate using local time.

If the local clock is clearly inconsistent/rolled back, security-sensitive time-limited authority fails closed while deterministic recovery remains available.

## Suspend/resume

Provider timeouts/deadlines should define whether suspend time counts.

Default recommendation for v0.1 protected runtime operations:

- use a monotonic clock semantics that does not grant extra authority because the machine slept;
- on resume from long suspension, revalidate expiring grants/credentials before the next protected operation;
- remote sessions/connections are treated as potentially stale.

Exact OS clock primitive selection is implementation-specific and must be tested on the reference platform.

## VM snapshot / system rollback

Restoring an old VM/system snapshot can roll back:

- database state;
- wall clock;
- grant-use counts;
- revocations;
- provenance;
- package/security state.

v0.1 cannot universally detect a full privileged snapshot rollback without an external/monotonic hardware anchor.

Claims must therefore distinguish:

```text
ordinary process/power crash recovery
vs
full storage/system snapshot rollback resistance
```

Future higher-assurance systems may use TPM counters, remote checkpoints, secure clocks, or organization services.

Do not claim those properties in v0.1 unless implemented.

## Provenance timestamps

Every provenance event retains a wall-clock timestamp for human/audit usefulness, but stream order is defined by:

```text
Task stream sequence
+ hash-chain linkage
```

not timestamp sorting.

When time confidence is uncertain, provenance SHOULD record time-confidence/clock-adjustment diagnostic events rather than rewriting prior event timestamps.

## Provider deadlines

Provider invocation deadline enforcement uses monotonic duration/deadline in the supervisor.

The provider does not choose/extend its deadline by returning a timestamp.

Wall-clock changes do not extend an already-running provider attempt.

## Credential lifetimes

Credential Broker uses:

- external credential absolute expiry/issuer metadata;
- current handle status/revocation;
- runtime monotonic lifetime for newly delegated short-lived tokens where possible;
- `TIME_UNCERTAIN` fail-closed behavior when absolute expiration cannot be trusted.

A refresh-token/source credential does not become safe to use merely because an external token endpoint accepts it; AIOS current authority still applies.

## Opaque token / nonce randomness

Opaque bearer material, idempotency nonces whose unpredictability matters, local secret material, pairing challenges, and cryptographic keys MUST use the operating system cryptographically secure random source.

Do not use:

- language default pseudo-random generators intended for simulation;
- timestamps;
- sequential Task IDs;
- model-generated "random" strings;
- hashes of predictable public metadata

as bearer secret material.

## Identifier uniqueness vs secrecy

Many stable identifiers need uniqueness/traceability but not secrecy:

```text
Task ID
Artifact ID
binding ID
attempt ID
transition/publication ID
policy decision ID
```

They may use UUID/ULID/content-addressed forms if collision resistance/ordering needs are satisfied.

Do not rely on an identifier being hard to guess as the authorization mechanism.

An opaque runtime token/bearer capability is different: its secret material must be unpredictable **and** validated against server-side grant state.

## Hash randomness is unnecessary

Semantic/content hashes are deterministic identities, not secrets.

Do not salt AIOS semantic/content hashes merely to make them secret; privacy for sensitive content is handled by access control/encryption/storage policy.

Be aware that hashes of low-entropy sensitive content can reveal equality/dictionary information if exposed. Avoid exposing content hashes to untrusted parties without policy need.

## Clock/time reason codes

Trusted services should have a stable cross-service time-confidence reason family, for example:

```text
TIME_OK
TIME_ROLLBACK_DETECTED
TIME_UNCERTAIN
TIME_SOURCE_UNAVAILABLE
TIME_EXPIRED
TIME_NOT_YET_VALID
```

Subsystems can map these into their own namespace (`AUTH_TIME_UNCERTAIN`, `CRED_TIME_UNCERTAIN`, etc.) while retaining the root reason internally/auditably.

## v0.1 acceptance tests

1. wall clock moves backward during an active short-lived grant → monotonic deadline prevents extension;
2. reboot with current clock earlier than persisted last-seen anchor beyond tolerance → `TIME_UNCERTAIN`;
3. `TIME_UNCERTAIN` does not resurrect expired/revoked one-shot grants;
4. local Task/provenance/Artifact inspection/recovery remains available while time-sensitive external action is denied;
5. wall clock jumps forward → current grant can expire early but moving clock backward again does not reactivate it;
6. provider timeout is unaffected by wall-clock adjustment;
7. provenance sequence remains correct despite equal/reversed wall timestamps;
8. delegated credential lifetime never exceeds source/current grant lifetime;
9. opaque bearer/token test uses OS CSPRNG and cannot be reproduced from Task ID/timestamp;
10. predictable IDs do not grant access without matching Authority Grant;
11. time-adjustment/trust-state change is auditable;
12. simulated full VM snapshot rollback is documented as outside v0.1 guaranteed detection unless an external/hardware anchor is configured.

## Non-goals

- globally synchronized distributed clock;
- Byzantine time service;
- full rollback protection against root/hypervisor snapshot attacker;
- blockchain/time-ledger infrastructure;
- requiring internet/NTP for offline operation;
- specifying one permanent UUID/ID library.

## Migration note for the local prototype

`specs/persistence-v0.1-0018-trusted-time.sql` is the reconciled migration for the
Task Manager's durable local time-confidence anchor. The earlier optional
`specs/persistence-v0.1-0002-time-trust.sql` is a design draft: the Task Manager
does not execute it or accept its migration stamp. Existing stores without 0018
receive the new state on migration; a malformed or unknown migration history
fails preflight. The local database anchor cannot detect a full snapshot rollback
of both the database and clock. That remains outside v0.1 protection without an
independent external or hardware anchor.

## Principle

> **Use monotonic time for durations, wall time for human/absolute expiry semantics, logical revisions for ordering, and never let a clock rollback silently extend authority.**
