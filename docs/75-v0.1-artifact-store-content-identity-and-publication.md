# 75 — v0.1 Artifact Store: Content Identity, Publication, and Recovery

## Purpose

AIOS capabilities exchange typed Artifact handles instead of ambient filesystem paths.

The v0.1 Artifact Store must make that abstraction real without turning the local filesystem layout into semantic identity.

It needs to safely support:

- user-selected input import;
- Task-scoped read handles;
- provider output allocation;
- streaming writes;
- content hashing/integrity;
- crash-safe publication;
- lineage/provenance;
- content deduplication without identity collapse;
- portable export;
- retention/garbage collection;
- future replica/cloud/peer placement without changing Artifact identity.

## Core identity split

AIOS separates three concepts:

```text
Semantic Object
  durable logical thing across versions/representations

Artifact
  one immutable published content/version instance + lineage

Storage Replica / Namespace Projection
  where/how Artifact bytes are currently materialized
```

Example:

```text
object://document/customer-proposal
   ├── artifact://proposal-rev-7-docx
   ├── artifact://proposal-rev-7-pdf
   └── artifact://proposal-rev-8-docx
```

Each Artifact can have local/peer/cloud replicas and filesystem projections without changing its Artifact identity.

## Published Artifact immutability

Once an Artifact is published:

```text
content bytes
content hash
content length
primary media type/content representation
origin Task/node/binding
core lineage
```

are immutable.

Editing/transformation creates a **new Artifact** linked through lineage (`derived_from`, `supersedes`, representation relationship, etc.).

This gives Tasks/recovery/provenance a stable input identity.

Mutable logical document/product/project identity belongs to the Universal Object layer, not by rewriting an old Artifact's bytes.

## Artifact ID vs content hash

They are different identities.

```text
artifact_id   logical immutable content-instance/lineage identity
content_hash  identity/integrity of bytes
```

Two Artifacts may share the same content hash but remain distinct Artifact records because they were produced/imported in different Task/semantic contexts or have distinct retention/lineage relationships.

The Blob Store may deduplicate the physical bytes.

Do not collapse Artifact identity solely because content hashes match.

## Internal Artifact URI

The canonical Artifact handle should use an AIOS scheme such as:

```text
artifact://<artifact-id>
```

It must not expose the host store path.

Concrete materialization belongs to Storage Replica / Namespace Projection records.

## Blob content identity

v0.1 uses SHA-256 as the bootstrap blob content hash with algorithm-tagged form:

```text
sha256:<lowercase hex>
```

Content hashing is over exact bytes.

This is an Artifact-byte identity, distinct from AIOS semantic-program/contract/registry/provenance hash domains even when SHA-256 is used everywhere.

## Local store layout is implementation detail

A possible local store could physically use:

```text
<store>/blobs/sha256/ab/cd/<digest>
<store>/staging/<allocation-id>
```

but this path layout is not a public semantic contract.

Do not put these paths into AIOS IR, Semantic Objects, or provider semantic interfaces.

## User input import

For the first prototype, user-selected persistent input is copied/streamed into the local Artifact Store before deterministic Task execution depends on it.

Import pipeline:

1. trusted UI/file broker receives user selection;
2. deterministic policy grants read of that selected source;
3. Artifact importer opens the source through the mediated boundary;
4. stream bytes into a staging object while hashing/counting;
5. capture declared/detected media type under explicit parser rules;
6. fsync/close staged content;
7. atomically place/deduplicate immutable blob;
8. create Artifact record + provenance in one metadata transaction;
9. return Artifact Handle.

The original host path is optional provenance/import metadata, not Artifact identity.

For v0.1 this copy-in behavior prioritizes reproducibility over zero-copy optimization.

Later optimizations may use reflinks/content-addressed external replicas when immutability/integrity can be proven.

The local implementation binds one canonical Artifact Store root and its filesystem
identity to the locked SQLite database identity. Reopening the same database through
a hardlink, symlink, case, or other path alias must reuse that binding. Store-relative
operations are resolved through an already-open directory capability; lexical path
validation alone is not sufficient because a staging/blob/quarantine directory can be
replaced by a symlink or reparse point after validation.

## Output allocation

A provider does not choose an arbitrary final host path.

Before provider execution, the control plane creates a Task-scoped Output Allocation such as:

```text
allocation_id
task_id
semantic program/node
binding/attempt
expected semantic type/media types
maximum size
sensitivity
retention class
expiry
```

The provider receives only an opaque writable output handle/projected staging destination authorized for that allocation.

It cannot turn `task.output` into `/home/user/anything`.

For the v0.1 mediated streaming API, successful reader/writer handle issuance is
the protected-use boundary that atomically consumes a `ONE_SHOT` grant. The
issued handle retains a non-transferable admission to that exact
Task/principal/binding/attempt/action/resource tuple so individual stream calls
do not consume the grant again. Every read, seek, write, flush, and finalize
still revalidates the current Task and binding lifecycle, manager lease, grant
expiry/revocation, and approval lifecycle; durable consumption never turns
revocation or cancellation into continuing authority.

## Provider write boundary

Preferred provider interfaces expose:

```text
open/write/stream/finalize output allocation
```

or a tightly scoped sandbox file projection.

A provider should not receive write access to the final blob store/index.

The store owns final content hashing/publication.

## Publication pipeline

A provider produces candidate bytes into staging.

Publication is deterministic:

```text
1. close/finalize provider writer
2. verify allocation still belongs to current Task/node/attempt
3. enforce size/quota limits
4. compute/finalize content hash + byte length
5. validate required media/type/output contract where applicable
6. fsync staged content and parent metadata as required for local durability
7. place/deduplicate bytes into immutable blob store
8. begin metadata transaction
9. create immutable Artifact record
10. create lineage relations
11. append Artifact/provenance journal event
12. attach Artifact to Task output/step result if required
13. commit metadata transaction
14. return Artifact Handle/publication result
```

Finalizing a streaming writer durably seals the exact staged byte length and SHA-256
after the writable file has been flushed, synced, and closed. Publication requires
that trusted seal and independently verifies the staged bytes against it. A live or
unclosed writer is not publishable.

Blob placement never streams directly into the final digest pathname. It writes and
syncs a unique pending blob, verifies its exact length/hash, atomically promotes it
without overwriting an existing digest path, and syncs the parent directory. Startup
reconciliation completes valid interrupted pending placements as orphan candidates;
metadata publication remains a separate authenticated transaction.

A provider process exiting successfully is **not** equivalent to Artifact publication success.

## Atomicity boundary

The filesystem blob move and SQLite metadata commit cannot always be one ACID transaction.

v0.1 uses a recoverable two-resource protocol:

### Before metadata commit

The content blob may exist without a published Artifact record.

This is an **orphan blob candidate**, not user-visible Task output.

### After metadata commit

A published Artifact record must reference a durable immutable blob whose expected content hash/size is known.

If metadata commits but the blob cannot be found/verified during recovery, the Artifact is integrity-failed and the Task cannot silently claim success.

## Crash recovery cases

### Staging file exists, no committed allocation/publication

If expired/unreferenced:

```text
cleanup/quarantine staging residue
```

Never promote it merely because bytes exist.

### Immutable blob exists, no Artifact record

Treat as unreferenced/orphan blob.

It may be reclaimed after a safety window or reused if a future publication independently computes the same hash.

### Artifact metadata exists, blob missing/corrupt

Mark/detect integrity failure.

Do not regenerate/replace silently unless the Task explicitly reruns the producing semantic step and creates a new/reconciled Artifact result.

### Publication committed, response lost

Stable `publication_id`/allocation state permits idempotent lookup/reply rather than creating duplicate Artifact records accidentally.

## Publication idempotency

Every finalize request uses stable `publication_id` or an allocation-scoped one-time finalize identity.

Rules:

```text
same allocation + same publication_id + same computed content
  -> return prior publication result

same publication_id + incompatible allocation/content
  -> reject ID reuse conflict
```

This mirrors Task transition idempotency.

## Artifact metadata mutability

Content identity/core lineage is immutable.

Administrative metadata may evolve under a separate Artifact metadata revision, for example:

- user label/title;
- retention/pin state;
- workspace relationship;
- added non-authoritative tags.

Sensitivity/classification lowering is security-sensitive and requires explicit policy; it must not be a casual metadata edit.

Changing media/semantic meaning generally creates a new Artifact/representation rather than rewriting the immutable content contract.

## Semantic type vs media type

Artifact publication can carry both:

```text
semantic_type_ref
media_type
format/profile metadata
```

A file extension alone does not prove semantic type.

A provider claiming an output semantic type must satisfy its capability/type conformance/validation rules before downstream deterministic code trusts that type.

## Artifact read boundary

A provider receives a read handle scoped to named Artifacts required by its Execution Binding.

Possible implementation:

```text
opaque Artifact reader API
or read-only sandbox projection of exact Artifact(s)
```

The provider does not receive the blob-store root or user's home directory.

## Integrity on read

The local store should protect immutable blobs from ordinary modification using ownership/permissions and validate expected size/hash when integrity is uncertain.

Possible v0.1 policy:

- verify exact hash on import/publication;
- immutable store files not writable by provider/user processes;
- record size/hash;
- rehash on recovery/integrity suspicion/export verification according to policy;
- never trust a changed mtime alone as integrity proof.

## Large Artifact handling

Large CAD/media/scientific/model files cannot be copied through control-plane JSON/SQLite.

The store interface must support bounded streaming and later range/chunk access.

v0.1 may initially stream full files, but APIs should not require `Vec<u8>`/whole-file-in-memory semantics for all Artifacts.

Potential later optimization:

- chunk/content-addressed manifests;
- sparse/range readers;
- shared-memory/mmap under isolation policy;
- reflink/local zero-copy replicas;
- peer content cache;
- resumable transfer.

## Task output allocation classes

Initial output selector:

```text
task.output
```

may map to one or more Artifact Output Allocations.

Task completion guards verify required allocations have become durably published Artifacts.

Temporary/intermediate outputs can use Task-scoped retention classes and remain available for recovery until safe GC.

## Export to user filesystem

Export is a separate capability/action:

```text
Artifact -> chosen destination path/URI
```

It requires destination authority and produces provenance.

Exporting does not move/rename the Artifact identity itself.

A later user edit to the exported file does not mutate the stored Artifact; re-import/sync creates a new Artifact/version relationship when desired.

## Retention and garbage collection

Do not delete bytes solely because a Task is terminal.

Reachability/retention roots may include:

- Task inputs/outputs retained by policy;
- Semantic Objects/representations;
- active/nonterminal/recovering Tasks;
- installed Skills/compiled targets/models/packages;
- rollback/recovery references;
- user pins/workspaces;
- required provenance/legal retention;
- active Storage Replicas/transfers.

Blob GC should use reference/reachability + retention policy and a safety/quarantine window.

Because many Artifact IDs can share one blob hash, a blob is deletable only when no retained Artifact/replica/package reference needs it.

## Secrets are not ordinary Artifacts

Passwords/API tokens/private keys should use Credential/Secret handles and secure stores, not Artifact content storage merely because the Artifact Store can persist bytes.

Accidentally imported secret-like user files are still user Artifacts, but provider access remains policy-scoped and should not convert them into credential handles automatically.

## At-rest security

The architecture should permit:

- per-user/org storage ownership;
- filesystem permissions;
- optional encrypted volume/blob store;
- future per-object encryption keys;
- secure deletion policies where feasible.

v0.1 need not invent custom encryption. It must not bake an unencrypted cloud/object-store assumption into Artifact identity.

## SQLite metadata boundary

Suggested core metadata tables/entities:

```text
artifacts
artifact_lineage
artifact_metadata_revisions
output_allocations
artifact_publications
blob_objects
artifact_blob_refs
```

Storage Replicas/Namespace Projections can remain separate tables/modules so the core Artifact identity survives future distributed storage.

## Output allocation states

Suggested:

```text
ALLOCATED
WRITING
FINALIZING
PUBLISHED
ABORTED
EXPIRED
FAILED
```

A published allocation is terminal/idempotent for its successful publication.

Candidate bootstrap families:

## v0.1 acceptance tests

At minimum:

1. import a synthetic file and compute exact content hash/size;
2. same source path changed after import does not mutate imported Artifact;
3. import same bytes twice can deduplicate blob while retaining distinct Artifact IDs/lineage;
4. provider can read only explicitly bound Artifact handle;
5. provider output allocation cannot escape staging/assigned destination;
6. oversized output fails before publication;
7. successful publish returns immutable Artifact Handle;
8. publishing same `publication_id` after response loss is idempotent;
9. conflicting reuse of publication ID is rejected;
10. crash before metadata commit leaves recoverable staging/orphan blob, not published Artifact;
11. metadata referencing missing/corrupt blob fails integrity/recovery;
12. Task completion guard sees only committed published required Artifacts;
13. exported file path change/rename does not change Artifact ID;
14. deleting one Artifact record does not delete deduplicated blob still referenced elsewhere;
15. large fixture streams without requiring full content in SQLite/control-plane JSON;
16. no provider receives blob-store root path/ambient user filesystem authority.

## Relationship to later Storage Fabric

Stage 4 can add:

```text
replicas
peer caches
cloud/edge storage
sync
content transfer
namespace projections
```

without changing v0.1 Artifact identity/publication semantics.

`specs/storage-replica.schema.json` and `specs/namespace-projection.schema.json` already preserve this boundary.

## Principle

> **A published Artifact is immutable content plus lineage; where its bytes live and which path shows them are replaceable runtime projections.**
