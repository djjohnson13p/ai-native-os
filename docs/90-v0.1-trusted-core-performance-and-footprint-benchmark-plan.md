# 90 — v0.1 Trusted-Core Performance and Footprint Benchmark Plan

## Purpose

AIOS adds semantic validation, authority, Artifact handles, provenance, provider isolation, and recovery layers that conventional ad-hoc scripts often skip.

Those layers are justified only if their overhead remains small enough that the system can operate on ordinary and constrained hardware while providing the security/portability benefits they exist for.

This document defines what to measure before making performance claims. It deliberately avoids inventing target numbers without implementation evidence.

## Principle

> **Measure every abstraction tax separately before optimizing or claiming it is negligible.**

## Measurement categories

For one Task, distinguish:

```text
T_parse          strict serialization parse/limits
T_schema         structural schema validation
T_semantic       graph/type/capability/effect validation
T_hash           normalization/JCS/hashing
T_task           Task persistence/transitions
T_artifact       import/handle/hash/publication overhead
T_provenance     event construction/hash-chain/persistence
T_policy         authority request/resource resolution/policy decision
T_grant          grant issue/check/consume/revoke
T_binding        provider resolution + Execution Binding creation
T_sandbox        provider startup/isolation setup
T_provider       actual useful provider computation
T_finalize       output publication/integrity/lineage
T_recovery       restart/reconciliation overhead
T_model          later planner/reasoning work
T_network        later transfer/remote latency
```

Report both absolute time and percentage of end-to-end latency.

Do not hide policy/provenance/startup overhead inside "provider execution."

## Memory/footprint categories

Measure:

```text
idle control-plane RSS
validator peak RSS
registry snapshot memory
Task/provenance SQLite footprint
Artifact metadata overhead
provider supervisor memory
sandbox/provider process memory
per-active-Task state
per-1,000-event provenance growth
per-1,000-Artifacts metadata growth
```

Large Artifact/model bytes are measured separately from control-plane metadata.

## Reference hardware classes

Use real hardware when available and deterministic resource limits/cgroups for repeatability.

### C1 — constrained baseline

Simulate something like:

```text
2 logical CPU cores
4 GiB RAM limit
no GPU/NPU requirement
local SSD-class storage
```

This is not a minimum installation promise; it is a pressure test for trusted-core bloat.

### C2 — ordinary laptop/desktop

Representative modern x86_64 Linux environment with enough RAM for development and normal local providers.

### C3 — capable workstation

More cores/RAM and GPU where later Resource/Model/CAD workloads require it.

The trusted deterministic core should not need C3 merely to validate/authorize/hash a small Task.

## Benchmark B0 — strict parser / validator

Fixture groups:

```text
minimal 1-node program
Demonstration A program
64-node valid DAG
512-node schema-limit DAG
invalid early-parser case
invalid late-semantic case
max-diagnostic adversarial case
```

Measure:

- cold/warm latency;
- peak memory;
- allocations if practical;
- malformed-input throughput;
- canonicalization/hash cost separately;
- registry load vs reused immutable snapshot.

Properties matter more than raw speed initially:

- bounded work;
- no panic;
- deterministic result;
- no network/provider/model access.

## Benchmark B1 — Task + provenance write path

Measure:

- create Task + provenance;
- legal state transition + provenance;
- rejected CAS transition;
- idempotent replay of committed transition;
- event-chain verification for 10/100/1,000/10,000 events;
- SQLite WAL/checkpoint behavior.

Report durability setting (`synchronous` etc.) with results.

Never compare a durable `FULL` transaction to an unsafe in-memory baseline without labeling the durability difference.

## Benchmark B2 — Artifact import/publication

Test sizes:

```text
1 KiB
1 MiB
100 MiB
1 GiB where test hardware permits
```

Measure:

- copy-in throughput;
- SHA-256 hashing throughput;
- dedupe lookup;
- staging/finalize metadata overhead;
- fsync/rename/DB publication cost;
- startup orphan reconciliation.

Separate:

```text
physical byte copy/hash cost
vs
AIOS metadata/policy/provenance overhead
```

## Benchmark B3 — Authority path

Using builtin deterministic fixture policy backend:

- exact Artifact-read allow;
- hard deny;
- approval-required classification;
- point-of-use grant validation;
- one-shot grant consumption;
- revocation lookup;
- 1/10/100 concurrent protected operations.

Then repeat with Cedar adapter if adopted.

Report differential overhead rather than assuming the backend is negligible.

## Benchmark B4 — Provider startup tax

For `artifact.hash@1`:

compare:

```text
in-process trusted baseline hash (measurement only)
provider process cold start
provider process warm/reused supervisor path if allowed
Wasm component path later
container path later
```

The in-process baseline is not necessarily an allowed production provider architecture; it quantifies isolation cost.

Measure:

- startup latency;
- memory;
- useful compute latency;
- broker/handle overhead;
- result serialization;
- sandbox setup cost.

## Benchmark B5 — complete deterministic spine

Run the Stage-1 reference Task from docs86.

Measure:

```text
Task create
Artifact import
IR validate/hash
Registry/provider resolve
Policy/grant
Binding
provider startup+hash
result/provenance
Task complete
```

Produce a waterfall/table showing where time goes.

Repeat 100+ times for warm-path distribution after correctness is established.

## Benchmark B6 — restart/recovery

Create fixture DBs with:

```text
10 active Tasks
100 active Tasks
1,000 historical Tasks + a few active Tasks
staging/orphan Artifacts
RUNNING/UNKNOWN attempts
expired/revoked grants
```

Measure:

- startup time until deterministic core is usable;
- active/relevant reconciliation time;
- memory;
- provenance verification policy.

Recovery should eventually avoid O(all-history) full scans on every boot, but do not prematurely optimize before profiling proves it necessary.

## Benchmark B7 — constrained resource denial

Set intentionally low:

- memory limit;
- max IR bytes/nodes;
- max log/output bytes;
- provider deadline.

Pass criteria:

- deterministic reason code;
- bounded resource usage;
- no host instability;
- no partial published output.

## Benchmark B8 — security overhead vs bypass temptation

For each subsystem, document the unsafe shortcut that would be faster:

```text
skip semantic validation
skip fsync
skip point-of-use grant check
let provider open host paths directly
skip provenance transaction
reuse process with ambient environment
```

Never adopt the shortcut merely because the benchmark is faster.

If overhead is unacceptable, optimize the mechanism while preserving the invariant, or propose an explicit architecture change with evidence.

## Regression policy

After the first implementation establishes baseline distributions:

- store benchmark input fixtures/configuration in the repo;
- track median and tail latency;
- track peak memory/control DB growth;
- flag material regressions in PRs where practical;
- do not create brittle CI timing gates until infrastructure noise is understood;
- require explanation for large trusted-core regression even if functional tests pass.

## Reproducibility metadata

Every reported benchmark includes:

```text
commit SHA
build profile/compiler version
OS/kernel
CPU/RAM/storage class
container/VM/cgroup limits
SQLite settings
provider/build identities
registry/policy snapshot identities where relevant
fixture sizes/counts
cold vs warm
sample count
```

For model/remote benchmarks later also include:

```text
model/provider version
quantization/backend
network conditions
cost accounting window
```

## Claims policy

Before measurements, say:

> "The architecture is designed to reduce repeated reasoning and support constrained hardware."

After evidence, we may say exactly what was measured:

> "On reference hardware X, a warm deterministic Task adds Y ms control-plane overhead; Skill reuse reduced planner calls by Z%."

Do not claim "AIOS becomes dramatically faster over time" without workload-specific data.

## Non-goals

- choosing performance targets before baseline evidence;
- micro-optimizing JSON before functionality is correct;
- benchmarking every future Domain Pack;
- competing with raw C syscall microbenchmarks;
- hiding security/durability differences between compared paths.

## Principle

> **The architecture should earn its abstraction layers with measured portability, safety, and reuse—not assume their cost is free.**
