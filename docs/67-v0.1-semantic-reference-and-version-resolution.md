# 67 — AIOS v0.1 Semantic Reference and Version Resolution

## Purpose

AIOS IR uses compact references such as:

```text
table.import@1
data.table@1
```

while registry contract records use full versions such as:

```text
table.import version 1.0
data.table version 1.0
```

The first validator cannot safely guess how `@1`, `@1.0`, or an unversioned name should resolve.

This document defines the v0.1 rule.

## Decision summary

For AIOS IR v0.1:

```text
semantic reference grammar = <semantic-id>@<major>
```

Examples:

```text
table.import@1
data.table@1
experimental.example@0
```

Unversioned semantic references are invalid.

Minor/patch selectors such as `@1.0` or `@1.0.2` are not part of AIOS IR v0.1 authoring syntax.

Semantic contract records still carry full contract versions:

```text
1.0
1.1
1.1.2
```

The immutable Registry Snapshot determines which exact full contract version satisfies one major selector.

## Why major selectors

A semantic major version represents a compatibility family.

An AIOS program typically needs to say:

> I require `data.table` semantics version family 1.

It should not need to pin the current patch release of the contract registry merely to remain executable.

Exact interpretation remains reproducible because the validation result also records the immutable registry snapshot identity.

Therefore exact validated meaning is attributable through:

```text
semantic_program_hash
+ registry_snapshot_id
+ IR version/hash profile
```

## Registry snapshot uniqueness rule

A v0.1 semantic registry snapshot MUST contain **at most one active contract version for each `(semantic ID, major version)` pair**.

Example valid snapshot selection:

```text
table.import / major 1 -> contract version 1.1
```

Example invalid/ambiguous snapshot:

```text
table.import 1.0
table.import 1.1
```

both active under the same v0.1 snapshot for major 1.

The registry builder must choose one contract version per major when creating the snapshot rather than making the validator select "highest" dynamically.

This keeps validation deterministic and prevents semver-resolution logic from changing beneath old snapshots.

## Resolution algorithm

Given IR reference:

```text
table.import@1
```

1. parse semantic ID `table.import` and major `1`;
2. look up the immutable snapshot index `(table.import, 1)`;
3. require exactly one matching active contract reference;
4. load/verify the referenced contract content hash;
5. require contract's declared full version major equals `1`;
6. validate program/node against that contract;
7. record registry snapshot identity in validation result.

No network/catalog lookup occurs during semantic validation.

## Semantic hash behavior

The authoring major selector is semantic and remains in the normalized semantic-hash view.

Therefore:

```text
table.import@1 != table.import@2
```

and the hash changes across a major-version change.

The selected registry contract's minor/patch version is **not substituted into the AIOS IR semantic hash**.

Instead it is bound through `registry_snapshot_id`.

This preserves two useful identities:

```text
semantic program hash = requested semantic major families + executable graph
registry snapshot      = exact contract versions/content used to validate that request
```

A cached/compiled result that requires exact contract interpretation must bind/check both identities (or a stronger derived compilation key), not semantic hash alone.

## Contract version rules

Semantic contract record `version` uses:

```text
MAJOR.MINOR
MAJOR.MINOR.PATCH
```

### Major

Incompatible semantic change.

Requires a new IR reference family such as `@2`.

### Minor

Backward-compatible semantic extension/clarification under the published compatibility rules.

A new Registry Snapshot can select the new minor for the same major.

### Patch

Compatible correction/clarification that does not intentionally change valid semantic meaning.

The exact contract bytes/content hash still change and are attributable in the snapshot.

## Pre-1.0 / major 0

Major `0` is allowed for experimental semantic families.

Because pre-1.0 compatibility is inherently less stable, registry/governance MAY treat every minor transition in major 0 more conservatively.

The v0.1 resolver itself still indexes `(id, 0)` exactly like other majors.

## Capability contract port types

Semantic type references inside capability-contract input/output ports use the same v0.1 major-reference syntax:

```text
data.table@1
```

A capability contract full version can evolve within its major while continuing to consume the same type major family.

## Provider declarations

Provider manifests/registrations may additionally pin the exact semantic contract content hash/full version they were tested against.

Provider conformance is evaluated against the contract version selected by the active registry snapshot or an explicitly compatible conformance policy.

A provider claiming `table.import@1` does not get to choose a different private definition of major 1.

## Fallbacks

Fallback capability refs use the same major selector grammar.

The validator resolves each fallback through the same immutable snapshot before checking input/output/effect compatibility.

## Skills / compiled targets

A Skill/compiled target must retain enough source-validation information to know which exact registry semantics it was validated/compiled against.

At minimum the source evidence includes:

```text
semantic program hash
registry snapshot ID
IR version/hash profile
compiler/Skill version as applicable
```

Reusing against a later snapshot requires explicit compatibility/revalidation rules; it is not inferred from matching major selector alone.

## Unknown/unversioned references

These fail closed:

```text
table.import
data.table
```

The validator does not silently append `@1`, select latest, or query a package registry.

Reason-code families should distinguish malformed/unsupported version syntax from a syntactically valid reference whose `(id, major)` is absent from the registry.

## No dependency on generic package SemVer solver

Semantic contract resolution is intentionally simpler than package dependency resolution.

Do not use a package-manager "highest compatible version" algorithm inside semantic IR validation.

Snapshot construction/governance resolves the active contract versions in advance; validation is a deterministic lookup.

## Future extension

A future IR major version could add explicit exact-version or version-range selectors if real workloads justify them.

That would require an ADR/schema/hash-profile update and test vectors.

Do not add ad-hoc range syntax to v0.1 references.

## Required validator tests

1. `table.import@1` resolves exactly one `table.import` contract whose full version major is 1.
2. unknown `(id, major)` fails closed.
3. unversioned reference is schema-invalid.
4. `@1.0` is schema-invalid in v0.1 IR.
5. duplicate snapshot contracts for same `(id, major)` make registry invalid.
6. contract full version whose major disagrees with snapshot/index ref fails registry validation.
7. same IR + same snapshot is deterministic.
8. same IR + compatible later snapshot retains semantic program hash but validation result records the new snapshot.
9. changing `@1` to `@2` changes semantic hash.
10. validator never fetches a missing contract from network/catalog.

## Principle

> **IR names the semantic compatibility family; the immutable registry snapshot pins the exact contract that gave that family meaning for one validation.**
