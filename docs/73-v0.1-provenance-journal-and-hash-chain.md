# 73 — v0.1 Provenance Journal and Tamper-Evident Hash Chain

## Purpose

AIOS provenance is not a debug log. It is the durable explanation of what a Task materially did, under which semantic program/provider/authority, with which inputs/outputs and external transfers.

The v0.1 implementation needs a small local journal that is:

- append-oriented;
- transaction-friendly with Task state changes;
- deterministically ordered;
- tamper-evident under normal integrity checking;
- privacy-aware;
- usable without AI/cloud;
- extensible to later signed/distributed checkpoints.

## Security claim

The v0.1 local hash chain is **tamper-evident**, not tamper-proof.

A privileged attacker able to rewrite the entire local database and every trusted checkpoint can construct a different chain.

Later stages may add TPM/key-backed signatures, remote transparency checkpoints, organizational audit sinks, or append-only storage.

Do not market a local hash chain as immutable proof against a fully compromised administrator.

## Stream model

v0.1 uses one primary provenance stream per AIOS Task. `task:<task-stream-key>`
means an opaque, deterministic key derived from the validated Task ID, rather
than the literal Task ID:

```text
task_stream_key = "v1:sha256:" + lowercase_hex(
  SHA-256("AIOS-TASK-PROVENANCE-STREAM-ID\0v1\0" || task_id UTF-8)
)
stream_id = task:<task_stream_key>
```

The opaque form keeps stream identifiers bounded and preserves the chain
identity already committed by the Stage-1 Task Manager. It is stable for a
given Task ID, carries no authority, and is not a privacy substitute for the
event payload's typed `task_id`. Changing this derivation requires a new stream
identity/profile; existing records are never rewritten or rehashed merely to
adopt a different display form.

Each event has a monotonically increasing integer `sequence` beginning at 1.

This gives deterministic local ordering without relying on timestamp ordering.

System-wide non-Task events can gain separate streams later.

## Event identity

Each event has:

```text
event_id     stable unique event identifier
stream_id    task provenance stream
sequence     monotonic within stream
event_hash   canonical hash-chain identity
```

`event_id` is useful before/independent of hashing and as a database reference.

`event_hash` establishes ordered content integrity.

Neither one is a capability grant.

## Append rule

For sequence `N`:

```text
previous_event_hash = hash(event N-1)
```

For genesis:

```text
sequence = 1
previous_event_hash = null
```

The journal rejects:

- duplicate `(stream_id, sequence)`;
- append with stale/wrong previous head;
- update/delete through normal API;
- sequence gaps unless an explicit import/recovery protocol says otherwise.

## Canonical event hash

The event hash includes the complete provenance record that is meant to be integrity-protected, excluding only the `event_hash` field itself and future detached signatures/checkpoint records.
`event_hash` and `previous_event_hash` are journal-envelope fields, not event
payload fields. The event payload schema forbids them; the canonical hash view
adds the preceding hash once from the journal envelope. This avoids accepting
an event property that looks typed but is removed from the hash preimage.

Included examples:

```text
schema version
event_id
stream_id
sequence
task_id
semantic program hash/node when present
event type
timestamp
actor
provider/component/model identifiers
capability
authority/policy/approval refs
input/output artifact refs
execution binding/attempt refs
external-transfer record
status
previous_event_hash
bounded structured details
```

Canonicalization:

1. validate typed provenance event record;
2. construct canonical hash view excluding `event_hash`/detached signatures;
3. serialize with RFC 8785 JCS semantics;
4. hash with domain-separated SHA-256.

Conceptual prefix:

```text
AIOS-PROVENANCE-EVENT\0v0.1\0<JCS bytes>
```

Stored form:

```text
sha256:<lowercase hex>
```

The exact byte prefix/test vectors are centralized in the implementation.

## Timestamp semantics

Timestamp is part of the event hash but **not** the sole ordering source.

Rules:

- trusted control-plane code assigns/normalizes event timestamp;
- model/provider prose cannot choose authoritative timestamps merely by returning a string;
- Task stream sequence establishes order;
- wall-clock anomalies are possible and should be represented rather than rewriting history.

Later distributed provenance may need monotonic/logical clocks.

## Atomicity with Task transitions

A material Task-state transition and its provenance event should be committed in one SQLite transaction when both live in the same local state database.

Conceptually:

```text
BEGIN IMMEDIATE
  check expected Task revision
  validate state transition
  allocate/verify next provenance sequence/head
  insert provenance event
  update Task state + revision + event reference
COMMIT
```

This prevents:

```text
Task says COMPLETED
but no completion provenance exists
```

or:

```text
provenance says COMPLETED
but Task record remained RUNNING
```

The provenance append API SHOULD therefore support caller-owned database transactions rather than requiring a separate daemon/RPC round trip for every local state transition.

## Transaction ownership

Suggested v0.1 library boundary:

```text
aios-provenance
  append_in_tx(tx, event_without_hash)
  verify_stream(tx/read_conn, stream_id)
  get_head(stream_id)
  list_events(stream_id, cursor/limit)
```

The control-plane state owner coordinates the SQLite transaction.

This is a library/service boundary decision, not permission for arbitrary code to mutate provenance tables.

## Event immutability

After append, normal APIs do not edit event content.

If a prior fact needs correction, append a new event that references/corrects the prior event.

Example:

```text
operation outcome initially UNKNOWN
later reconciled as COMPLETED
```

Do not rewrite the original uncertainty out of history.

## Material event threshold

Do not emit provenance for every internal function call.

Events should capture facts users/security/recovery/debugging need, including:

- Task creation/state transitions;
- semantic plan/IR validation/revision;
- provider/resource placement decisions;
- authorization/approval decisions;
- execution attempts/start/completion/failure;
- model invocation/provider attribution;
- external egress/transfers;
- Artifact import/create/verify/integrity failure;
- irreversible/compensating external effects;
- verification start/result;
- recovery/reconciliation/rollback;
- Skill proposal/creation/execution;
- component/provider version/security-relevant activation when it materially affects execution.

Every material Task state transition uses the generic `task.transitioned` event
type. Its required typed `task_transition` object records the transition ID,
previous/new state, previous/new revision, and structured reason code. These
security- and recovery-relevant identities are not hidden in free-form details.

High-volume tracing belongs in a separate observability/telemetry subsystem.

## Privacy rule

Provenance should record **what happened without unnecessarily copying the user's private content into the audit log**.

Prefer:

```text
Artifact/Object IDs + hashes
provider/model IDs
capability IDs
semantic program/node IDs
transfer byte counts/destination classes
policy/grant/approval references
structured reason/status codes
```

over:

```text
full document contents
full prompts/responses
raw credentials
auth headers
private message bodies
secret values
arbitrary provider debug dumps
```

`details` is a closed, event-specific, privacy-safe vocabulary rather than a
free-form diagnostic map. v0.1 accepts only the established Task and Artifact
projection fields named by `provenance-event.schema.json`. The machine schema
declares which detail keys each event type may carry; implementations also
reject unknown keys in nested objects. Aggregate serialized-byte limits and
cross-field rules such as consecutive Task revisions remain trusted runtime
checks because JSON Schema cannot express them directly. Every accepted field
has a path-specific
value contract: bounded integers and collections, booleans, fixed enums,
RFC 3339 timestamps, lowercase `sha256:<64 hex>` digests, or bounded identifiers.
Stream IDs and reason codes use their dedicated grammars; schema fields typed
as `safeIdentifier` use the non-whitespace rule below. Opaque values
copied from accepted Task fields preserve that field's existing Unicode-scalar
contract instead: `principal.id` and `workspace_id` are nonempty and at most 256
scalars, step IDs are nonempty and at most 128 scalars, waiting IDs and plan IDs
are nonempty and at most 256 scalars, and reason `related_ids` are at most 512
scalars. Those opaque values may contain spaces, punctuation, emoji, or
canonically distinct Unicode and MUST NOT be normalized before hashing. An
allowed field name therefore does not make an arbitrary scalar or unbounded
string exportable. Adding a field or widening its value contract requires an
explicit schema and validator change.
The `input_artifacts`, `output_artifacts`, and
`external_transfer.data_refs` collections each have a 512-item maximum in
both the schema and the validator. These bounds are compatible with the
projected-event size limit below, including when all three collections and
the 512-item Task step set occur together.
Append, local verification, and migration all apply the same rule, so
legacy rows with an unknown or ill-typed detail field fail validation and remain
unavailable to normal export.

The implementation also enforces size, collection, and nesting-depth limits:
at most 4,096 Unicode scalars per general string, 512 items per array, 256
fields per object, 256 scalars per object key, and 32 JSON nesting levels.
A source event is capped at 524,288 serialized JSON bytes, with its `details`
value capped at 458,752 serialized JSON bytes. This leaves room for the full
512-item Task step boundary when each step identifier contains 128 Unicode
scalars, including characters that expand when JSON-escaped. The event is
checked against these bounds before it is appended or accepted as a stored row.
Fields typed as `safeIdentifier` in the event schema accept any nonempty string
of at most 256 Unicode scalars without whitespace. Validation uses that same
contract for actions, resources, execution identifiers, and nested details.
Invalid verification-request metadata (stream ID, verification timestamp, or
checkpoint expectation) returns an API error before a verification-result
object is constructed. Malformed records produce bounded, schema-shaped
diagnostics; an invalid event ID is omitted from a diagnostic rather than
copied into it.

### Private creation-intent commitment

`task.created` MUST NOT copy `original_intent`, `normalized_intent`, or a
reversible encoding of either field into provenance. The Task Manager generates
a fresh 256-bit (32-byte) nonce from an operating-system CSPRNG for every Task.
The raw nonce remains private trusted-control-plane data and is never returned
by a public API. Raw intent remains Task-private content: an authorized Task
reader may retrieve it under the Task access policy, but provenance APIs,
diagnostics, logs, checkpoints, and exports never copy it.

The v1 field commitment is:

```text
SHA-256(
  "AIOS-TASK-CREATION-FIELD-COMMITMENT\0v1\0" ||
  u64be(len(nonce)) || nonce ||
  u64be(len(field-name UTF-8)) || field-name UTF-8 ||
  u64be(len(field-value bytes)) || field-value bytes
)
```

`original_intent` uses its exact validated UTF-8 bytes. A present
`normalized_intent` uses its RFC 8785 JCS bytes. The provenance value is a
versioned object, for example:

```json
{
  "kind": "task-field-commitment",
  "version": "v1",
  "algorithm": "sha256-keyed-prefix",
  "field": "original_intent",
  "commitment": "sha256:<64 lowercase hex characters>"
}
```

The secret per-Task nonce prevents an exported digest from becoming a practical
dictionary oracle for short or predictable intents. This commitment establishes
equality with the private Task field during trusted verification; it does not
make the intent public and is not an authority token.

Each commitment reference is an exact five-field object. `kind`, `version`, and
`algorithm` are fixed to `task-field-commitment`, `v1`, and
`sha256-keyed-prefix`; `commitment` is a lowercase SHA-256 digest. The `field`
discriminator must match its location (`original_intent`, `normalized_intent`,
`reason_message`, `waiting_message`, or `failure_summary`). The original-intent
reference is required and non-null. Optional source fields may use null only at
their specifically typed reference location.

Legacy handling is fail closed:

- historical hash-chained events are never rewritten merely to remove a raw
  legacy intent;
- a portable export of an explicitly migrated legacy Task uses
  `privacy-redacted-projection-v1`, retaining its established v1 commitment but
  no original stream or event hash; it does not claim that the redacted
  projection is the byte-for-byte original chain;
- raw legacy intent bytes, the nonce, private Task fields, and opaque identifiers
  are excluded from every portable export;
- a legacy Task without a valid 32-byte nonce and verifiable commitment is
  inspect-only and quarantined from scheduling/recovery mutation until an
  explicit migration verifies the trusted Task row against its original hashed
  creation record and establishes the v1 private commitment;
- an unmigrated/quarantined Task is unavailable to normal provenance export; an
  administrative quarantine report contains only bounded identifiers/reasons
  and never the legacy raw intent;
- any nonce-length error, commitment mismatch, malformed commitment profile, or
  disagreement between the private Task record and committed creation evidence
  quarantines the Task. The verifier never substitutes a plain unsalted digest
  or invents a successful match.

## Model provenance

For a model call, record enough to attribute/reconstruct the runtime decision without automatically storing complete private prompt text.

Candidate fields/refs:

```text
model provider identity
model/version/deployment descriptor
request schema/version
input Artifact/Object refs and sensitivity class
local/peer/remote placement
egress transfer reference when remote
structured-output result Artifact/hash when retained
token/latency/cost accounting if available
policy decision/grant refs
verification linkage
```

Exact prompts may be retained only under explicit Task/debug/retention policy.

## External transfer provenance

Material transfer records should identify:

```text
source semantic refs
destination service/trust identity
destination class
purpose
authority/policy decision
bytes/content IDs as appropriate
started/completed/failed/partial state
```

Network endpoint details can appear as runtime diagnostics but do not replace stable service identity.

## Execution/provider attribution

A material execution event SHOULD identify exact available versions/immutable IDs such as:

```text
semantic program hash
registry snapshot ID
node ID
Execution Binding ID
provider ID/version
provider package digest/build provenance
execution profile/sandbox reference
placement decision/device/service identity
attempt number
```

This lets a historical Task answer not just "what capability?" but "which implementation actually ran?"

## Artifact linkage

Provenance events reference Artifact IDs; final/create/verify events SHOULD include content hash/version evidence when available.

Artifact content remains outside provenance JSON.

A later Artifact GC/archive operation must preserve enough metadata to interpret historical provenance according to retention policy.

## Stream verification

`verify_stream` walks events in sequence and checks:

1. sequence starts/continues correctly;
2. each `previous_event_hash` matches prior computed hash;
3. each canonical event hash recomputes exactly;
4. final computed head matches stored stream head/checkpoint if one exists;
5. schema/version is supported.

It returns structured verification diagnostics, not a boolean only.

## Checkpoints

v0.1 MAY persist a stream-head table:

```text
stream_id
last_sequence
last_event_hash
updated_at
```

This improves append performance/recovery but is not independent tamper proof.

Later signed checkpoint record:

```text
stream_id
sequence
event_hash
signer trust identity
signature profile
signature
```

belongs outside the individual event hash.

## Recovery

On control-plane startup:

- verify stream heads needed for active/nonterminal Tasks;
- detect database/task revision/event-head mismatch;
- transition uncertain Tasks into recovery rather than guessing;
- append recovery/reconciliation events after the prior durable head;
- never rewrite failed/partial history to look clean.

A full database-wide chain scan need not block every boot if integrity checkpoints/targeted verification provide equivalent evidence; v0.1 can start conservatively.

## SQLite guidance

Suggested constraints/indexes:

```text
UNIQUE(stream_id, sequence)
UNIQUE(event_id)
UNIQUE(event_hash) where non-null/appropriate
INDEX(task_id, sequence)
INDEX(event_type, timestamp) for inspection
```

Append should use transactions that prevent two writers from allocating the same next sequence.

For v0.1 a single control-plane writer / serialized append path is preferable to distributed locking complexity.

## Export

Normal portable export is `privacy-redacted-projection-v1`: JSONL projected
records plus a projection manifest. Export first verifies the authoritative
original chain, then reads and projects the complete stream in one SQLite read
transaction. Journal bytes, stream IDs, event hashes, and Task rows are never
rewritten.

The portable bundle contains no original stream ID, original event/head hash,
or Task-derived bundle identity. Every non-fixed string channel, including
top-level event/Task/actor/step IDs and every nested plan, waiting, related,
artifact, provider, or mutation duplicate, becomes a typed bundle-local alias.
Aliases use a fresh secret 256-bit bundle key, a fixed namespace, and the exact
UTF-8 bytes; the key and alias mapping are not exported. Equal bytes in one
namespace receive equal aliases, while different namespaces or canonically
distinct Unicode receive different aliases. This is not an unsalted value hash.

Only closed reviewed enums, RFC 3339 timestamps, numbers, booleans, nulls, and
validated keyed private-field commitments remain literal. The projection record
chain and manifest descriptor use separate domain-separated hashes under
`aios-provenance-redacted-projection-v1`.

The exporter and offline verifier share the same closed path contract. Each
alias namespace must match its exact source path (including the distinct
`approval` namespace), and the reconstructed shape must satisfy the complete
event-type contract, required fields, nullability, nested objects, commitment
discriminators, and value bounds. A projected event is capped at 524,288 JSON
bytes, its record envelope adds at most 4,096 bytes, and one portable JSONL
bundle is capped at 8 MiB. The event cap accounts for simultaneous alias
expansion of the valid 512-item active-step, input-artifact, output-artifact,
and external-transfer-reference collections; generated records are checked before
they leave the database snapshot. Before private Task validation or chain
verification, export also rejects a snapshot with more than 10,000 records or
more than 32 MiB of original `event_json` UTF-8 bytes. The byte cap bounds
work on streams whose large source strings would shrink into aliases; such
streams remain available for local verification and bounded paging.

Offline verification has scope `exported-projection`. It verifies descriptor,
record order, completeness relative to the manifest, projected event shape, and
the projection hash chain. It always reports
`original_chain_verified_offline=false` and
`original_chain_linkage_proven=false`; the bundle contains no cryptographic
proof linking it to the locally verified original journal. Unsupported fields,
profiles, raw projected strings, malformed aliases, splice attempts, and
descriptor/record tampering fail closed.

An export is a copy, not the authoritative mutable journal.

## Retention

Retention is policy-dependent.

Potential classes later:

```text
ephemeral-debug
standard-task
security-audit
organization-retained
legal/compliance
```

Never silently delete provenance required to explain a still-retained Task/Artifact/irreversible external effect.

## Failure modes

The provenance subsystem itself can fail.

For operations requiring durable provenance before effect:

- inability to append the prerequisite event MUST block the effect;
- do not perform an irreversible action and hope the audit write succeeds later.

For non-consequential observability-only events, a bounded degraded policy may differ, but core material provenance is part of correctness.

## v0.1 acceptance tests

At minimum:

1. genesis event sequence/hash validates;
2. 100-event chain validates;
3. changed historical event field breaks verification;
4. changed previous hash breaks verification;
5. deleted/missing middle event breaks sequence/chain;
6. reordering events breaks verification;
7. concurrent append attempts cannot allocate same sequence;
8. stale Task revision transaction writes neither Task transition nor provenance;
9. successful Task transition writes both atomically;
10. failed transaction writes neither;
11. event correction uses new event rather than update;
12. provenance projection export re-verifies its projection offline and does not claim original-chain verification or linkage;
13. event size/diagnostic bounds enforced;
14. secret fixture strings are rejected/redacted according to future schema policy rather than intentionally persisted by normal test APIs;
15. no model/network/provider invocation is required to verify a local stream;
16. two Tasks with the same intent receive different v1 commitments because their CSPRNG nonces differ;
17. provenance and normal exports contain the versioned commitment but contain neither raw intent nor nonce;
18. a malformed/missing nonce or mismatched creation commitment quarantines the legacy Task;
19. every legacy and current portable export is labeled as a redacted projection and contains no original stream/event hashes.

## Relationship to system logging

Provenance ≠ system logs.

```text
provenance   durable material Task facts/audit/recovery
logs         developer/operator diagnostics
metrics      aggregated performance/health
traces       detailed execution timing/path
```

These can reference common Task/Binding IDs but have different privacy/retention/integrity semantics.

## Principle

> **Provenance is part of Task state correctness: append material facts before claiming or performing the state/effect they justify.**
