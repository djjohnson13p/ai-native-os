# 35 — v0.1 Durable Persistence Model

## Purpose

The control plane must survive process restarts without reconstructing task truth from model memory, UI state, provider processes, or filesystem guesses.

For v0.1, use a small transactional local database—**SQLite is the proposed default**—for control-plane state and keep large artifact bytes/model data outside the database behind handles.

The persistence model must preserve the architecture separations already defined:

```text
Task identity
  ≠ Planner proposal
  ≠ Validated semantic program
  ≠ Execution binding
  ≠ Provider process
  ≠ Artifact bytes
```

## Goals

The database must support:

- durable task identity and revisioned state;
- original/normalized intent;
- planner proposal history;
- validated AIOS IR program revisions;
- IR validation results and registry snapshot identity;
- execution binding/attempt recovery;
- artifact identity/lineage;
- policy/approval/grant references;
- append-oriented provenance;
- installed/local Skill metadata;
- restart reconciliation;
- transactional state transitions.

## Non-goals

The control database is not:

- a vector database for all user memory;
- an artifact-content blob store;
- a model-weight store;
- a secret vault;
- a replacement for portable user files;
- a distributed consensus system in v0.1.

## Proposed SQLite baseline

Suggested connection initialization:

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA busy_timeout = 5000;
```

These are prototype defaults, not immutable requirements.

Rationale:

- SQLite gives atomic transactions and crash recovery without a server dependency;
- WAL supports concurrent readers with serialized writes;
- `foreign_keys=ON` makes relationships explicit;
- `synchronous=FULL` favors control-plane durability while the project is correctness-first.

Benchmarks may justify a different durability setting later, but state transitions involving external side effects should remain conservative.

## Logical tables

`specs/persistence-v0.1.sql` is an executable-style schema draft. This document defines the semantics rather than locking every SQL detail.

### `schema_migrations`

Tracks ordered migration identity/checksum and application time.

Never infer schema version from application binary version alone.

### `tasks`

One row per stable task.

Key fields:

```text
task_id PK
revision
state
principal_kind
principal_id
workspace_id
original_intent
normalized_intent_json
active_program_revision
created_at
updated_at
completed_at
```

`revision` is optimistic-concurrency state and increments on material task updates.

### `task_artifacts`

Many-to-many task/artifact role relation.

Roles:

```text
input
output
intermediate
checkpoint
```

An Artifact can be referenced by more than one task under policy without duplicating bytes.

### `plan_revisions`

Preserves planner-facing proposals independently of executable semantic identity.

Key fields:

```text
task_id
plan_revision
plan_id
planner_kind/provider
plan_json
created_at
superseded_at
```

Raw model output may be retained only according to privacy/diagnostic policy; the normalized proposal is the important control-plane record.

### `semantic_program_revisions`

One row per material validated/candidate AIOS IR program revision associated with a task.

Key fields:

```text
task_id
program_revision
program_id
ir_version
semantic_hash
registry_snapshot_id
validation_result_id
program_json or durable content ref
status
created_from_plan_revision
created_at
superseded_at
```

Suggested status values:

```text
candidate
validated
active
superseded
rejected
```

Only a successfully validated program can become `active`/runnable.

### `validation_results`

Persists the deterministic output of the trusted IR validator.

Key fields:

```text
validation_result_id
program hash/identity
valid
registry snapshot
validator ID/version/build
result_json
timestamp
```

Invalid results intentionally have no executable semantic hash under the validation-result contract.

### `registry_snapshots`

Locally retains the semantic registry snapshot metadata required to understand persisted programs/Skills.

The canonical contract content may be stored in a separate content-addressed registry directory with the DB retaining identity/path/hash metadata.

### `execution_bindings`

Attempt-specific realization of one semantic node.

Key fields:

```text
binding_id
task_id
semantic_hash
node_id
attempt
provider_id/provider_version
policy_decision_id
execution_profile_ref
placement_json
binding_json
state
created_at
started_at
finished_at
```

This table answers what concrete implementation attempted a semantic operation.

A retry/provider switch creates a new binding/attempt rather than mutating history in place.

### `operations`

Stable side-effect/idempotency identity used across retries/recovery.

Example:

```text
operation:T91:send_report:v1
```

Key facts:

- task/program/node;
- binding/attempt;
- effect class;
- idempotency key;
- status (`prepared`, `started`, `succeeded`, `failed`, `unknown`);
- external receipt/reference where applicable.

An `unknown` external outcome must not be automatically converted to `failed` and retried when duplication could cause harm.

### `artifacts`

Artifact metadata/handle, not the large bytes themselves.

Key fields:

```text
artifact_id
uri
semantic_type
media_type
content hash
size
sensitivity
retention
origin task/node/provider
storage ref
created_at
```

Artifact bytes live in a controlled content/output store.

### `artifact_lineage`

Directed derivation edges:

```text
parent_artifact_id
child_artifact_id
task_id
node_id
relationship
```

Possible relationships:

```text
consumed-by
transformed-to
verified-as
exported-as
```

### `policy_decisions`

Stores deterministic authorization decision metadata/JSON and links it to task/program/node/provider context.

Do not treat a previous `allow` row as a new authorization decision for later tasks.

### `approvals`

Human approval workflow records:

```text
approval_id
task_id
request scope
impact level
state
actor
requested_at
resolved_at
```

The approval is evidence contributing to a specific grant/policy decision, not a universal permission flag.

### `grant_records`

Stores metadata needed to audit/recover task-scoped authority.

Long-lived/raw bearer secret material should not be stored unprotected in ordinary SQLite fields.

If token material must persist across restart, store it through a platform secret/key service or encrypted authenticated record, with the DB storing a reference and non-secret metadata.

### `provenance_events`

Append-oriented task event stream.

Columns should expose common indexes while retaining canonical event JSON:

```text
event_id
task_id
sequence
timestamp
event_type
semantic_hash
node_id
execution_binding_id
provider_id
status
previous_event_hash
event_hash
event_json
```

No normal UPDATE/DELETE path should rewrite historical event meaning.

Retention/redaction policy needs a deliberate later design rather than unrestricted SQL mutation.

### `skills`

Installed/local Skill metadata:

```text
skill_id
version
status
manifest_hash
source_semantic_hash
manifest_json
privacy_scope
last_validated_at
created_at
updated_at
```

Compiled target bytes remain outside SQLite; the manifest references their content hashes/locations.

## Transaction boundaries

### Task state transition

One transaction should:

1. compare expected task revision;
2. validate allowed state transition;
3. update task row and increment revision;
4. add/update structured waiting/failure metadata as needed;
5. append/link corresponding provenance event;
6. commit.

Do not update UI-visible state in one transaction and provenance in an unrelated best-effort write.

### Activate semantic program

One transaction should:

1. confirm successful validation result;
2. confirm program hash/registry snapshot match;
3. mark prior program revision superseded if applicable;
4. mark selected revision active;
5. update task `active_program_revision`;
6. append provenance event;
7. commit.

Authorization remains separate; valid program does not imply runnable authority.

### Create execution binding

Before launching a provider:

1. create immutable attempt-specific binding;
2. associate current policy decision/grant references;
3. create `prepared` operation record for external side effects where needed;
4. persist `execution.bound` provenance;
5. commit;
6. only then launch/hand authority to provider.

This improves restart reconstruction if the daemon dies immediately after launching.

### Artifact publication

For file-like outputs, prefer a two-phase pattern:

1. provider writes to task-scoped temporary allocation;
2. close/sync as required;
3. verifier/hash step validates output;
4. atomically rename/commit into artifact store where filesystem supports it;
5. transaction creates Artifact Handle + lineage + provenance;
6. expose final artifact to task/UI.

Do not mark an artifact final merely because a path exists.

## External side effects and the database

SQLite cannot make a remote email/API/legacy application action atomically commit with the local DB.

Use an outbox/idempotency-style discipline:

```text
DB: persist prepared operation + idempotency identity
      ↓ commit
invoke external provider
      ↓
DB: persist observed outcome/receipt
```

On crash, `prepared/started/unknown` operations are reconciled rather than blindly retried.

Providers that support idempotency keys should receive the stable operation identity.

Exactly-once external effects cannot be assumed universally.

## Provenance hash chain

The schema has `previous_event_hash`/`event_hash` fields, but cryptographic chain semantics are still an open architecture question.

Until an ADR defines canonical event hashing/signing:

- preserve immutable sequence ordering;
- do not make security claims about tamper evidence;
- keep fields available for the future chain;
- tests should distinguish append-only application behavior from cryptographically tamper-proof storage.

## Sensitive data

Control-plane persistence should minimize secrets/private content.

Prefer storing:

- artifact handles instead of content;
- secret handles instead of secrets;
- structured intent where possible;
- redacted diagnostics where detailed prompts/provider logs are unnecessary.

Raw model prompts/responses may contain private artifact content and should have a separate configurable retention policy rather than being automatically stuffed into provenance.

## File permissions / database location

v0.1 should place the database in a user-scoped protected state directory by default and use least-privilege ownership/mode.

System-wide/multi-user deployment requires a separate principal/isolation design; do not make one user database globally readable.

## Database corruption / backup

The recovery plan should include:

- integrity check on detected abnormal corruption;
- periodic backup/checkpoint strategy for meaningful test deployments;
- known behavior when DB is unusable;
- never asking an AI model to reconstruct authoritative task/grant state from prose logs.

Artifact bytes without metadata can be quarantined/scanned for recovery; they should not automatically become trusted task outputs.

## Migrations

Use ordered transactional migrations with checksums.

Rules:

1. database schema version is explicit;
2. migration runs before new code writes new semantics;
3. failed migration rolls back when SQLite transaction support permits;
4. backup/export strategy exists before risky destructive migrations;
5. avoid editing historical applied migrations after release;
6. prefer expand/migrate/contract for compatibility across rolling development;
7. system rollback and database rollback compatibility must be part of image update testing.

## Concurrency

v0.1 can use a single logical writer/transaction coordinator in `aiosd` even if multiple async tasks/providers are active.

Providers should not open the control DB directly.

They interact through typed control-plane interfaces and artifact allocations.

This preserves one deterministic owner for task/authority/provenance state.

## Retention

Different records have different lifetimes:

- Task/provenance: user/policy-defined history;
- ephemeral intermediate artifacts: task retention;
- final artifacts: user-managed/exported;
- validation/registry data: retain while referenced by tasks/Skills/provenance;
- execution diagnostics: shorter configurable retention may be appropriate;
- grants/tokens: expire quickly but retain non-secret audit metadata as policy permits.

Do not implement one global `delete everything older than N days` rule for all classes.

## v0.1 recovery tests

Persistence implementation should pass at least:

1. create task -> kill daemon -> task remains `CREATED` with identical intent;
2. activate validated program -> restart -> semantic hash/registry snapshot remain intact;
3. kill daemon after execution binding commit but before provider launch -> recovery recognizes prepared attempt;
4. kill daemon during provider execution -> task enters `RECOVERING` and reconciles attempt;
5. create output bytes but crash before Artifact Handle commit -> bytes are quarantined/not published as final;
6. stale task revision update is rejected;
7. foreign-key violation fails rather than creating dangling lineage;
8. old expired grant metadata remains auditable but cannot authorize execution;
9. provenance sequence remains monotonic per task under concurrent event attempts;
10. failed migration leaves the previous database usable or explicitly restores backup.

## Architectural principle

> **Persist facts that let deterministic services recover reality; do not persist AI guesses as authoritative state.**
