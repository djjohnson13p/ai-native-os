# 69 — v0.1 Capability Effect and Authority Contract Profile

## Purpose

A semantic capability contract must answer two different questions:

1. **What effects/authority are inherent to this semantic operation?**
2. **What optional effects/authority may some valid execution mode/provider require without changing the capability family?**

An `allowed_*` list alone cannot detect a planner that omits authority the capability always needs.

This document defines the v0.1 lower-bound/upper-bound model used by the IR validator.

## Contract fields

Each Semantic Capability Contract carries:

```text
required_effect_classes
allowed_effect_classes
required_authority_classes
allowed_authority_classes
allowed_egress_modes
allowed_execution_classes
```

### Required = semantic lower bound

`required_*` identifies effects/authority inherent to every valid invocation of that semantic capability.

Examples:

```text
artifact.copy@1
  required effects: ARTIFACT_READ, ARTIFACT_WRITE
  required authority: artifact.read, artifact.write

chart.render@1
  required effects: ARTIFACT_WRITE
  required authority: artifact.write
```

### Allowed = semantic upper bound

`allowed_*` is the maximum effect/authority envelope that a conforming invocation/provider may require for that capability family.

Example:

```text
report.summarize@1
  required effects: []
  allowed effects: PURE, NETWORK, DATA_EGRESS
  required authority: []
  allowed authority: network.connect, data.egress
  allowed egress: deny, policy
```

A local model can execute with no external effect; a remote provider can be eligible only when the IR/policy explicitly allows the additional network/egress envelope.

## PURE semantics

`PURE` is the canonical derived effect summary when a node has no externally relevant effects.

Rules:

- `PURE` is mutually exclusive with non-PURE effects in a **derived node/program effect set**;
- a capability that is semantically always pure declares:

```text
required_effect_classes: [PURE]
allowed_effect_classes: [PURE]
```

- a capability that can be either local-pure or externally effectful declares `required_effect_classes: []` and includes `PURE` plus optional non-PURE classes in `allowed_effect_classes`;
- if `required_effect_classes` contains `PURE`, `allowed_effect_classes` MUST NOT contain a non-PURE class.

## Contract consistency rules

A Semantic Capability Contract is invalid if:

1. any `required_effect_class` is absent from `allowed_effect_classes`;
2. any `required_authority_class` is absent from `allowed_authority_classes`;
3. `PURE` appears in required effects alongside another effect;
4. `PURE` is required while any non-PURE effect is allowed;
5. an effect/authority combination contradicts the capability's egress/execution semantics under the published contract rules.

Registry validation, not the AI planner, enforces these contract-level invariants.

Suggested registry reason codes:

```text
REGISTRY_REQUIRED_EFFECT_NOT_ALLOWED
REGISTRY_REQUIRED_AUTHORITY_NOT_ALLOWED
REGISTRY_PURE_EFFECT_CONTRADICTION
```

## IR invocation rules

For a node invoking a semantic capability, the IR validator:

1. resolves the exact capability contract through the immutable Registry Snapshot;
2. verifies node `execution_class` is allowed;
3. verifies node `egress.mode` is allowed;
4. verifies every required authority class appears in the node's semantic authority requests;
5. verifies no requested authority class exceeds the allowed authority set;
6. derives actual semantic effects from:
   - required capability effects;
   - requested authority classes under the effect mapping;
   - egress declarations;
   - operation/contract-specific rules;
7. verifies the derived effect set is within `allowed_effect_classes`;
8. normalizes `PURE` only when no non-PURE effect remains.

Missing required authority:

```text
IR_REQUIRED_AUTHORITY_MISSING
```

Requested authority outside allowed set:

```text
IR_AUTHORITY_CLASS_NOT_ALLOWED
```

Derived effect outside allowed set:

```text
IR_EFFECT_CLASS_NOT_ALLOWED
```

## Authority class to effect mapping

v0.1 registry/trusted validator maintains an explicit mapping for core authority classes used by the bootstrap contracts.

Minimum mappings:

```text
artifact.read      -> ARTIFACT_READ
artifact.write     -> ARTIFACT_WRITE
network.connect    -> NETWORK
data.egress        -> DATA_EGRESS
secret.use         -> SECRET_ACCESS
state.write        -> PERSISTENT_STATE
device.use         -> DEVICE_ACCESS
system.change      -> SYSTEM_CHANGE
external.send      -> EXTERNAL_MESSAGE
```

This mapping is semantic infrastructure, not inferred from string prefixes at runtime.

Domain Packs may add authority classes/effect mappings through versioned registry contracts later. The v0.1 validator fails closed if it needs to reason about an unknown authority/effect mapping not defined by the loaded trusted registry profile.

## Data-flow input access

Passing a value/artifact along a declared graph input does **not** grant ambient access to its backing host storage.

For external/persistent resources requiring read authority, the capability contract's required authority/effect lower bound and the node's authority request make the access explicit.

The Execution Binding later supplies only the concrete handles authorized for that node.

Task-local in-memory/value transport that does not cross a protected resource boundary may not require a separate Artifact-read authority if the semantic type/capability contract defines it as pure value flow.

This distinction is why effect/authority semantics belong to capability contracts rather than being inferred solely from whether a port's type contains the word `artifact`.

## Provider conformance

A provider implementation may operate within the semantic envelope but cannot silently broaden it.

A provider whose actual implementation requires:

```text
network.connect
```

for a capability contract allowing only:

```text
PURE
```

is non-conforming even if the provider would otherwise produce correct output.

For a capability allowing optional remote execution, the provider registration may declare that it requires the optional allowed authority/effects. The Resource/Policy Broker then considers that provider only when the node's semantic envelope/current policy allows them.

## Egress

`DATA_EGRESS` is not implied merely by the fact that a capability contract allows `NETWORK`.

The node's egress declaration plus matching `data.egress` authority request determines that Task data may leave the relevant trust boundary, subject to deterministic policy.

`docs/68-aios-ir-v0.1-edge-case-semantics.md` defines the exact v0.1 egress authoring rules.

## Fallbacks

Fallback contract checking uses both lower and upper bounds.

A fallback is invalid if its required effects/authority exceed the node's existing semantic authority/effect envelope.

Allowed optional effects on the fallback are treated conservatively according to `docs/68`: the v0.1 semantic validator should reject a fallback whose contract cannot be proven to fit the existing node envelope without runtime authority broadening.

## Effect summary derivation

For a valid node:

```text
required effects
+ effects implied by declared authority/egress
+ contract/operation rules
= derived non-PURE effects
```

If this set is empty:

```text
derived effect = PURE
```

The whole-program summary is the union of node non-PURE effects; if every node is pure, whole-program effect is `PURE`.

The summary is an upper bound for validated semantics, not a permission grant.

## Examples

### Pure deterministic transform

```text
table.normalize@1
required effects: PURE
allowed effects: PURE
required authority: none
allowed authority: none
```

### Required Artifact read

```text
artifact.hash@1
required effects: ARTIFACT_READ
allowed effects: ARTIFACT_READ
required authority: artifact.read
allowed authority: artifact.read
```

### Local-or-remote reasoning

```text
report.summarize@1
required effects: none
allowed effects: PURE, NETWORK, DATA_EGRESS
required authority: none
allowed authority: network.connect, data.egress
allowed egress: deny, policy
```

A local node with `egress=deny`, no network/egress authority derives `PURE`.

A remote-eligible node with matching network/data-egress authority derives `NETWORK + DATA_EGRESS`, subject to policy/provider placement.

## Required tests

1. required effect missing from allowed effect -> registry invalid;
2. required authority missing from allowed authority -> registry invalid;
3. required PURE plus non-PURE allowed -> registry invalid;
4. node omits required authority -> IR invalid;
5. node requests undeclared authority -> IR invalid;
6. derived effect exceeds allowed effects -> IR invalid;
7. local `report.summarize` path derives PURE;
8. explicit policy/remote summarize path derives NETWORK + DATA_EGRESS;
9. provider implementation requiring broader effects fails conformance;
10. fallback cannot use a capability with broader required effect/authority.

## Principle

> **Capability contracts declare both the minimum semantic effects an operation cannot avoid and the maximum envelope a valid implementation may ever require.**
