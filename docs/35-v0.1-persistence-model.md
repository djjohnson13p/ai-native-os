# 35 — v0.1 Durable Persistence Model

## Purpose

The control plane must survive process restarts without reconstructing Task truth from model memory, UI state, provider processes, filesystem guesses, or prose logs.

For v0.1, use a small transactional local database—**SQLite is the proposed default**—for authoritative control-plane metadata and keep large Artifact bytes, model weights, and raw credentials outside the database behind typed/opaque references.

The persistence model preserves these separations:

```text
Task identity
  ≠ planner proposal
  ≠ validated semantic program
  ≠ semantic registry snapshot
  ≠ provider registration
  ≠ Execution Binding / attempt
  ≠ policy decision / Authority Grant
  ≠ provider process
  ≠ Artifact bytes
  ≠ credential secret material
```

`specs/persistence-v0.1.sql` is the executable-style draft associated with this document.

## SQLite baseline

Prototype initialization:

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA busy_timeout = 5000;
```

Correctness/recovery clarity outranks maximum throughput during the trusted-core stage.

## Authoritative ownership

The local control-plane daemon/runtime owns database writes.

Providers, models, legacy applications, and untrusted components do **not** open the control database directly. They use typed broker/service interfaces.

## Durable record families

### Task / program

```text
tasks
task_transitions
plan_revisions
semantic_program_revisions
validation_results
registry_snapshots
```

`tasks.revision` is the optimistic-concurrency/CAS revision.

A Task transition uses a stable `transition_id` so response loss cannot cause a second transition/revision/provenance append when the caller retries.

A validated semantic program records both:

```text
semantic_program_hash
registry_snapshot_id
```

so historical meaning does not depend on today's mutable provider inventory.

### Semantic/provider registry

```text
registry_snapshots
provider_registrations
provider_conformance_evidence
```

The semantic Registry Snapshot defines meaning.

Provider registrations define which implementations currently claim/qualify to execute that meaning.

Adding/removing/upgrading a provider does not rewrite semantic history.

### Artifact substrate

```text
artifact_blobs
artifacts
artifact_output_allocations
artifact_publications
task_artifacts
artifact_lineage
```

Important distinction:

```text
blob bytes/content hash = physical immutable content
Artifact               = semantic/user-visible immutable content instance + lineage
output allocation       = bounded staging right for one Task/node/attempt
publication             = idempotent transition from staging to published Artifact
```

A blob that exists without committed Artifact publication is not automatically a Task output.

### Policy / approval / authority

```text
policy_snapshots
authority_requests
policy_decisions
approval_requests
approval_decisions
authority_grants
```

The authoritative runtime scope is stored in `authority_grants`.

`token_id` is an opaque runtime handle identity only; raw bearer/token material is not persisted in ordinary SQLite.

One policy `ALLOW` row is not reusable authority for another Task/provider/resource/binding.

### Credential mediation

```text
credential_handles
credential_use_records
```

`credential_handles` store non-secret metadata plus an opaque secure-store reference.

They do not store passwords, private-key bytes, refresh tokens, API keys, or reusable session cookies.

Credential use is separately tied to a current Authority Grant + provider/Execution Binding.

### Execution / attempts

```text
execution_bindings
step_executions
provider_invocations
operations
```

An **Execution Binding is immutable**.

It records exactly which provider/build, input/output refs, policy/grants, execution profile, placement, and attempt were intended for one node attempt.

Mutable attempt lifecycle belongs in `step_executions` / `provider_invocations`, not by rewriting the binding receipt.

A retry/provider switch creates a new attempt and binding.

`operations` carry stable side-effect/idempotency identity, especially for future external/opaque actions.

### Provenance

```text
provenance_events
provenance_checkpoints
```

The database exposes indexed fields while retaining the canonical typed event payload.

The v0.1 journal envelope is defined by `specs/provenance-journal-record.schema.json`:

```text
stream_id
sequence
previous_event_hash
event payload
event_hash
```

The hash-chain profile is defined in `docs/73-v0.1-provenance-journal-and-hash-chain.md`.

This is tamper-**evident** under the stated local threat model; it is not claimed tamper-proof against a privileged attacker who can rewrite all trusted storage and keys.

### Recovery

```text
recovery_epochs
recovery_assessments
```

Recovery stores deterministic evidence/classification rather than AI guesses.

Outcome certainty:

```text
NOT_STARTED
STARTED_NO_EFFECT
COMPLETED
FAILED_NO_EFFECT
FAILED_PARTIAL_EFFECT
OUTCOME_UNKNOWN
```

`OUTCOME_UNKNOWN` is never silently converted to retry permission.

### Skills

`skills` holds reusable Skill metadata and source semantic identity.

Compiled artifacts/large binaries remain outside SQLite behind content-addressed references.

## Core transaction boundaries

### Task state transition

One transaction should:

1. locate `transition_id` and return the prior result if already committed;
2. compare Task expected revision/state;
3. validate the deterministic state transition/guards;
4. update Task + increment revision;
5. append the corresponding provenance event/journal record;
6. store transition result;
7. commit.

Task state and its material provenance must not diverge because of best-effort writes.

### Activate semantic program

One transaction should:

1. confirm successful validator result;
2. confirm semantic hash + Registry Snapshot identity;
3. supersede prior active revision where applicable;
4. mark selected semantic revision active;
5. update Task active program revision;
6. append provenance;
7. commit.

Semantic validity still does not authorize execution.

### Create Execution Binding

Before provider launch:

1. ensure semantic node + exact registry contract are valid;
2. resolve exact provider registration/build;
3. resolve input refs/output allocations;
4. obtain current policy decisions/grants;
5. choose execution profile/placement;
6. persist immutable binding + attempt record;
7. append `execution.bound` provenance;
8. commit;
9. only then launch the provider.

If any material fact changes, create a new binding.

### Artifact publication

Filesystem/blob content and SQLite metadata are not one ACID transaction.

Use the protocol from docs 75/80:

```text
reserve allocation
→ provider writes staging
→ flush/close + validate
→ place/verify immutable blob
→ idempotent publication DB transaction
   (Artifact metadata + lineage + allocation/publication state + provenance)
→ expose published Artifact
```

Crash-created orphan bytes/blobs are reconciled; they are never promoted merely because they exist.

### Policy/grant issuance

One logical issuance path:

```text
authority request
→ deterministic policy decision
→ optional trusted approval
→ durable scoped Authority Grant
→ opaque token handle delivered out-of-band if needed
```

A grant-use/revocation/consumption update must be durable before a protected broker treats a one-shot use as available again.

### External side effect

SQLite cannot atomically commit with arbitrary external systems.

Use:

```text
persist operation/idempotency identity
→ commit local intent
→ invoke external provider
→ persist observed receipt/outcome
```

If the response is lost and completion/no-effect cannot be proven, persist `OUTCOME_UNKNOWN` and reconcile rather than blind retry.

## Immutability rules

Normal runtime must prevent:

- UPDATE/DELETE of historical provenance events;
- mutation of published Artifact content identity;
- mutation of an Execution Binding after its attempt begins;
- mutation of released semantic Registry Snapshot meaning;
- rewriting Task transition history to make recovery look clean.

Corrections append/derive new records.

## Secrets / private content

Prefer storing:

```text
Artifact handles instead of Artifact contents
credential handles instead of credentials
policy/grant metadata instead of bearer bytes
bounded/redacted diagnostics instead of full provider logs
structured provenance instead of raw prompts
```

Raw model prompts/responses can contain private Artifact content and require a separate configurable retention policy if retained at all.

## Concurrency

v0.1 can use one logical SQLite writer/transaction coordinator in `aiosd` while many reads/providers run concurrently.

Use:

- Task revision CAS;
- unique transition/publication IDs;
- unique `(task,node,attempt)` identities;
- serialized/transactional grant consumption;
- unique provenance sequence allocation per Task stream.

Do not resolve write races with last-writer-wins convenience.

## Durability / filesystem assumptions

`write()`/process exit does not equal power-loss durability.

Artifact implementation should explicitly test:

- staged write;
- file flush/fsync as required;
- atomic rename/content-store placement where supported;
- parent directory durability where required;
- DB commit before publication is reported to callers.

SQLite is configured conservatively during v0.1; implementation may measure and refine settings without weakening semantic commit rules.

## Corruption / maintenance

Ordinary crash recovery and database corruption are different cases.

Detected DB/blob corruption should enter deterministic maintenance/recovery behavior.

The system must not ask a model to reconstruct authoritative Task/grant history from natural-language logs.

## Migrations

Use ordered transactional migrations with checksums.

Rules:

1. explicit DB schema version;
2. migrate before new code writes new semantics;
3. failed migration rolls back where possible;
4. backup/export before destructive migration;
5. never edit released/applied migration history invisibly;
6. preserve system-image rollback/database compatibility;
7. semantic/security contract changes require the change-control process, not SQL-only edits.

## v0.1 crash/recovery gates

Implementation must test at least:

1. create Task -> restart -> exact intent/state survives;
2. transition commit/response loss -> same `transition_id` returns prior result;
3. active program -> restart -> semantic hash/snapshot remains interpretable offline;
4. binding commit/provider not launched -> `NOT_STARTED`/fresh attempt path;
5. provider crash with staging bytes -> no published Artifact;
6. publication committed/response lost -> return prior publication/no recompute;
7. one-shot grant use commit/response lost -> use remains consumed;
8. expired/revoked grants remain unusable after restart;
9. provider/output result committed but Task stale -> reconcile without duplicate operation;
10. opaque external uncertain outcome -> `OUTCOME_UNKNOWN`, not automatic retry;
11. concurrent recovery workers cannot commit contradictory resolutions;
12. provenance sequence/hash chain remains valid after recovery.

## Retention

Retention differs by record class.

Examples:

- Task/provenance: user/policy history;
- referenced registry/validation data: retain while history/Skills need them;
- final Artifacts: user-managed/portable;
- ephemeral allocations/staging: short-lived and recoverable;
- grant token handles: short validity, non-secret audit metadata may persist;
- provider diagnostics: bounded shorter retention;
- credential secret material: not in this DB.

## Architectural principle

> **Persist enough deterministic evidence to reconstruct reality, but do not turn the control database into a dump of user content, secrets, provider internals, or AI recollection.**
