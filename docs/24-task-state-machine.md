# 24 — Task State Machine

## Purpose

A task can outlive a shell window, provider process, model invocation, or control-plane restart. Its lifecycle therefore needs a deterministic persisted state machine rather than ad-hoc status strings generated by agents.

## Durable states

```text
CREATED
PLANNING
WAITING_FOR_INPUT
WAITING_FOR_AUTH
RUNNABLE
RUNNING
VERIFYING
PAUSED
RECOVERING
ROLLING_BACK
COMPLETED
FAILED
CANCELLED
ROLLED_BACK
```

States are control-plane facts. A model may recommend a transition but cannot write task state directly.

## State meanings

### CREATED

Task identity exists and original intent/input references have been durably recorded.
The private Task record retains the intent; append-only provenance retains only
the versioned, nonce-bound creation-intent commitment defined by doc 73.

No provider execution may begin in this state.

### PLANNING

The control plane is normalizing intent, creating/revising a typed plan, resolving required capabilities, or determining what clarification/authority is needed.

### WAITING_FOR_INPUT

The task cannot safely continue until the user/system provides missing or disambiguating information.

Examples:

- which of two date ranges is intended;
- which artifact should be used;
- output format is materially ambiguous;
- conflicting instructions cannot be safely resolved.

### WAITING_FOR_AUTH

A specific approval or authority condition must be satisfied before the next action can become runnable.

The required approval/request IDs must be persisted with the task/provenance; the state is not merely a UI message.

### RUNNABLE

A valid current plan exists and at least one step is eligible for execution after normal execution-time revalidation.

### RUNNING

One or more plan steps are actively executing or being coordinated.

A task can have multiple independent steps running concurrently if the plan and authority model permit it.

### VERIFYING

Execution has produced candidate outputs that require deterministic or independent verification before final publication/completion.

Verification failure may lead back to `PLANNING`/`RUNNING` for repair or to `FAILED`.

### PAUSED

Execution was intentionally suspended while retaining sufficient state to resume later.

Pause may be user-requested, policy-driven, resource-driven, or due to system shutdown.

### RECOVERING

After daemon/device restart or uncertain provider failure, the control plane is reconciling persisted state with real execution/artifact state.

No uncertain side effect should be blindly repeated while the task is in `RECOVERING`.

Entry is a trusted coordinator operation, including while the daemon remains
live. It is accepted only from `RUNNING`, `VERIFYING`, or `PAUSED`. The public
transition-request surface cannot request this state. Actor strings, reserved
transition-ID prefixes, and caller-supplied `internal` booleans are descriptive
data rather than proof that the caller is the recovery coordinator.

### ROLLING_BACK

The control plane is executing declared compensation/rollback operations for actions that are reversible.

Rollback is itself authorized and recorded; it is not assumed to be universally possible.

### COMPLETED

Terminal success. Required outputs have been published and required verification passed.

### FAILED

Terminal failure when the task cannot continue safely or usefully under current constraints and no automatic recovery/rollback path remains active.

Partial artifacts may remain but must not be represented as a completed task result.

### CANCELLED

Terminal state representing explicit cancellation before normal completion.

Cancellation may trigger a separate rollback/compensation path before the terminal state is committed if policy requires it.

### ROLLED_BACK

Terminal state indicating the task did not complete its requested outcome and declared rollback/compensation successfully restored the targeted reversible effects.

It does not imply every external observation can be erased (for example, a sent email cannot be unsent merely by changing task state).

## Normal transition graph

```text
CREATED
   │
   ▼
PLANNING ───────────────┐
   │                    │
   ├──> WAITING_FOR_INPUT ──┐
   │                    │   │
   ├──> WAITING_FOR_AUTH ───┤
   │                    │   │
   ▼                    │   │
RUNNABLE <───────────────┘   │
   │                         │
   ▼                         │
RUNNING <────────────────────┘
   │  │  │  │
   │  │  │  ├──> WAITING_FOR_AUTH
   │  │  ├─────> WAITING_FOR_INPUT
   │  ├────────> PAUSED ─────> RUNNABLE
   │
   ├───────────> VERIFYING ─────> COMPLETED
   │                 │
   │                 ├──────────> PLANNING/RUNNING (repair)
   │                 └──────────> FAILED
   │
   └───────────> FAILED
```

Recovery/rollback branches:

```text
persisted nonterminal state
        │ daemon/device restart or uncertain execution
        ▼
   RECOVERING
    │   │   │
    │   │   ├──> PAUSED / WAITING_FOR_* (state reconciled)
    │   ├──────> RUNNABLE / RUNNING (safe resume)
    └──────────> FAILED

FAILED or cancellation/recovery decision
        │
        ▼
  ROLLING_BACK
    │       │
    │       └──> FAILED (rollback itself failed/partial)
    ▼
ROLLED_BACK
```

## Allowed-transition table

The persisted Task Manager should enforce an explicit table rather than accept arbitrary next-state values.

| From | Allowed next states |
| --- | --- |
| CREATED | PLANNING, CANCELLED, FAILED |
| PLANNING | WAITING_FOR_INPUT, WAITING_FOR_AUTH, RUNNABLE, FAILED, CANCELLED, PAUSED |
| WAITING_FOR_INPUT | PLANNING, CANCELLED, PAUSED, FAILED |
| WAITING_FOR_AUTH | PLANNING, RUNNABLE, CANCELLED, PAUSED, FAILED |
| RUNNABLE | RUNNING, PLANNING, PAUSED, CANCELLED, FAILED |
| RUNNING | RUNNABLE, PLANNING, WAITING_FOR_INPUT, WAITING_FOR_AUTH, VERIFYING, PAUSED, RECOVERING, FAILED, CANCELLED, ROLLING_BACK |
| VERIFYING | COMPLETED, RUNNING, PLANNING, PAUSED, RECOVERING, FAILED, CANCELLED, ROLLING_BACK |
| PAUSED | PLANNING, RUNNABLE, RECOVERING, CANCELLED, FAILED |
| RECOVERING | PLANNING, RUNNABLE, RUNNING, WAITING_FOR_INPUT, WAITING_FOR_AUTH, PAUSED, FAILED, ROLLING_BACK |
| ROLLING_BACK | ROLLED_BACK, FAILED |
| COMPLETED | none |
| FAILED | ROLLING_BACK only when an explicit post-failure compensation policy allows it; otherwise none |
| CANCELLED | none after cancellation finalization |
| ROLLED_BACK | none |

Implementation may model pre-final cancellation compensation by entering `ROLLING_BACK` before committing `CANCELLED`, or may record the desired terminal outcome separately. The semantics must be explicit and tested.

The `RUNNING/VERIFYING/PAUSED -> RECOVERING` edges are reserved for deterministic
startup or live reconciliation through the private trusted coordinator entry.
That entry derives evidence from durable records and performs the normal
revision CAS; ordinary workers cannot use recovery as a retry shortcut.

## Transition transaction

A material task-state transition should be one atomic control-plane transaction containing at least:

1. current state/version check;
2. transition validation;
3. state update;
4. task revision increment;
5. state reason/code;
6. provenance event append or durable linkage;
7. related approval/failure/recovery metadata when applicable.

This prevents the UI from showing a state that has no corresponding durable event/history.

## Optimistic concurrency

Task records should carry a monotonically increasing revision.

Example:

```text
Task T91 revision 12: RUNNING
worker A attempts revision 12 -> VERIFYING
worker B attempts revision 12 -> RUNNABLE
```

Only one compare-and-swap/transactional update may succeed. The other must reload/reconcile rather than overwrite the task.

## Step state vs task state

Task state is not sufficient to represent every node.

Each plan-step execution should separately track states such as:

```text
PENDING
BLOCKED
READY
STARTING
RUNNING
SUCCEEDED
FAILED
CANCELLED
SKIPPED
UNKNOWN
```

The Task Manager derives/coordinately sets overall task state from the plan plus policy/user conditions.

For example, one failed optional step does not necessarily force `FAILED`; plan semantics decide whether the task can replan or complete without it.

## Idempotency and effect identity

Retries require stable execution-attempt and side-effect identities.

Before invoking an external side effect, the control plane should assign an operation ID such as:

```text
operation:T91:S8:send-report:v1
```

Providers that support idempotency keys should receive that ID.

On recovery, the control plane must determine whether the operation:

- definitely did not start;
- definitely completed;
- failed before effect;
- has unknown outcome.

Unknown external outcome must not be blindly retried if duplication could cause harm.

## Cancellation semantics

Cancellation means:

- stop scheduling new work;
- signal cancellable active providers;
- revoke/expire outstanding task grants where practical;
- record which active side effects could not be stopped;
- decide whether compensation is required/possible;
- retain provenance and produced artifacts under retention policy.

Cancellation is not "kill every PID and erase history."

## Completion gate

A task may enter `COMPLETED` only if:

- all required plan outcomes are satisfied;
- required verification is successful;
- required final artifacts are durably published;
- no mandatory approval remains pending;
- provenance is durably recorded through the completion transaction.

## Failure record

A failed task should carry structured failure data:

```text
failure_code
human_summary
responsible component/provider
failed step
retryable yes/no
safe_to_replan yes/no
unknown_side_effects yes/no
rollback_available yes/no
supporting provenance event IDs
```

Models may produce a user-friendly explanation from this record, but the structured failure facts come from deterministic services/providers.

## Restart recovery algorithm — v0.1

After `aiosd` has acquired exclusive kernel-held ownership of the local store
and advanced its durable fencing epoch, startup recovery:

1. load tasks whose state is nonterminal;
2. select only `RUNNING`, `VERIFYING`, and `PAUSED` tasks whose durable facts require reconciliation and enter `RECOVERING` through the private coordinator operation;
3. inspect persisted execution attempts, operations, allocations/publications, grants, and provider supervisor state;
4. classify each attempt, external operation, Artifact publication, and other recovery subject independently from evidence for that exact subject;
5. validate output artifact hashes/commit markers;
6. reconstruct ready/blocked plan nodes;
7. expire invalid grants;
8. move task to `RUNNABLE`, `WAITING_FOR_*`, `PAUSED`, or `FAILED` as appropriate;
9. never infer one subject's certainty from another subject or assume missing evidence means an effect did not start;
10. never assume an unrecorded external side effect can simply be repeated.

## v0.1 tests

At minimum:

- reject illegal `CREATED -> COMPLETED` transition;
- reject stale revision update;
- persist/reload every state;
- restart while a deterministic provider is running;
- restart after output file exists but before completion event;
- recover a task waiting for approval;
- cancel a task with one running and one pending step;
- provider failure triggers safe retry/alternate-provider path;
- verification failure returns to repair path without publishing false final output;
- terminal state cannot be silently reopened;
- public transitions to `RECOVERING` fail even when the actor string or transition ID claims to be internal;
- trusted live reconciliation accepts only `RUNNING`, `VERIFYING`, or `PAUSED` and derives its own evidence;
- two local-store owners cannot both mutate or run recovery, and a stale fencing epoch cannot commit;
- mixed per-subject evidence does not collapse into an optimistic Task-level retry decision.

## Non-goal

This state machine does not attempt to model every future distributed multi-device condition. It establishes a durable deterministic local foundation that can later gain distributed leases/consensus where needed without making current task state probabilistic.
