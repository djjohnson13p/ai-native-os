# 77 — v0.1 Authority Coordinator: Policy, Approval, and Grant Lifecycle

## Purpose

AIOS agents/models/providers must be able to request narrowly scoped actions without inheriting the logged-in user's full authority.

The v0.1 Authority Coordinator turns semantic authority requests into deterministic runtime decisions/grants while preserving these separations:

```text
semantic request != permission
user approval      != unrestricted permission
provider need      != permission
policy allow       != ambient credential
credential         != authority
```

The coordinator must remain deterministic, auditable, revocable, and independent of one model/provider/policy-language implementation.

## Core authorization equation

A runtime grant is the intersection of:

```text
validated semantic authority request
∩ current deterministic policy
∩ exact provider principal / Execution Binding
∩ exact concrete resource resolution
∩ current Task state/constraints
∩ required approval state
∩ time/usage constraints
```

No layer may broaden the result.

If any required dimension is unknown/incompatible, fail closed.

For the Stage-1 local Artifact policy profile, activating a new policy revision
is a mandatory re-evaluation event for every previously coordinator-issued
grant, even when the payload is identical. The prior grant remains an immutable
historical receipt but cannot authorize a new Task transition or Artifact use.
The coordinator must issue fresh grants under the new activation rather than
silently carrying old approval or unconditional allow forward. A policy change
therefore cannot leave an already-open reader or writer with continuing use
authority merely because its short time limit has not elapsed.

## Actors

### User / organization principal

Owns/controls resources and policy context.

The user does **not** automatically become the principal under which provider code executes.

### Agent/planner

Can propose plans/authority requests but receives only explicitly granted agent-scoped capabilities.

### Provider principal

The concrete provider/workload that will perform the capability invocation.

Runtime grants are normally bound to this provider/workload principal plus Task/Execution Binding.

### Authority Coordinator

Trusted deterministic component that:

- normalizes runtime authorization requests;
- resolves policy entities/context;
- invokes the policy engine;
- coordinates required human/organizational approval;
- creates/revokes/validates scoped grants;
- mediates credential/resource handles;
- emits provenance.

### Policy engine

Pure deterministic decision backend.

Cedar remains the proposed v0.1 reference backend under ADR 0010, but AIOS semantic authority/grant contracts do not depend on Cedar syntax.

## Authorization stages

ADR 0044 and migration `0016_authority_candidate_reservations` make the provider/resource selection stage durable without creating a premature Execution Binding. The coordinator reserves binding/attempt IDs and seals exact Task, validated semantic node, provider/build/evidence/trust, and resolved resource pins in a PENDING candidate. The candidate grants no authority. Policy/approval evaluate those exact reserved IDs; later finalization must revalidate current facts and commit grants, issuance receipts, bound allocations, and the complete immutable binding atomically. Exact response-loss replay returns the same pending candidate; changed facts require a new identity. Historical bindings are not backfilled.

```text
Validated AIOS IR node
  ↓ semantic authority requests
Provider/resource selection candidate
  ↓ runtime Authority Evaluation Request
Deterministic policy evaluation
  ├─ DENY
  ├─ REQUIRE_APPROVAL
  └─ ALLOW
         ↓
approval conditions satisfied if required
         ↓
scoped Capability Grant / token-handle
         ↓
Execution Binding/provider invocation
         ↓
validation at point of use
```

A plan/IR validation success never bypasses this runtime process.

## Runtime authority request

A concrete request binds semantic intent to runtime facts:

```text
request_id
task_id
semantic program hash + registry snapshot + node
capability
requesting principal/provider
execution binding / attempt
semantic action
resolved resource identity/class
resource sensitivity/ownership
external destination/service identity when relevant
effect/egress context
requested duration/use constraints
current Task/policy/approval context
```

The runtime request must correspond to an authority request already present in validated semantic IR or another explicitly permitted control-plane authority path (for example rollback/recovery policy).

A provider cannot invent a new action/resource at runtime merely by asking for it.

## Resource resolution

Semantic IR uses symbolic selectors such as:

```text
input:source
task.output
service:model
destination:remote-model
credential:mail-send
```

The Authority Coordinator resolves them to concrete resource entities/handles from the Task/Execution Binding.

Examples:

```text
input:source
  -> Artifact artifact://A123

task.output
  -> Output Allocation alloc-88

service:model
  -> service://model/provider-X deployment Y

credential:mail-send
  -> credential handle cred-17 (not raw secret)
```

Resolution itself cannot broaden scope beyond the selector/Task binding.

## Policy model

Policy is default-deny.

Unknown principal/action/resource type or unsupported policy schema fails closed.

Policy decision categories:

```text
ALLOW
DENY
REQUIRE_APPROVAL
```

A policy engine may internally produce more detailed diagnostics/obligations, but the Authority Coordinator owns the stable AIOS decision semantics.

## Deny precedence

An explicit hard deny cannot be bypassed by:

- model/planner confidence;
- provider manifest;
- user clicking an approval prompt generated by an untrusted provider;
- package signature;
- provider conformance;
- administrator-friendly UI text;
- previous Task approval;
- cached Skill execution.

Approval satisfies a policy condition; it does not override architecture invariants/hard policy prohibitions.

## Policy context

Useful deterministic context can include:

```text
Task ID/state
semantic program/node hash/identity
principal/provider/workload identity
resource/Object/Artifact/credential identity
resource sensitivity/classification
requested effect class
egress destination/service/region
current time/expiry
network/locality class
cost/irreversibility class
approval record refs
organization/device trust state
```

Do not put arbitrary model prose into trusted policy context and then treat it as an authoritative fact.

## Reference policy engine mapping

If Cedar is used:

```text
principal -> AIOS Principal/Provider/Workload entity
action    -> normalized AIOS authority action
resource  -> resolved AIOS Resource entity
context   -> bounded typed Task/effect/egress/approval/runtime facts
```

AIOS owns the mapping schema and tests.

Changing Cedar policy text/runtime does not redefine semantic capability/Task contracts.

## Policy snapshot identity

The bounded Stage-1 local Artifact policy evaluator uses migration `0017_authority_policy_evaluation`. A trusted coordinator activates a strictly parsed, immutable `0.1` builtin rule payload identified by canonical SHA-256 content. Activation is an independent monotonic revision, so reactivating identical content invalidates approvals from an earlier revision. Rules match exact action, resource kind, and sensitivity; hard `DENY` wins over `REQUIRE_APPROVAL` and `ALLOW`; unmatched requests deny. Only `artifact.read` and `artifact.write` on the pending local candidate's pinned Artifact and output allocation are supported. Remote, egress, network, destructive, and unknown actions cannot reach an allow path in this profile.

Each candidate evaluation persists one runtime authority request per validated semantic action/selector and an immutable decision per evaluation phase. The approval fingerprint commits the full ordered candidate resource set (including inherited output sensitivity), Task security constraints, provider/build/evidence/trust pins, reserved binding/attempt, semantic identity, and policy content plus activation revision. Task revision and normal Task state changes remain separate eligibility/CAS checks. A trusted approval remains a condition: re-evaluation after approval writes a new `ALLOW` decision and never edits the original `REQUIRE_APPROVAL` decision. This stage issues no grant, token, output allocation, Execution Binding, or Step Execution. Finalization must recheck current evidence, resources, policy activation, approval fingerprint and expiry, trusted time, and point-of-use validity within its own atomic transaction.

The coordinator may reserve and evaluate a non-executable candidate while the Task is `PLANNING`. If evaluation creates a real pending approval, the ordinary Task CAS transition names that approval and moves to `WAITING_FOR_AUTH` before the authenticated user decides it; approval-backed finalization requires that waiting state. If every freshly re-evaluated decision is unconditional `ALLOW` with no approval reference, finalization may instead commit the exact grants, binding, READY step, allocations, and provenance while the Task stays `PLANNING`, provided its active plan and program are coherent. This does not admit execution: the normal guarded `PLANNING → RUNNABLE → RUNNING` path and independent point-of-use checks remain required. A policy `DENY` or mixed approval result never uses the `PLANNING` finalization path.

The initial local Artifact issuance profile has a trusted five-minute ceiling measured from the paired effective wall-time floor. The grant's stored expiry is the earliest of that ceiling, the approval request expiry, and the approved-until time when approval is required. Checked nanosecond arithmetic maps that exact duration to the same session's monotonic clock; a provider cannot choose or extend the expiry. A restarted manager creates a new clock session, so a previous session's grant remains historical evidence but cannot authorize new work. This local profile is an implementation limit, not a general duration policy language; adding configurable duration requires an explicit contract update.

At startup, a finalized coordinator preparation from an older clock session is retired only when its exact issuance receipts and deadlines are present and no grant use, protected operation, invocation, credential use, publication, output writer, or started attempt indicates possible protected work. A completed, unbound reversible Artifact import is input history, not use of this candidate. Its grants become durably `REVOKED` with reason `AUTHORITY_SESSION_RETIRED`; the immutable candidate, binding, deadline, and original finalization response remain historical evidence. A `RUNNABLE` or approval-backed `WAITING_FOR_AUTH` Task then follows its ordinary CAS and provenance path back to `PLANNING` so new execution requires a new candidate and fresh grants; the waiting approval marker is cleared only on that transition. Missing issuance evidence or possible use blocks this automatic replanning. A second restart must not reinterpret the old preparation as current authority.

Evaluation and approval recheck the currently authenticated provider trust-source receipt against the candidate's pinned source, the exact unique verified Task input association, and that each reserved output allocation ID remains unused. A sealed approval request is compared with its canonical structured prompt and requiring evaluation sidecar before it can satisfy the condition; missing or changed sidecars fail closed. Earlier approval rows are not backfilled into this trust path.

The baseline SQL approval ledger predates the JSON schemas' `REVOKED` status, `REVOKE` decision, and nullable scope. Migration 0017 does not reinterpret those legacy rows or silently widen the broker's checks. It stores a private revocation marker in `authority_approval_bindings`; a future finalizer must reject a marked binding explicitly. No 0017 approval can authorize a grant until that reconciliation is complete.

The grant finalizer must treat approval withdrawal as an atomic issuance fence:
it rejects a revoked binding while holding the same serialized transaction that
creates the grant and receipt. Every later grant admission, including an
already-open Artifact handle's next protected operation, must reject that
withdrawal marker independently of the approval row's older `APPROVED` status.
Withdrawal must have a durable, one-way, queryable result that survives a lost
response and restart; legacy approval rows are not silently upgraded into this
path. Grant issuance also binds the exact clock session and monotonic deadline
specified in doc 89. A prior-session grant remains historical/recoverable but
cannot authorize new protected work after restart.
The `RUNNABLE → RUNNING` admission checks every ready coordinator binding's
grants against one locked wall/monotonic observation before starting any step.
An expired grant rejects the transition and records an irreversible expiry
latch. Finishing staged output does not extend its authority: publication
placement and final metadata adoption check the same grant deadlines again.
Within an issued grant's clock session, a later lower monotonic sample cannot
erase an earlier trusted observation, including one recorded by an advisory
preflight. Every protected grant check compares its exact entry sample against
those immutable observations before allowing use.

Every runtime decision should be attributable to a policy-set snapshot/version/hash.

This answers:

> Which deterministic policy actually allowed/denied this action when the Task ran?

Policy content identity is separate from semantic Registry Snapshot and provider package identity.

Future organization policy distribution/signing can build on this.

## Approval request

When policy returns `REQUIRE_APPROVAL`, the coordinator persists a structured approval request.

It includes enough information for a trusted system View to explain:

- Task/outcome context;
- exact action;
- exact resource/object/artifact/credential class;
- provider/service/destination;
- data sensitivity/egress;
- irreversible/external effect class;
- monetary/cost limit where relevant;
- requested scope/duration;
- why policy requires approval.

Untrusted provider UI cannot self-certify approval.

## Trusted approval UI boundary

The trusted shell/Presentation Broker renders security-sensitive approval facts from structured coordinator data.

Provider content may be shown as supplementary context but cannot replace/obscure:

```text
action
resource/destination
scope
sensitivity
effect/irreversibility
provider identity
expiry
```

A provider window/web page cannot impersonate a system approval decision.

## Approval scope

Initial classes:

```text
ONE_SHOT
TASK
TIME_LIMITED
PERSISTENT_POLICY_CHANGE   # separate explicit administrative action
```

Default for consequential side effects is narrow/one-shot or Task-scoped.

"Always allow" is not merely a bigger Capability Token; it is a deliberate policy/configuration mutation with stronger UI/provenance/review requirements.

## Approval freshness

Approval becomes stale/invalid when material facts change, such as:

- Task/node semantic identity changes;
- resource/destination changes;
- provider principal/binding changes where approval was provider-specific;
- requested effect/egress/cost scope increases;
- approval expires/revoked;
- policy revision requires reapproval.

Replanning cannot silently carry old approval to broader work.

## Capability grant/token

A successful allow path creates a narrowly scoped runtime grant.

v0.1 should prefer an **opaque random token/handle + server-side durable grant record** over a complex self-contained bearer/JWT design.

Reasons:

- simple revocation;
- small trusted parser surface;
- easy Task/provider/binding lookup;
- no claim-parser ambiguity;
- local-first operation.

The token value itself is a credential and must not be logged/provenance-copied in raw form.

Record only grant/token ID references where useful.

## Grant binding

A grant binds at least:

```text
grant/token ID
task ID
semantic program/node/capability
principal/provider/workload
execution binding or declared binding scope
action(s)
concrete resource IDs/handles/constraints
issued/expiry time
usage limit / one-shot state when applicable
policy decision ID + policy snapshot
approval ID when required
delegation = false by default
revocation state
```

A grant created for provider A must not work for provider B merely because both implement the same capability.

Provider substitution/rebinding requires re-evaluation/new grant unless an explicit contract proves the old grant is valid for the new principal (v0.1 should default to new grant).

### Stage-1 issuance fence

Migration `0015_authority_issuance_fence` adds an immutable issuance receipt for each newly admitted grant. Launch and Artifact resource mediation require that receipt to match the durable grant's token ID, Task, Execution Binding, attempt, policy decision, and issue time. No historical grant is backfilled: legacy rows remain available for interpretation and recovery but cannot authorize new protected work merely because they look like coordinator output. A missing, changed, or unversioned receipt schema fails store preflight. The receipt cannot replace the point-of-use scope, approval, expiry, revocation, and usage checks.

This is a compatibility fence, not proof against a privileged writer who can edit arbitrary SQLite rows. The production coordinator-only writer boundary is still required before any new runtime grant can be issued. Test fixtures may insert synthetic receipts through test-only code; that route is absent from production builds. The baseline persistence tables retain nullable historical columns for migration compatibility, while an admitted receipt requires nonempty token and binding identity. Historical nulls must never be filled by inference.

## Point-of-use validation

Grant creation is not enough.

The mediating resource service validates at use:

- token/grant exists;
- active/not revoked;
- not expired;
- Task/binding/principal match;
- requested action/resource within scope;
- usage budget remains;
- Task not cancelled/terminal in a way that invalidates grant;
- policy requires no mandatory re-evaluation event that has occurred.

Resource services should not trust provider-supplied decoded token fields.

## Revocation

Grant revocation triggers include:

- Task cancellation/rollback/failure where scope no longer needed;
- user/admin revocation;
- provider crash/rebinding;
- Execution Binding invalidation;
- approval withdrawal/expiry;
- policy/security revocation;
- credential rotation;
- one-shot use consumed;
- token expiry.

Revocation prevents future use. It cannot erase an already completed external effect.
For a Task cancellation, active eligible grants are marked `REVOKED` in the
same transaction as the Task transition and provenance event. Active grants
alone do not block cancellation; a live attempt, unresolved operation,
provider invocation, or credential use still does. A rejected cancellation
leaves both the Task and its grants unchanged.

## Delegation

Default:

```text
delegable = false
max_depth = 0
```

v0.1 should avoid arbitrary agent/provider delegation.

If later supported, a child grant must be a strict subset of parent authority, have shorter/equal lifetime, and retain provenance of the delegation chain.

## Egress authority

Keep separate:

```text
network.connect
```

and:

```text
data.egress
```

A provider may be allowed to establish a network connection without being allowed to send protected Task data.

For data egress, runtime request/grant ties to:

```text
source Artifact/Object refs
destination class/service identity
purpose
sensitivity
byte/record scope where known
```

The Network Fabric still enforces path/connectivity; Authority Coordinator enforces permission.

For the Stage-1 local fixture profile in ADR-0045, the trusted coordinator
resolves the exact service and adapter from its privileged catalog and pins
them with the source Artifact/content revision, purpose, sensitivity, operation
ID, and whole-operation byte ceiling in the candidate reservation. The same
candidate must request `artifact.read` for that source. Finalization issues
the read and exact `external-destination` egress grants atomically; every
destination callback checks both grants and the current service registration.
`network.connect` cannot stand in for either grant. The v0.1 Task contract has
no residency field, so a Task with a known residency restriction is outside
this profile and must fail closed at its integration boundary.
The evaluation request schema requires `data.egress` and
`external-destination` together with non-null egress details, including the
source content hash, operation ID, adapter ID, descriptor hash, and byte
ceiling, together with a nonempty purpose, resolved sensitivity, and one
source Artifact reference. Non-egress requests retain optional or null egress details. This
closes a class-only request shape that did not match the coordinator's sealed
request serialization.

## Secret/credential mediation

Providers do not receive the user's long-lived credential store.

Flow:

```text
IR requests credential.use / semantic external action
  ↓
policy/approval
  ↓
Credential Broker resolves opaque credential handle
  ↓
provider receives narrowly scoped short-lived injection/handle
```

Where an external service supports delegated short-lived tokens, prefer those over raw long-lived secrets.

Raw secret material must never be put in AIOS IR, provenance, logs, Capability Token metadata, or planner prompt by default.

## Irreversible actions

For actions classified as `IRREVERSIBLE_EXTERNAL`, the coordinator requires the stronger cross-domain gate defined in `docs/45-cross-domain-transactions-and-compensation.md`:

- prerequisite verification complete;
- current approvals valid;
- destination/resource revisions current;
- prior operation not possibly completed;
- required provenance durable before effect;
- grant current at point of use.

## Rollback/compensation authority

Compensation is a new side effect and gets separately evaluated/granted.

A failed original operation does not automatically confer authority to perform rollback operations.

Recovery policy can predeclare allowable compensation classes, but the runtime still creates auditable scoped grants.

## Offline behavior

Local deterministic policy and grant validation must work offline for local resources/providers.

A cloud policy service cannot be required for basic recovery/local operation unless an organization intentionally configures that dependency and accepts the degraded-mode consequences.

## Policy failure modes

If policy engine is unavailable/corrupt:

- default to deny new protected actions;
- retain recovery/read-only inspection paths that do not require granting new broad authority;
- never ask the model to substitute for policy;
- expose a deterministic degraded-state diagnostic.

## v0.1 acceptance tests

At minimum:

1. provider requesting action absent from validated node is denied before policy grant;
2. unknown action/resource/principal fails closed;
3. explicit deny cannot be overridden by approval/model/provider trust;
4. require-approval persists structured approval request;
5. trusted approval creates a new decision/grant only within approved scope;
6. changed destination/provider/semantic node invalidates stale approval as specified;
7. same grant cannot be used by different provider principal;
8. same grant cannot access unrelated Artifact/output allocation;
9. expired/revoked/one-shot-consumed grant fails at point of use;
10. Task cancellation revokes outstanding eligible grants;
11. provider rebinding requires a new grant in v0.1;
12. `network.connect` grant alone cannot authorize Task-data egress;
13. credential use reveals no raw secret to provenance/logs/planner;
14. compensation action requires separate authority evaluation;
15. policy-engine outage denies new protected action without asking model;
16. offline local policy works without cloud;
17. decision/provenance records identify policy snapshot/version;
18. model/planner cannot mutate policy/grant records directly.

### Issue #3 executable fixture evidence map

The 14 rows in `examples/authority/authority-cases.json` are expected
outcomes, not executable setup instructions. A test runner must construct
validated programs, trusted provider and service records, Tasks, resources,
policy activations, approvals, grants, and trusted time through the production
coordinator and Artifact interfaces. It must load every row exactly once,
reject unmapped names or facts, and compare the row's expected outcome and
reason with the actual result or durable receipt from the named production
stage: reservation, policy evaluation, approval, issuance, or protected use.
A test-derived
reason or a synthetic database grant does not satisfy this gate. A denial
must prove that no new or broader grant, additional protected admission, or
external effect escaped. Revoked, expired, consumed, and wrong-context cases
must first obtain a genuine historical grant and verify its lifecycle.

Candidate reservation keeps a coarse safe outer error message and carries a
typed, same-fence stage and reason for trusted diagnostics. An undeclared
runtime action/resource claim returns `AUTH_SEMANTIC_REQUEST_MISMATCH` before
unsupported-action handling and creates no candidate or grant. Policy
evaluation returns the reason persisted in each decision, so tests do not
infer a reason from a fixture name.

| Fixture | Production action and observable |
| --- | --- |
| `exact-local-artifact-read-allowed` | Reserve a validated input, evaluate `AUTH_ALLOW`, finalize, then read its bytes through a bound provider session. |
| `provider-invents-network-action-not-in-semantic-ir` | Submit an extra `network.connect` claim at coordinator reservation; `AUTH_SEMANTIC_REQUEST_MISMATCH` precedes any policy/grant. |
| `private-data-egress-requires-approval` | Resolve one private Artifact and exact service; evaluation persists `REQUIRE_APPROVAL/AUTH_REQUIRE_APPROVAL`, and pending approval cannot finalize. |
| `approval-stale-after-destination-change` | At a trusted approval-application boundary, claim the old approval for a same-class different service; reject that claim with `AUTH_APPROVAL_STALE` and zero bytes. Fresh evaluation may instead request a new approval. |
| `approval-stale-after-semantic-program-change` | Supersede a real validated program and claim the old approval for the new program at that boundary; reject reuse with `AUTH_APPROVAL_STALE`. Symbolic example hashes must map to real validated identities. |
| `grant-used-by-wrong-provider` | At a trusted admission boundary, present a genuinely issued grant under a separately authenticated provider context; return `AUTH_GRANT_PRINCIPAL_MISMATCH` before protected use. |
| `grant-used-for-wrong-task` | At a trusted admission boundary, present a genuinely issued grant under another Task context; return `AUTH_GRANT_TASK_MISMATCH` before protected use. |
| `one-shot-grant-already-consumed` | Consume one real admission, then attempt a distinct protected admission; return `AUTH_GRANT_USAGE_EXHAUSTED`. Historical replay of the first operation remains valid. |
| `expired-grant` | Advance trusted time beyond a real grant deadline and attempt admission or retained use; return `AUTH_GRANT_EXPIRED` with no further effect. The denial must not depend on a test mutating the grant row to `EXPIRED`. |
| `revoked-grant-after-task-cancel` | Cancel through Task transition, verify atomic grant revocation, then use a retained handle; return `AUTH_GRANT_REVOKED` and release zero further bytes. |
| `network-connect-alone-does-not-authorize-egress` | Issue independent, genuine `network.connect` authority, then attempt data export without `data.egress`; return `AUTH_GRANT_SCOPE_MISMATCH` with no writer or bytes. No fabricated network grant qualifies. |
| `explicit-policy-deny-cannot-be-overridden-by-approval` | Evaluate a real approved request under a current hard deny; persist `DENY/AUTH_DENY_POLICY` and issue no grant. |
| `policy-engine-unavailable-fails-closed` | Make the trusted policy backend unavailable after valid candidate setup; return `DENY/AUTH_POLICY_ENGINE_UNAVAILABLE` and issue no grant. Missing policy and corrupt snapshots are distinct conditions. |
| `provider-rebinding-requires-new-grant` | Retry with a new authenticated Execution Binding and present the old authority at a trusted binding admission boundary; return `AUTH_PROVIDER_BINDING_MISMATCH`. A grant used under another binding has the separate `AUTH_GRANT_BINDING_MISMATCH` meaning. |

This map describes required evidence, not current coverage. In particular,
old-approval claims, cross-context grant presentation, old authority at a new
binding, independent `network.connect` issuance, and policy-backend outage
need explicit trusted production entry points or contract changes. Private
session fields, direct SQL changes, fabricated grant rows, and generic errors
must not be used to impersonate those paths. The fixture runner also needs
documented symbolic aliases for real validated program hashes.

Admission diagnostics must be produced by the same trusted operation and
time/transaction fence that enforces the denial. In particular, testing a
generic `InvalidRecord` or `ARTIFACT_AUTHORITY_DENIED` and inferring the
catalog reason afterward does not prove this fixture gate. Keep coordinator
mutation methods privileged; public-path evidence means calling their real
production implementations from tests, not exposing them to providers.
These 14 rows are necessary but do not replace the rest of Issue #3:
task-local write, external communication and destructive-action handling,
malformed and overbroad tokens, denied planner escalation, R-SEC-001 through
R-SEC-007, and expiry, revocation, and race coverage still require evidence.

## Relationship to Cedar

Cedar remains a strong reference candidate because its principal/action/resource/context model aligns well with AIOS.

However v0.1 should place it behind an Authority/Policy Engine interface and test AIOS semantics independently from Cedar policy syntax.

The Cedar spike should prove:

- typed entity mapping;
- deny/permit/approval-obligation mapping strategy;
- schema validation;
- policy snapshot hashing/versioning;
- deterministic embedded/offline evaluation;
- bounded performance;
- safe failure behavior.

If Cedar fails the spike, replace the backend without changing AIOS semantic authority contracts.

## Principle

> **Models request. Policy decides. Approvals satisfy policy conditions. Scoped grants let one exact principal act on one exact Task/resource—and nothing in that chain silently widens authority.**
