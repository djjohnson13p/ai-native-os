# 74 — v0.1 Task Manager Transition and Compare-and-Swap Contract

## Purpose

The Task is the durable operating-system execution/audit object. It can outlive models, providers, Views, processes, and control-plane restarts.

The Task Manager therefore needs a deterministic single-writer transition boundary that prevents:

- stale workers overwriting newer state;
- illegal state jumps;
- terminal Tasks silently reopening;
- Task state changing without matching provenance;
- retries duplicating a transition after a response is lost;
- model/provider code directly mutating Task rows;
- external side-effect uncertainty being collapsed into an optimistic retry.

This document turns `docs/24-task-state-machine.md` into a Phase-I implementation contract.

## v0.1 ownership model

The **Task Manager is the only component allowed to commit Task current-state transitions**.

Other components may submit transition requests/proposals, but they do not update the `tasks` table directly.

Conceptually:

```text
planner/provider/policy/user/recovery coordinator
        ↓ transition request
Task Manager
        ↓ deterministic guards + CAS + transaction
Task current record + Provenance journal
```

The v0.1 implementation can live as a library/module inside the local control-plane process before it becomes an RPC service.

### Exclusive local-store owner and fencing epoch

The local Task store has exactly one mutation owner. Before opening the store
for schema migration, provenance verification, recovery, or any mutation, the
daemon MUST acquire an operating-system kernel-held exclusive lock associated
with that store. A second daemon that cannot acquire the lock fails closed; it
does not inspect active Tasks and must not trigger recovery. The lock is held for
the entire writable store lifetime and is released by the kernel if the owning
process exits or crashes.

The kernel lock MUST be bound to the database file object (or an identity-bound
stream of that object), not to a path-derived sidecar or process-selected lock
directory. Alternate spellings and aliases of the same file, including symbolic
links, hard links, case variants, and short-path forms where supported, MUST
contend on the same owner lock even when processes use different environment or
temporary-directory settings. Failure to acquire an identity-bound lock fails
closed before schema migration, recovery, or mutation.

While holding the lock, startup atomically increments a durable monotonic
`store_fencing_epoch` in trusted store metadata and binds that exact
epoch to the in-memory Task Manager. Bootstrap/migration may create the metadata
record for a legacy store while the exclusive lock is held, but it must establish
the epoch before application migrations or recovery mutate Task data. The epoch
must never reset, wrap, or be reused; inability to advance it leaves the store
closed for mutation.

Every transaction that creates or changes trusted state, including migrations,
Task/provenance writes, transition idempotency records, execution attempts,
recovery assessments, and maintenance repair, checks that its held epoch equals
the durable current epoch before its first mutation and again as part of the
commit predicate. An epoch mismatch rolls back and reports a storage/fencing
failure. SQLite's writer serialization and actor/daemon IDs do not replace the
kernel lock or the durable fence.

### Task creation privacy binding

Task creation generates a fresh 32-byte OS-CSPRNG nonce inside the trusted
transaction boundary. The nonce and original/normalized intent are private Task
data. The `task.created` event records only the versioned field commitments from
doc 73. Public Task summaries, provenance APIs, logs, and exports never include
the nonce, and provenance/exports never include raw intent.

Creation fails atomically if randomness cannot be obtained or the private nonce
cannot be stored with the Task. A malformed/missing nonce or commitment mismatch
found later quarantines that Task from scheduling and recovery mutation. Legacy
raw-intent events remain immutable but fail the current typed verification gate,
so they cannot be emitted through normal `privacy-redacted-projection-v1`
export; they are not silently rehash-upgraded. A migrated legacy Task whose
immutable creation event already satisfies the current typed commitment
contract may use that projection after full chain and private-row verification.

## Durable Task state

The canonical durable states remain:

```text
PLANNING
WAITING_FOR_INPUT
WAITING_FOR_AUTH
RUNNABLE
RUNNING
VERIFYING
PAUSED
RECOVERING
ROLLING_BACK
COMPLETED
FAILED
CANCELLED

```

The allowed-transition table in `docs/24-task-state-machine.md` remains controlling unless an accepted ADR changes it.

## Compare-and-swap precondition

Every mutation request carries:

```text
task_id
expected_revision
expected_state
transition_id
to_state
```

The transition transaction first verifies:

```text
stored revision == expected_revision
stored state    == expected_state
```

If either fails:

- no Task mutation;
- no state-transition provenance append;
- caller receives current revision/state plus structured conflict reason;
- caller must reload/reconcile rather than retry with guessed state.

## Revision semantics

A Task starts at revision 1.

Each successful **Task current-record mutation transaction** increments revision exactly once.

A transition request that changes state plus associated current metadata (waiting reason, active plan, failure record, etc.) is one revision increment.

Pure read/inspection does not increment revision.

A rejected/stale/invalid request does not increment revision.

Step-execution records have their own revision/attempt identity; not every internal provider progress update needs to increment the Task revision unless it materially changes Task current state/current-record fields.

## Transition request idempotency

Every transition request has stable `transition_id`.

The Task Manager persists enough transition-result identity to support:

```text
same transition_id + byte/semantic-equivalent request
    -> return prior result / do not append duplicate event

same transition_id + different requested transition
    -> reject ID reuse conflict
```

Transition-ID lookup precedes Task lookup. A `TASK_NOT_FOUND` result therefore
has null observed state/revision, and an ID-reuse conflict may also have null
observations when its new payload names an absent Task. Reuse-conflict
observations are always a pair: both null or both populated. Every other result
has a populated observed Task state/revision.

This protects a caller that times out after the database committed but before it received the response.

Suggested code:

```text
TASK_TRANSITION_ID_REUSE_CONFLICT
```

`transition_id` is not an authority grant.

## Transaction boundary

A successful material transition commits in one SQLite transaction:

```text
BEGIN IMMEDIATE
  verify held store_fencing_epoch equals durable current epoch
  load Task row
  check expected revision/state
  check transition_id idempotency
  validate allowed transition
  validate target-state guards
  validate structured metadata update
  allocate/append provenance journal record
  update Task current record
  increment Task revision once
  persist transition result/idempotency record
  verify fencing epoch remains current as part of commit predicate
COMMIT
```

Any failure rolls back all writes.

This implements ADR 0035.

## Provenance event

Every successful state transition produces one `task.transitioned` material
Task provenance event with a typed `task_transition` object containing at least:

```text
task ID
previous state
new state
previous revision
new revision
transition ID
structured reason code
requesting actor/principal
relevant plan/program/approval/failure/recovery references
```

The Task record can link its current `state_reason` to the resulting provenance event ID.

A failed transition request may be logged diagnostically; it does not need to become Task provenance unless the denial/conflict is itself a material Task fact required by policy/recovery.

Authorization/approval denials already have their own provenance semantics where relevant.

## Transition guards

Allowed adjacency is necessary but not sufficient.

The Task Manager evaluates deterministic target-state guards using current durable records.

### `CREATED -> PLANNING`

Requires:

- original intent is durably present;
- required initial Artifact references that already exist are syntactically resolvable;
- Task is not terminal/cancelled.

### `PLANNING -> WAITING_FOR_INPUT`

Requires structured waiting reason/input request identity.

### `PLANNING/RUNNING -> WAITING_FOR_AUTH`

Requires at least one persisted approval/authorization request the Task is actually blocked on.

### `PLANNING/WAITING_FOR_AUTH/PAUSED/RECOVERING -> RUNNABLE`

A coordinator may prepare an exact READY attempt in `PLANNING` after unconditional policy `ALLOW`; preparation does not itself change Task state or authorize runtime use. The normal guarded transition remains the admission boundary.

Requires:

- current validated semantic program exists;
- current program validation evidence is acceptable/current;
- at least one required node is deterministically eligible to attempt after normal policy/provider/resource checks or the transition contract explicitly represents that those checks have passed;
- when the active program has a finalized coordinator candidate, at least one READY attempt has a current, exact binding and usable authority;
- no unresolved blocker that makes `RUNNABLE` false.

The Task Manager does not treat a model's claim that the Task is runnable as evidence.

### `RUNNABLE -> RUNNING`

Requires one or more step attempts can be/were atomically admitted for execution under current binding/authority.

### `RUNNING -> VERIFYING`

Requires candidate required outputs/claims exist and the current semantic program requires verification before completion/publication.

### `VERIFYING -> COMPLETED`

Completion gate requires:

- all required semantic outputs/outcomes satisfied;
- required verification passed;
- required final Artifacts durably published;
- no mandatory approval/input blocker remains;
- no required external operation has `OUTCOME_UNKNOWN`;
- material provenance through completion is commit-ready in the same transaction.

### Any nonterminal -> `CANCELLED`

Uses the exact allowed-transition table.

Before finalizing cancellation:

- stop admission of new work;
- signal cancellable active attempts;
- revoke/expire outstanding grants where practical;
- record active attempts/effects that could not be stopped;
- route through `ROLLING_BACK` first when policy requires compensation before the terminal cancellation outcome.

### `FAILED -> ROLLING_BACK`

Allowed only when:

- an explicit compensation/rollback policy says it is appropriate;
- compensating operations are separately authorized;
- the Task retains sufficient recovery metadata to proceed.

### `ROLLING_BACK -> ROLLED_BACK`

Requires all mandatory declared compensation operations have deterministically completed to the degree the rollback contract defines.

It does not claim externally observed effects were erased.

## Terminal-state immutability

Terminal states:

```text
COMPLETED
FAILED
CANCELLED
ROLLED_BACK
```

are not reopened by ordinary transition requests.

The only v0.1 exception is the explicit documented post-failure `FAILED -> ROLLING_BACK` compensation path.

A future user request to repeat/repair completed work creates a new Task or an explicitly versioned derived/retry Task relationship rather than mutating historical success.

## Step execution is separate

Task state is a coarse durable lifecycle.

Each semantic node/provider attempt uses a separate execution record with states such as:

```text
PENDING
BLOCKED
READY
STARTING
RUNNING
SUCCEEDED
FAILED
CANCELLED
SKIPPED
UNKNOWN
```

A Task can be `RUNNING` while some steps are `SUCCEEDED`, another is `RUNNING`, and later steps are `BLOCKED`.

The Task Manager derives/validates Task-level transitions from these records and semantic-program requirements.

## Execution attempt identity

Every provider attempt has stable:

```text
attempt_id
binding_id
task_id
semantic_program_hash
node_id
attempt_number
```

Side-effecting operations also have stable `operation_id`/idempotency identity before the effect starts.

Retries create new attempt records. They do not overwrite failed/unknown attempts.

## External effect certainty

The execution record tracks an outcome-certainty state sufficient for recovery:

```text
NOT_STARTED
STARTED_NO_EFFECT
COMPLETED
FAILED_NO_EFFECT
FAILED_PARTIAL_EFFECT
OUTCOME_UNKNOWN
```

An `OUTCOME_UNKNOWN` irreversible/external operation blocks blind retry/completion until reconciliation/policy resolves it.

A model cannot change `OUTCOME_UNKNOWN` to `COMPLETED` merely by inference.

## Waiting/blocker identity

`WAITING_FOR_INPUT` and `WAITING_FOR_AUTH` are not generic UI labels.

The Task current record must retain structured blocker IDs such as:

```text
input request ID
approval request ID
resource/provider blocker ID
validation blocker ID
```

Resolving a blocker is itself a deterministic state mutation/precondition check.

The transition mutation's `waiting_on.kind` vocabulary is the same as the Task
record vocabulary, including `validation`. SQLite persists current blocker and
step identities in `tasks.waiting_on_json` and `tasks.active_step_ids_json`;
`active_plan_revision` resolves the selected plan through `plan_revisions`.

## Plan/program revision relationship

A Task can have multiple planner proposals/semantic program revisions over time.

Only one validation-approved semantic program revision is active for execution at a time.

Replanning:

- never mutates historical semantic-program records in place;
- produces a new program revision/hash/validation evidence;
- invalidates stale unstarted Execution Bindings as appropriate;
- does not erase prior attempt/provenance history.

The Task transition revision and semantic-program revision are different counters/identities.

The trusted local replacement admission for an approval-blocked Task is a
single `WAITING_FOR_AUTH → PLANNING` transaction. It requires the exact Task
revision, an active coherent plan/program with authenticated validation, no
binding, grant, attempt, protected allocation, or protected operation, and a
currently admitted registry snapshot. A completed unbound source import is
permitted only when its keyed operation, immutable receipt, Artifact, and
hash-chained provenance event authenticate as one import. NULL or forged
operation fields block revision. The manager validates the new raw program against that registry and
checks the new plan against it before changing either active pointer. The
ordinary transition guard's old-program coherence check is bypassed only for
this trusted replacement; the ordinary executable paths still require current
active validation and coherence.

The transaction marks every pending old authority candidate `STALE` under its
status revision check, marks their pending approval requests `STALE` while
retaining already approved requests and all decision bytes, marks the
old plan/program superseded, writes new plan/program/validation revisions,
clears approval-wait markers, advances the Task revision once, and appends the
transition provenance event. Reuse of the same transition ID with different
raw plan/program bytes, registry snapshot, expected Task revision, or
operation kind conflicts. An exact replay returns its committed receipt even
after subsequent revisions; old candidate status is never restored by an
A→B→A semantic-hash return.

## Cancellation vs process kill

Cancellation means a semantic/control-plane operation, not merely killing PIDs.

The provider supervisor may kill/cancel processes after Task Manager commits/adopts the cancellation path, but Task state/provenance remains the source of lifecycle truth.

## Crash recovery

Startup recovery runs only after exclusive store ownership and fencing are
established. The same trusted recovery coordinator may start reconciliation
while the daemon remains live when durable/provider evidence becomes uncertain.
It uses a private, non-serializable entry point rather than the public
`TransitionRequest` API.

Before uncertain-execution recovery, startup retires exact, unused coordinator
grants from an older clock session. A `RUNNABLE` or approval-backed
`WAITING_FOR_AUTH` Task with no evidence of protected use follows its normal
CAS edge to `PLANNING`; the old candidate and attempt remain immutable history.
A completed, unbound Artifact import does not count as use of this candidate.
A possible effect or incomplete issuance cannot be called unstarted merely
because the attempt is READY, and automatic replanning stops. Actual uncertain
running work still enters the ordinary recovery path.

The entry point:

- accepts only a current `RUNNING`, `VERIFYING`, or `PAUSED` Task;
- requires the exact current Task revision and store fencing epoch;
- derives attempt/operation/publication/grant evidence from durable trusted
  records and provider status mechanisms itself;
- rejects caller-supplied evidence/classifications as authoritative; and
- commits the `RECOVERING` transition, assessment references, and provenance
  through the normal CAS transaction.

It MUST NOT be exposed by recognizing a `requested_by` actor string, a reserved
transition-ID prefix, an internal-looking principal ID, or a caller-provided
boolean. Those values can be forged at a serialization/API boundary.

On control-plane startup:

1. load all nonterminal Tasks;
2. verify/reconcile Task current revision with provenance stream head;
3. move only uncertain `RUNNING`/`VERIFYING`/`PAUSED` Tasks into `RECOVERING` through the private coordinator entry;
4. inventory every recovery subject: attempts/bindings, external operations, Artifact allocations/publications, grants/approvals, and credential uses where relevant;
5. derive one evidence-backed certainty assessment for each subject independently;
6. verify committed Artifact hashes/publication markers and provider status evidence;
7. expire invalid grants;
8. determine safe target state (`RUNNABLE`, blocker state, `PAUSED`, `FAILED`, `ROLLING_BACK`);
9. append recovery provenance; never rewrite pre-crash history.

Task-level state is the conservative aggregate of the per-subject assessments.
Evidence for one attempt, operation, or Artifact cannot prove the outcome of a
different subject. An absent row/receipt, unreachable provider, present blob, or
Task state alone is not optimistic proof that work never started or completed.
If the evidence for any consequential subject is insufficient, that subject is
`OUTCOME_UNKNOWN` and blind retry remains blocked.

## Single-writer rule

v0.1 requires one kernel-locked, durably fenced local Task-state
writer/transaction coordinator for each store.

Multiple async workers may execute providers, but they report results through the Task Manager with expected revisions/attempt identities.

Do not add distributed consensus/leases to v0.1 solely for theoretical future scale.

```text
TASK_ILLEGAL_TRANSITION

```

Human messages remain separate.

## Acceptance tests

At minimum:

1. legal transition succeeds and revision increments once;
2. `CREATED -> COMPLETED` rejected;
3. stale expected revision rejected with no provenance append;
4. wrong expected state rejected;
5. same transition ID retry returns prior outcome without duplicate event;
6. same transition ID with different payload rejected;
7. Task transition + provenance append commits atomically;
8. simulated provenance insertion failure rolls back Task mutation;
9. terminal `COMPLETED` cannot reopen;
10. `FAILED -> ROLLING_BACK` only with explicit compensation guard;
11. completion denied while verification pending/failed;
12. completion denied while required external operation is `OUTCOME_UNKNOWN`;
13. cancellation stops scheduling admission and records unresolved active effects;
14. control-plane restart moves uncertain running Task through recovery;
15. concurrent writers using same revision result in one winner and one conflict;
16. model/provider cannot directly update Task record through public API;
17. prior semantic program/attempt records remain immutable across replan;
18. recovery does not blindly retry unknown irreversible effect;
19. a second process cannot migrate, recover, or mutate a store while its kernel-held owner lock remains live, including when it opens the same file through an alternate path alias;
20. every mutation with a stale `store_fencing_epoch` rolls back, including maintenance/migration paths;
21. Task creation persists a fresh 32-byte nonce privately and provenance contains only the doc-73 v1 commitment;
22. public recovery requests fail even with trusted-looking actor IDs, transition-ID prefixes, or booleans;
23. the private live coordinator accepts only `RUNNING`, `VERIFYING`, or `PAUSED` and derives evidence rather than accepting a claimed certainty;
24. mixed subject evidence produces separate assessments, and one unknown consequential subject blocks optimistic Task-level retry.

## Principle

> **Task current state is a deterministically guarded materialized view over durable semantic execution facts—not a status string any worker may overwrite.**
