# 17 — v0.1 Acceptance and Test Plan

The v0.1 prototype is successful only if the architecture can be demonstrated and tested. A visually impressive assistant that bypasses the contracts below does not satisfy v0.1.

## Test environment

Initial reference environment:

- x86_64 Linux host;
- one deterministic local provider set for file/table/chart/report operations;
- one local model adapter;
- one optional remote model adapter;
- container/sandbox support;
- SQLite or equivalent embedded state/provenance store;
- Windows compatibility habitat for Demonstration B;
- synthetic/non-sensitive test data.

Exact distro, model, UI toolkit, and IPC mechanism are intentionally not release requirements yet.

## Demonstration A — Task-first data analysis

User intent:

> Understand these numbers, identify important changes, create a chart and a concise report, and save the result.

### A1 — Task creation

**Given** a CSV or XLSX input,
**when** the user submits the intent,
**then** the system creates a stable task ID and records the original intent.

Pass criteria:

- task ID exists;
- input is referenced by an artifact/data handle;
- original user text is retained;
- no spreadsheet application is manually launched by the user.

### A2 — Typed planning

The planner must produce a typed graph whose steps resolve to declared capabilities.

Pass criteria:

- graph validates against the task-plan schema;
- unknown capabilities fail closed;
- malformed provider/model output cannot enter execution directly.

### A3 — Least authority

The task receives read authority to the selected input and write authority to a task-local output location only.

Pass criteria:

- attempting to read an unrelated protected test file is denied;
- attempting to write outside the allowed output area is denied;
- denial is represented in provenance;
- the planner cannot broaden its own grant.

### A4 — Provider substitution

At least one capability must have two conforming providers.

Pass criteria:

- changing policy/provider priority switches the selected provider;
- task semantics remain valid;
- resulting provider choice is visible in provenance.

### A5 — Deterministic calculations

Numerical calculations used in the report must be produced or independently checked by a deterministic provider.

Pass criteria:

- fixture dataset has known expected totals/statistics;
- verifier detects an intentionally injected incorrect model claim;
- incorrect values do not silently become final report facts.

### A6 — Artifact production

The task must produce at least:

- one chart image or vector artifact;
- one concise report artifact;
- one machine-readable analysis artifact containing key computed values.

Pass criteria:

- artifacts are ordinary portable formats;
- each artifact has a stable handle and content hash when practical;
- lineage links outputs to input and producing steps.

### A7 — Provenance inspection

The user/developer can inspect:

- task creation;
- plan revisions;
- capability/provider selections;
- authorization decisions;
- model calls;
- external data transfers, if any;
- produced artifacts;
- verification;
- completion/failure.

### A8 — Local/remote policy routing

If a remote provider is configured, policy can force the same eligible reasoning step local or remote.

Pass criteria:

- local-only mode causes no remote network transfer for protected task data;
- remote mode records provider identity and egress metadata;
- absence of a remote provider does not prevent deterministic task execution when local capabilities are sufficient.

### A9 — Planner failure containment

Inject planner failure cases:

- invalid JSON/typed output;
- unknown capability;
- request for unauthorized path;
- attempt to invoke shell arbitrarily;
- contradictory steps;
- excessive/repeated planning.

Pass criteria:

- no case bypasses deterministic authorization;
- task transitions to recoverable failure/clarification state rather than corrupting host state.

### A10 — Reusable procedure

Execute the same task pattern repeatedly with structurally similar inputs.

Pass criteria:

- system can identify a reusable plan pattern;
- a skill/procedure artifact can be created explicitly;
- subsequent execution can reuse deterministic portions;
- the saved skill still undergoes current policy checks.

## Demonstration B — Legacy application routing

Initial practical target: one Windows application that is legally redistributable or user-supplied and works through a mature Windows-on-Linux compatibility environment.

### B1 — Package inspection

Pass criteria:

- broker identifies package/binary family and CPU architecture;
- unsupported/unknown types fail safely;
- inspection does not execute the package.

### B2 — Habitat selection

Pass criteria:

- broker chooses a named Windows compatibility habitat;
- the choice and compatibility profile are inspectable;
- user is not required to manually configure the compatibility layer for the known fixture.

### B3 — Sandboxed launch

Pass criteria:

- application launches successfully;
- filesystem access is limited to assigned test resources;
- network policy is applied;
- host secrets are unavailable unless explicitly granted.

### B4 — Failure mode

Provide an intentionally incompatible or malformed fixture.

Pass criteria:

- failure is reported as a compatibility result rather than a generic OS crash;
- host remains intact;
- relevant diagnostics are retained.

## Hardware/resource tests

### H1 — Hardware profile

Pass criteria:

- CPU architecture, logical cores, RAM, storage availability, and detectable accelerator metadata are represented in a structured hardware profile;
- missing accelerator support does not make the profile invalid.

### H2 — Constrained profile simulation

Run with artificial resource limits.

Pass criteria:

- broker changes provider/placement selection or reports a bounded inability;
- task identity and security policy remain unchanged.

## Recovery tests

### R1 — Provider crash

Kill a provider during task execution.

Pass criteria:

- task records failure;
- broker may retry or select an alternate provider according to policy;
- completed prior artifacts are not silently misrepresented as complete task output.

### R2 — Control-plane restart

Restart the prototype control-plane process during a persisted task.

Pass criteria:

- task state and provenance can be recovered from durable storage;
- task is marked recoverable/paused/failed consistently.

## Security regression fixtures

The v0.1 test suite should include at least these adversarial fixtures:

1. prompt injection embedded in a CSV cell;
2. prompt injection embedded in document metadata;
3. provider requests unrelated filesystem access;
4. provider attempts network egress in local-only mode;
5. model returns executable shell text instead of the required schema;
6. legacy application attempts to read a host-only test secret;
7. stale or expired capability token;
8. capability token for the wrong task;
9. artifact hash mismatch;
10. malicious/invalid capability manifest.

## v0.1 release gate

v0.1 is not complete until:

- Demonstration A passes A1–A10;
- Demonstration B passes B1–B4 for one known fixture;
- H1–H2 and R1–R2 pass;
- all security regression fixtures fail safely;
- a fresh developer can reproduce the demo from repository instructions;
- architecture documentation is updated to match the implemented contracts rather than describing an imaginary future system.
