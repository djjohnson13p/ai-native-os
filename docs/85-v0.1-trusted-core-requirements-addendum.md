# 85 — v0.1 Trusted-Core Requirements Addendum

## Purpose

`docs/16-requirements.md` defines the broad architecture requirement families. During Stage-0 closure, the Task/Artifact/Authority/Credential/Provider/Recovery contracts became precise enough that several trusted-core requirements deserve stable IDs of their own.

This addendum is normative for the v0.1 trusted-core implementation and is incorporated by reference into the traceability/acceptance gates.

It does not replace `docs/16`; it narrows the implementation-sensitive guarantees discovered after the original requirements document expanded to cover the wider platform fabrics.

Status meanings remain:

- **MUST** — required for the trusted-core architecture to be valid;
- **SHOULD** — strong default, change only by explicit architecture decision;
- **MAY** — optional capability.

## Artifact publication

### R-ART-001 — Published Artifact immutability

Once an Artifact content instance is published with a content identity, its bytes/content hash MUST NOT be mutated in place. Changed content creates a new Artifact/content instance with lineage.

### R-ART-002 — Staging is not publication

Partial/staging bytes or an orphan content blob MUST NOT be exposed as a published Task output until trusted publication metadata/integrity checks commit successfully.

### R-ART-003 — Output allocation confinement

A provider MUST be able to write only through output allocations explicitly bound to its current Task/node/attempt. It MUST NOT choose arbitrary host output paths as a trusted-core behavior.

### R-ART-004 — Idempotent publication

Artifact finalization/publication MUST have a stable idempotency identity so response loss after committed publication does not duplicate the Artifact or rerun the provider solely to reconstruct the response.

### R-ART-005 — Artifact integrity before downstream use

When a content hash/integrity requirement exists, downstream trusted execution MUST reject or recover rather than consume a missing/corrupt/mismatched published blob as valid input.

## Authority Coordinator

### R-AUTH-001 — Semantic request is an upper bound on runtime authority

A runtime Authority Evaluation Request MUST derive from a validated semantic authority request/effect context and MUST NOT introduce a protected action absent from the validated semantic program/contract envelope.

### R-AUTH-002 — Concrete principal/action/resource evaluation

Policy MUST evaluate a concrete principal, action, resource, Task/program/node/binding context—not only a broad capability name or user login state.

### R-AUTH-003 — Deny precedence and default deny

Unknown/unmapped protected actions/resources, explicit denies, stale approvals, or policy-engine uncertainty MUST fail closed. An approval record MUST NOT override an explicit hard policy deny unless an explicit higher-order policy model defines that behavior.

### R-AUTH-004 — Structured trusted approval

Approval for consequential actions MUST bind to structured trusted facts including Task, semantic program/node, action, resolved resource, provider/workload principal, and destination/effect facts where relevant. Provider/model prose MUST NOT be the authoritative approval statement.

### R-AUTH-005 — Durable grant / opaque token separation

Authoritative scope, expiry, usage, delegation, policy-decision, and approval linkage MUST live in a durable grant record. Runtime bearer/token material SHOULD be opaque/out-of-band and MUST NOT be treated as the durable source of grant semantics.

### R-AUTH-006 — Point-of-use grant validation

Trusted brokers/resources MUST validate current grant state/scope/principal/Task/binding/expiry/usage at the protected operation boundary. Launch-time validation alone is insufficient.

### R-AUTH-007 — Network connectivity and data egress are distinct

Permission to establish a network connection MUST NOT by itself authorize Task/user data egress. Data egress requires its own semantic authority/policy treatment.

### R-AUTH-008 — Rebinding does not inherit old provider authority

Changing provider, binding, destination, semantic program, or materially scoped resource MUST trigger fresh authority/approval evaluation where the prior grant no longer exactly applies.

## Credential mediation

### R-CRED-001 — Raw long-lived secrets outside normal control-plane records

Raw passwords, API keys, refresh tokens, private-key bytes, session cookies, or equivalent long-lived secret material MUST NOT be stored in AIOS IR, Task records, normal provenance, provider manifests, ordinary logs, or Authority Grant records.

### R-CRED-002 — Credential handle is not permission

Possession of a credential handle MUST NOT authorize credential use. Current matching Task/provider/binding authority is independently required.

### R-CRED-003 — Brokered use preferred over export

When an external ecosystem permits it, AIOS SHOULD perform a brokered operation or issue a narrower short-lived delegated credential rather than exposing the source long-lived secret to a provider.

### R-CRED-004 — Exportability follows placement

A credential marked non-exportable/local-restricted MUST remain so when execution moves to peer/remote providers. Resource placement MUST NOT silently weaken credential exportability.

### R-CRED-005 — Delegation is non-amplifying

A delegated credential/token/session MUST have scope/lifetime no broader than the intersection of source credential capability, current Authority Grant, provider principal, destination/service, and requested operation.

### R-CRED-006 — Secret-use failure is fail-closed

Expired/revoked handle, secure-store outage, scope/service mismatch, stale approval, wrong Task/provider/binding, or unavailable credential MUST fail closed rather than asking a model/provider to reconstruct or substitute secret material.

## Execution Binding / Provider Supervisor

### R-EXEC-001 — Immutable Execution Binding

Once an attempt starts, its provider/build, inputs, output allocations, grants, execution profile, placement, and attempt identity MUST NOT be mutated in place. Material runtime changes require a new attempt and Execution Binding.

### R-EXEC-002 — Exact provider/build attribution

Every material provider attempt MUST identify the concrete provider version plus immutable package/build/component identity where available.

### R-EXEC-003 — No shell-as-core provider ABI

The trusted provider-execution path MUST NOT execute arbitrary model/planner-generated shell command strings as its generic provider ABI. Registered entry points/components use typed invocation contracts under bounded execution profiles.

### R-EXEC-004 — No ambient provider authority

Provider execution MUST default to no unrelated filesystem, network, secret, device, clipboard, desktop-session, or user-environment authority. Interfaces are allowlisted/bound explicitly.

### R-EXEC-005 — Typed structured provider result

Provider process exit status/stdout/stderr MUST NOT alone determine semantic success. The Provider Supervisor MUST validate the structured result against the expected invocation/capability contract.

### R-EXEC-006 — Semantic failure distinct from runtime failure

The runtime MUST distinguish a declared capability/semantic failure from provider process/runtime/protocol failure for retry, fallback, diagnostics, and provenance.

### R-EXEC-007 — Output publication independent from provider exit

Provider success MUST NOT expose output until the trusted Artifact Store finalizes the bound output allocation successfully.

### R-EXEC-008 — Deadline/cancellation/revocation enforceable

A provider attempt MUST be bounded by explicit timeout/cancellation/resource policy, and protected access after Task cancellation/grant revocation MUST be denied at point of use.

### R-EXEC-009 — Provider substitution creates new history

Retry with another provider/build/placement MUST create a new attempt/binding and preserve the prior attempt/result rather than rewriting it.

## Crash consistency / recovery

### R-REC-001 — Persist attempt/operation identity before effect

Before starting a protected or externally observable operation, the system MUST persist enough stable attempt/operation identity and binding context to recognize/reconcile it after restart.

### R-REC-002 — Durable evidence before success claim

A Task/node/output MUST NOT be reported complete until the durable evidence required by its contract (result/publication/verification/provenance/state) has committed.

### R-REC-003 — Explicit outcome certainty

Recovery MUST distinguish at least `NOT_STARTED`, `STARTED_NO_EFFECT`, `COMPLETED`, `FAILED_NO_EFFECT`, `FAILED_PARTIAL_EFFECT`, and `OUTCOME_UNKNOWN` where applicable.

### R-REC-004 — Unknown outcome is not retry permission

An `OUTCOME_UNKNOWN` irreversible/opaque external operation MUST NOT be blindly retried until deterministic reconciliation/idempotency/status evidence proves another attempt safe or explicit higher-level handling resolves it.

### R-REC-005 — Idempotent local commit identities

Task transitions and Artifact publications MUST use stable request/transition/publication identities so a committed operation followed by response loss can return/reconcile the prior result without applying the state change twice.

### R-REC-006 — Grant consumption survives response loss/restart

When a trusted resource operation durably consumes a one-shot/bounded grant, loss of the response or process restart MUST NOT restore the consumed authority.

### R-REC-007 — Recovery revalidates mutable facts

Retry/resumption after restart MUST revalidate current Task state, inputs/revisions, provider eligibility, policy/grants/approvals, output/publication state, and semantic failure budget as relevant.

### R-REC-008 — Recovery preserves history

Recovery MUST append reconciliation/state evidence; it MUST NOT delete or rewrite prior failure/uncertainty/provenance to present a cleaner narrative.

### R-REC-009 — Local deterministic recovery works without AI

Purely local trusted-core recovery/reconciliation MUST be possible without a functioning model planner or network service.

### R-REC-010 — Recovery entry is a private trusted capability

Only the trusted recovery coordinator may move a live Task from `RUNNING`,
`VERIFYING`, or `PAUSED` into `RECOVERING`. The public transition API MUST reject
that target. Actor strings, internal-looking IDs, transition-ID prefixes, and
caller-provided booleans MUST NOT confer coordinator authority. The coordinator
MUST derive recovery evidence rather than accept a caller's claimed certainty.

### R-REC-011 — Recovery certainty is evidence-based per subject

Recovery MUST assess each attempt/binding, external operation, Artifact
publication, grant, or other consequential subject from evidence bound to that
exact subject. Missing, conflicting, stale, or cross-subject evidence MUST NOT
support optimistic `NOT_STARTED`, no-effect, or completion inference. Any
insufficiently proved consequential outcome remains `OUTCOME_UNKNOWN` and blocks
blind retry/completion.

## Persistence / transaction integrity

### R-PERSIST-001 — Single-owner trusted metadata writes

Untrusted providers/models/legacy applications MUST NOT write the trusted control-plane database directly.

### R-PERSIST-002 — Material Task transition + provenance atomicity

Where both records share one local transactional database, a material Task state transition and its required provenance record SHOULD commit/rollback together.

### R-PERSIST-003 — SQLite/filesystem boundary is explicitly recoverable

The Artifact Store MUST NOT assume database ACID makes filesystem/blob writes atomic. Staging/blob placement/metadata publication MUST follow a crash-recoverable protocol.

### R-PERSIST-004 — Released historical records are not rewritten for convenience

Historical semantic registry snapshots, Execution Bindings, published Artifact content identity, provenance events, and committed transition/publication identities MUST be treated as immutable/auditable according to their contracts.

### R-PERSIST-005 — Exclusive store owner with durable fencing

A writable local trusted store MUST be held by one kernel-enforced exclusive
owner before migration or recovery begins. Ownership acquisition MUST advance a
durable monotonic fencing epoch, and every mutation MUST verify the caller's
held epoch against the durable current epoch at commit. Lock contention or a
stale/missing/unadvanceable epoch fails closed.

### R-PERSIST-006 — Private, nonce-bound creation-intent commitment

Every new Task MUST use a fresh per-Task 256-bit OS-CSPRNG nonce to bind its
private creation intent to a versioned commitment. The nonce and raw intent MUST
remain private trusted-store data; provenance and export contain only the
versioned commitment. Legacy raw-intent events remain immutable but fail the
current typed provenance verification gate and MUST NOT enter normal portable
export. An eligible legacy stream whose immutable creation event already has a
valid typed commitment MAY use the explicitly marked privacy-redacted projection
after the original chain and private Task row verify. Missing/malformed or
mismatched commitment state quarantines the Task rather than inventing proof.

## Principle

> **The trusted core is successful only if semantic meaning, authority, execution, durable output, and recovery remain separate enough that failure or compromise in one cannot silently redefine the others.**
