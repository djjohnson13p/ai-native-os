# 72 — v0.1 Semantic Contract and Registry Snapshot Hash Profile

## Purpose

Issue #17 records an immutable Registry Snapshot identity and replaces the checked-in AIOS IR fixture placeholders with generated semantic contract and snapshot identities.

A raw-file hash is insufficient as the only semantic identity because whitespace, object-key order, descriptions, notes, and set ordering should not redefine a semantic contract.

This document defines the v0.1 bootstrap content-hash profiles for:

```text
Semantic Capability Contract
Semantic Type Contract
Semantic Registry Snapshot
```

These identities are separate from AIOS IR semantic-program hashing, provider-package hashes, and publisher signatures.

## Design goals

The profiles MUST be:

- deterministic across conforming implementations;
- independent of JSON formatting/object-key order;
- insensitive to explicitly non-semantic prose;
- sensitive to fields that alter semantic validation/conformance expectations;
- independent of publisher signature/timestamp/catalog location;
- domain separated from Artifact/package/IR hash namespaces;
- reproducible offline from local validated contract bytes.

## Shared pipeline

```text
strict parsed contract/snapshot record
    ↓ structural + semantic consistency validation
normalized semantic content view
    ↓ RFC 8785 JCS canonical JSON
canonical bytes
    ↓ domain-separated SHA-256
algorithm-tagged semantic content ID
```

Invalid contract/snapshot records receive no trusted semantic content ID.

## Capability contract semantic-content profile

### Included fields

Include all execution/conformance-relevant fields:

```text
capability
version
role
inputs (names, semantic type refs, required flags)
outputs (names, semantic type refs, required flags)
allowed_execution_classes
required_effect_classes       # once ADR 0033 structural migration is applied
allowed_effect_classes
required_authority_classes    # once ADR 0033 structural migration is applied
allowed_authority_classes
allowed_egress_modes
determinism/equality/tolerance semantics
error_classes
conformance suite identity/version/hash
```

### Excluded fields

Exclude:

```text
description
notes
```

These are human explanatory prose and may improve without changing the contract's semantic content identity.

If future contract metadata is added, it is excluded by default unless an ADR explicitly classifies it as semantic.

### Set ordering

Normalize these arrays as semantic sets by lexicographic canonical string ordering:

```text
allowed_execution_classes
required_effect_classes
allowed_effect_classes
required_authority_classes
allowed_authority_classes
allowed_egress_modes
error_classes
```

Named input/output ports are JSON objects and canonicalized by JCS property ordering.

### Port description

Port `description` is excluded from the semantic-content view.

Port `type` and `required` are included.

## Type contract semantic-content profile

### Included fields

Include:

```text
type_id
version
kind
logical_schema_ref
nullable
representations (minus explanatory-only metadata if later added)
equality/canonicalizer/tolerance semantics
unit_semantics
conversion_capabilities
conformance suite identity/version/hash
```

### Excluded fields

Exclude:

```text
description
notes
```

### Representation ordering

`representations` are a semantic set for v0.1 and are sorted by representation `id` before JCS serialization.

Within a representation include:

```text
id
media_type
schema_ref
zero_copy_candidate
```

`zero_copy_candidate` participates because it is currently part of the type contract's declared representation behavior/optimization eligibility. If implementation shows this should be provider/runtime metadata instead, change the contract/profile explicitly rather than silently excluding it.

### Conversion ordering

`conversion_capabilities` is a semantic set and sorted lexicographically.

## Referenced schema/profile content

`logical_schema_ref`, representation `schema_ref`, and conformance-suite hashes must not cause trusted validation to fetch mutable network resources.

For v0.1:

- a `*_ref` is an identifier/path reference only;
- if the referenced content affects trusted semantic validation, the surrounding contract/snapshot must also carry or resolve a locally available immutable content hash/profile before relying on it;
- a URL alone is not trusted semantic content.

Bootstrap fixtures may leave these refs null where not needed.

A later contract revision may replace raw refs with explicit content-addressed descriptors.

## Capability/type contract hash domain separation

Conceptual domain prefixes:

```text
AIOS-CAPABILITY-CONTRACT\0v0.1\0<JCS bytes>
AIOS-TYPE-CONTRACT\0v0.1\0<JCS bytes>
```

The exact byte sequences are centralized in the trusted library and locked by test vectors.

Stored identifiers use:

```text
sha256:<lowercase hex>
```

and MUST NOT infer algorithm from digest length.

## Registry Snapshot semantic identity

A Registry Snapshot identity represents the exact selected semantic contract set used for validation.

The normalized snapshot hash view includes:

```text
snapshot format/profile version
type contract entries:
  type_id
  full contract version
  semantic contract hash
capability contract entries:
  capability ID
  full contract version
  semantic contract hash
```

It excludes distribution/provenance labels such as:

```text
human snapshot name/label
creation timestamp
publisher display name
signature bytes
catalog/mirror URL
local file path
```

Those can be stored next to the snapshot identity.

### Entry ordering

Sort entries deterministically:

```text
types        by (type_id, parsed full version, contract hash)
capabilities by (capability_id, parsed full version, contract hash)
```

Because v0.1 enforces at most one active contract per `(ID, major)`, ordering does not perform semantic version selection. Selection already occurred during snapshot construction.

### Snapshot domain separation

Conceptual prefix:

```text
AIOS-SEMANTIC-REGISTRY\0v0.1\0<JCS bytes>
```

The resulting `registry_snapshot_id` is algorithm tagged.

## Snapshot label vs identity

A human/tool label such as:

```text
bootstrap-demo-a-2026-09
```

is not exact identity.

Multiple labels/publishers/mirrors can distribute the same snapshot ID.

A new contract selection/content hash creates a new snapshot ID even if the human label is reused incorrectly.

## Contract hash verification

When loading a snapshot bundle with generated hashes:

1. strictly parse each contract;
2. validate structural + registry semantic consistency;
3. compute its normalized semantic contract hash;
4. compare to snapshot entry hash;
5. reject mismatch before using the contract;
6. enforce one `(ID, major)` entry;
7. compute normalized Registry Snapshot ID;
8. compare to declared snapshot ID when supplied;
9. freeze immutable in-memory indexes for program validation.

Reason-code families:

```text
REGISTRY_CONTRACT_HASH_MISMATCH
REGISTRY_SNAPSHOT_HASH_MISMATCH
```

## Generated fixture rule

The checked-in `examples/aios-ir/` capability contracts, type contracts, and Registry Snapshot carry generated semantic identities. Strict mode requires every declared contract hash and snapshot ID to match the locally recomputed value exactly.

An explicit `BootstrapGenerate` mode remains available only as non-production development/test tooling for computing identities from deliberately marked placeholder inputs. Registries built in that mode remain marked non-strict and cannot produce an executable semantic-program identity through the validator.

Production/trusted validation MUST NEVER accept a placeholder sentinel as evidence.

## Hash equality tests — capability contract

Hash MUST remain equal when only:

- JSON whitespace/key order changes;
- `description` changes;
- `notes` change;
- port descriptions change;
- semantic-set array order changes.

Hash MUST change when any included semantic field changes, including:

- capability/version/role;
- port type/required state;
- execution class envelope;
- required/allowed effect or authority envelope;
- egress modes;
- determinism/tolerance;
- error class set;
- conformance suite identity/hash.

## Hash equality tests — type contract

Hash MUST remain equal for prose/set-order differences.

Hash MUST change for:

- ID/version/kind;
- nullability;
- logical schema identity;
- representation contract;
- equality/tolerance/canonicalizer;
- unit semantics;
- conversion capability set;
- conformance suite identity/hash.

## Hash equality tests — registry snapshot

Snapshot ID MUST remain equal when only:

- entry array authoring order changes;
- human label changes;
- creation timestamp changes;
- publisher/signature/catalog/mirror metadata changes.

Snapshot ID MUST change when:

- a selected contract version changes;
- a semantic contract hash changes;
- a contract entry is added/removed;
- snapshot profile version changes.

## Relationship to AIOS IR semantic hash

Do **not** include Registry Snapshot ID in the AIOS IR semantic-program hash.

Use both identities when exact validated interpretation matters:

```text
SemanticProgramKey {
  semantic_program_hash
  registry_snapshot_id
  ir_version
  semantic_hash_profile
}
```

Compiled targets/Skills/cache entries may add target/compiler/provider identities as additional keys.

This allows the same semantic-family program to retain its program hash across compatible registry snapshots while keeping exact validation interpretation reproducible.

## Relationship to signatures

Publisher signatures should sign a structured statement containing the generated semantic contract/snapshot ID and profile/version, not prettified source JSON.

Signature identity remains separate:

```text
semantic content hash -> what content is this?
publisher signature    -> who attested/published it?
policy/trust            -> do we accept it for this purpose?
```

## Relationship to package hashes

A component/provider package hash identifies implementation bytes/package metadata.

It is not the same as:

- semantic capability contract hash;
- type contract hash;
- registry snapshot ID;
- AIOS IR semantic-program hash.

One provider package may implement multiple semantic contracts; many packages may implement the same contract.

## Required implementation ownership

The trusted implementation should centralize:

```text
capability contract semantic-view normalization/hash
type contract semantic-view normalization/hash
registry snapshot normalization/hash
AIOS IR semantic-view normalization/hash
```

behind distinct domain-separated functions/types.

Never pass around generic `sha256:String` where the code can cheaply distinguish `ProgramHash`, `CapabilityContractHash`, `TypeContractHash`, `RegistrySnapshotId`, and `PackageHash` at the type level.

## Principle

> **Content-address every semantic layer in its own domain: program meaning, contract meaning, registry selection, and implementation bytes are related—but they are not the same identity.**
