# 78 — v0.1 Execution Binding and Provider Supervisor Lifecycle

## Purpose

After AIOS IR is validated, policy is satisfied, and a provider/resource candidate is selected, the system still needs one deterministic boundary that turns an abstract semantic node into one concrete execution attempt.

That boundary is the **Execution Binding + Provider Supervisor**.

The key separation is:

```text
AIOS IR node            = what the operation means
Semantic contract       = what implementations must satisfy
Policy/grant            = what this exact principal may do
Execution Binding       = which exact provider/resources/grants this attempt uses
Provider Supervisor     = launches/monitors the provider under those bounds
Provider result         = what this attempt observed/produced
```

The supervisor is not a planner, policy engine, semantic validator, or application launcher with ambient user authority.

## v0.1 goals

The first implementation must prove that one deterministic provider can execute one validated node while receiving only explicitly bound resources and authority.

It must support:

- immutable attempt-specific binding;
- exact provider/build attribution;
- scoped input handles and output allocations;
- point-of-use authority validation;
- explicit execution/isolation profile;
- deadline/cancellation;
- crash-safe output publication;
- stable result/failure classes;
- complete provenance linkage;
- safe provider substitution through a **new** binding.

## Binding creation prerequisites

A binding may be created only when all required facts exist:

```text
validated semantic program + registry snapshot
Task in eligible state
resolved semantic capability contract
selected registered/conforming provider
selected conformance evidence ID pinned in the immutable binding receipt
resolved input Artifact/value handles
reserved output allocations
eligible placement/resource decision
execution/isolation profile
current policy decisions/approvals
current scoped grant references
attempt number
```

If any mandatory fact is unknown, the node remains unbound.

## Execution Binding immutability

Once an attempt starts, the binding is immutable.

For Stage-1 provider admission, the binding receipt pins the selected conformance evidence ID, the exact non-null capability-contract, provider-manifest, and build hashes, and the `provider_trust_source_id` that authorized this attempt. Durable insert guards require the exact registration ID, provider ID/version, non-null manifest/build projections, and matching required provider fields in the public binding JSON before an immutable binding identity can be consumed. The complete required receipt must also match the durable attempt, task, semantic program, selected snapshot, node, capability, policy, grants, execution profile, placement, attempt number, and creation time; a mismatch fails at insertion rather than leaving a permanently unusable attempt. The guards reject a missing or mismatched evidence or trust pin and require the pinned evidence suite to match the immutable provider manifest. The provider must already be enabled, and the evidence and trust decision must exist and be effective no later than the binding creation time. Expiring evidence must remain valid strictly after that creation instant; equality is expired. At launch, the pinned evidence ID must still be the latest valid result for the exact provider build, capability contract, and suite. A newer pass or failure requires a new attempt and binding; historical receipts retain their original evidence ID for audit.

The insertion guard and launch use the same bounded, strict Rust receipt parser and exact typed column projection. Versioned SQLite functions expose only the validated binding match and exact evidence/trust pins to the relational guards; SQLite JSON1 key extraction does not decide receipt identity. A direct SQLite writer without those registered functions cannot insert a binding. This prevents JSON key, integer, and parser differences from consuming a binding ID that launch would later reject.

The selected conformance result is also checked with one bounded, schema-validated Rust projection at provider ingestion, binding insertion, candidate selection, and launch. It binds the result payload to the exact provider build, capability major and full contract version, suite ID/version/hash, pass counts, evidence ID, status, and execution time. RFC 3339 instants, including offsets and nanoseconds, determine creation-time expiry and latest-result order. Malformed retained evidence cannot consume a new binding identity, and previously admitted bindings with invalid retained evidence fail closed at launch.

When an older stamped store is upgraded to the write-time evidence, trust, or provider enablement guard, bindings that predate the guard and their original markers are retained for audit. They are recorded in an immutable quarantine table and cannot authorize a new launch. Recovery creates a new attempt and binding so evidence, trust, and enabled state are proven at insertion. A semantic admission guard repair appends an immutable `0014` repair-fence generation. Formerly ADMITTED/DEPRECATED snapshots keep their primary state but cannot authorize executable work until a trusted owner-bound strict re-attestation records a fresh decision/source for that generation. Old binding markers remain permanently quarantined; a new attempt and binding are required after re-attestation. Terminal snapshots and historically unprovable pre-`0014` admissions cannot be re-attested. `0014` retains every activation scope identity observed since healthy bootstrap; repair invalidates the whole history, including deleted or renamed rows whose CAS revisions may have been rolled back. A new scope can be activated after recovery only when that history is complete. If activation guards were already missing before the first `0014` bootstrap, the store cannot know which scope identities vanished and globally quarantines activation until an explicit future migration.

The v0.1 Stage-1 binding schema requires these pins and non-null hashes. Earlier unpinned or nullable receipts remain readable as historical data in unstamped stores, but are not valid new Stage-1 bindings. This tightens the pre-v1 runtime contract without changing AIOS IR or its semantic hash. The example binding uses synthetic evidence, trust-source, manifest, and build IDs to demonstrate the receipt shape; it is not an assertion that a provider passed conformance or trust review.

A Stage-1 binding also receives an immutable trust-source marker when inserted. The marker and receipt both identify the initial trusted registration receipt or the latest admitted same-build trust decision effective at the binding creation time. A binding made before trust approval cannot become executable after a later review; a changed trust decision requires a new attempt and binding once that decision becomes effective. The launch gate verifies the complete registration and trust-decision history and requires the marker and receipt to match the source effective at the launch check time. A future-dated review does not invalidate the existing source early.

The provider's enabled interval is pinned by a separate immutable control-plane marker created in the same binding insert. Each provider state transition advances an append-only revision, including equal-time disable/re-enable transitions. Launch requires the binding's marker to match the current registered revision. A prior binding cannot regain launch authority after re-enable even when the clock value repeats. This internal sidecar does not alter the public Execution Binding receipt, AIOS IR, or semantic hashes. A stamped store with a missing or malformed provider-history ledger or guard fails closed for explicit operator migration because lost revocation history cannot be reconstructed. A missing binding-only marker guard may be repaired under a fence, but prior bindings remain quarantined and require a new attempt.

Do not mutate provider, input, output allocation, grant, placement, or execution profile in place.

If any of those must change:

```text
invalidate/finish old attempt
→ create a new attempt ID
→ create a new Execution Binding
→ re-evaluate authority where required
→ execute again only if retry/fallback semantics permit
```

This preserves historical truth and keeps semantic identity separate from runtime history.

## Attempt identity

Use distinct identities for:

```text
Task ID              durable unit of work
semantic program hash exact semantic computation
node ID              semantic graph node
binding ID           concrete provider/resource/grant binding
attempt ID           one launch/execution attempt
provider invocation ID one supervisor invocation record
```

A retry does not overwrite the previous attempt.

## Provider principal

Every provider process/component executes as a distinct workload/provider principal.

The runtime must not simply say "the user launched it" and inherit the user's authority.

Provider identity should include enough evidence to distinguish:

```text
provider semantic ID
provider version
manifest/package/build hash
runtime kind
workload/process identity where useful
```

Package signature/conformance may influence eligibility, but neither grants runtime permission.

## Provider Supervisor responsibilities

The supervisor is trusted to enforce execution setup and collect results.

Responsibilities:

1. verify the binding is current and internally consistent;
2. verify required grants are current before launch;
3. materialize only the bounded interfaces/resources named by the binding;
4. establish the declared execution profile/sandbox;
5. launch the provider without arbitrary shell interpretation;
6. pass a typed invocation request over the provider ABI;
7. monitor deadline/cancellation/resource failure;
8. collect structured provider result/error;
9. coordinate Artifact Store output finalization;
10. record attempt/result/provenance;
11. revoke/retire attempt-scoped runtime resources when finished.

The supervisor does **not** infer missing permission or repair semantic IR.

## No shell-as-runtime-ABI

The core provider path must not be:

```text
model generates command string
→ /bin/sh -c ...
```

Native providers may ultimately be processes, but the supervisor launches a known registered entry point/component under an explicit execution profile and communicates through a typed interface.

Shell is allowed for development/build/maintenance tooling outside the trusted provider invocation path.

## Runtime environment

Provider environment is allowlisted rather than inherited wholesale.

Do not implicitly inherit:

- user shell environment;
- HOME filesystem authority;
- SSH/GPG/cloud credentials;
- browser/session tokens;
- arbitrary PATH resolution;
- host network;
- desktop session buses;
- clipboard/device access;
- secret-bearing environment variables.

Any required interface must be deliberately projected through the execution profile and current grants.

## Input binding

Provider inputs are typed handles/value references.

For Artifact inputs, provider receives an opaque/bounded handle or descriptor rather than an arbitrary host path where practical.

A handle does not grant read permission by existence alone. The Artifact service validates the caller principal/binding/grant at use.

Input bindings SHOULD carry expected content identity/revision where available so stale/mutated inputs can fail before computation.

## Output binding

Providers do not choose arbitrary destination paths.

The binding contains task-owned **Output Allocations**.

Conceptual flow:

```text
Task/Artifact Store reserves allocation
→ provider writes through allocation interface/staging area
→ provider returns completion metadata
→ trusted Artifact Store validates/hash/finalizes
→ immutable published Artifact receives identity
```

A process exit code alone never turns partial bytes into a valid published Artifact.

## Point-of-use authority

Before each protected broker/resource operation, the receiving trusted service validates the current grant.

This matters even after launch because:

- Task can be cancelled;
- grant can expire/revoke;
- one-shot use can be consumed;
- provider can attempt a different resource;
- binding can be invalidated.

The provider cannot broaden its scope by changing parameters after launch.

## Provider ABI boundary

The provider receives a structured invocation request containing runtime facts, not semantic authority invention.

The first ABI needs only enough for a deterministic fixture provider:

```text
invocation ID
binding/attempt IDs
semantic program + node identity
capability selector
provider/build identity
input handle refs
output allocation refs
grant refs
execution-profile identity
deadline/resource limits
```

It does not carry raw long-lived credentials.

## Result classes

Stable supervisor-level outcomes should include:

```text
SUCCEEDED
SEMANTIC_FAILURE
PROVIDER_FAILURE
START_FAILED
TIMED_OUT
CANCELLED
OUTPUT_FINALIZATION_FAILED
AUTHORITY_REVOKED
OUTCOME_UNKNOWN
```

`SEMANTIC_FAILURE` means the provider executed normally but returned a declared capability error.

`PROVIDER_FAILURE` means implementation/runtime failure outside the semantic error contract.

`OUTCOME_UNKNOWN` is used when the supervisor cannot prove whether an externally observable opaque effect occurred. It should be rare for deterministic local v0.1 providers because external effects are not part of the first execution proof.

## Provider exit vs semantic result

Do not equate Unix exit status with capability semantics.

The provider adapter/runtime maps implementation behavior to a structured result.

Examples:

```text
process exits 0 + structured success -> candidate SUCCEEDED
process exits 0 + malformed result    -> PROVIDER_FAILURE
process exits nonzero                 -> PROVIDER_FAILURE unless ABI defines startup-specific mapping
structured TABLE_IMPORT_MALFORMED_INPUT -> SEMANTIC_FAILURE
```

## Output publication atomicity

The supervisor should use staged publication:

1. output allocation exists before provider runs;
2. provider writes only to its staging allocation;
3. completion returns expected output descriptors;
4. Artifact Store validates size/type/hash/integrity constraints;
5. Artifact metadata + publication/provenance commit atomically where defined;
6. only then may downstream nodes consume the Artifact.

Crash-before-finalize leaves staging/orphan data that recovery can safely discard or reconcile.

## Retry/fallback

The supervisor itself does not invent retries.

The Task/orchestration layer consults validated AIOS IR failure policy and attempt/result certainty.

Retry is permitted only when:

- semantic budget remains;
- previous attempt is known not to have produced an unsafe irreversible duplicate effect;
- inputs/revisions are still valid;
- current provider/resource/policy/grants remain eligible or a new binding is created.

Provider substitution always creates a new binding/attempt.

## Cancellation

Cancellation has two layers:

```text
request cancellation
→ revoke/stop future protected operations
→ ask/terminate provider according to profile
```

A hard-killed provider may leave staging data; it must not leave a published Artifact merely because bytes exist.

For future irreversible external providers, cancellation cannot pretend an already observed external effect was undone.

## Crash recovery

Persist before launch:

- binding identity;
- attempt/invocation identity;
- provider/build identity;
- input/output refs;
- policy/grant refs;
- state = STARTING/RUNNING as appropriate.

On control-plane restart:

```text
known provider process alive + binding valid -> reconnect/monitor if supported
local provider gone + no finalized output    -> failed/retryable according to policy
finalized output + task transition incomplete -> reconcile publication/provenance, do not blindly rerun
uncertain opaque external operation           -> OUTCOME_UNKNOWN/reconcile, do not blind retry
```

## Provider isolation classes

The existing execution-profile system remains authoritative.

The supervisor should support increasing containment mechanisms over time:

```text
native restricted process
Wasm Component
container/namespaces
VM/microVM
legacy compatibility habitat
remote worker
```

The semantic capability is independent of which eligible isolation/runtime class implements it.

## Logging

Provider stdout/stderr are diagnostics, not trusted structured results and not authority.

Logs must be bounded and treated as potentially sensitive/untrusted.

Do not automatically copy environment values, raw tokens, or full user Artifact content into logs/provenance.

## v0.1 acceptance tests

At minimum:

1. provider cannot start without successful validated binding prerequisites;
2. provider receives only declared input/output interfaces;
3. provider cannot open an unrelated Artifact through a valid grant for another Artifact;
4. provider cannot use grant after Task cancellation/revocation;
5. unknown provider result shape fails as `PROVIDER_FAILURE`;
6. semantic provider error remains distinguishable from process/runtime crash;
7. crash before Artifact finalization produces no published output;
8. crash after finalization but before Task transition reconciles without duplicate execution;
9. provider substitution creates a new binding/attempt and authority evaluation;
10. changing provider/build/placement does not change semantic program hash;
11. timeout/cancel are persisted and attributable;
12. provider receives no ambient network/secret/filesystem access beyond execution profile;
13. raw runtime token values never appear in persisted provider result/provenance;
14. deterministic fixture provider can run entirely offline;
15. all attempt outcomes identify provider/build/binding/semantic node.

## v0.1 non-goals

- distributed provider scheduling;
- arbitrary remote RPC;
- general app launching;
- GPU job preemption;
- checkpoint/migration of arbitrary providers;
- irreversible SaaS transactions;
- shell scripting as provider ABI;
- automatic recovery by model reasoning.

## Principle

> **An Execution Binding is a receipt for exactly what the runtime intended to execute; the Provider Supervisor is the deterministic mechanism that makes the attempt obey that receipt.**
