# 88 — v0.1 Trusted-Core Threat and Abuse-Case Matrix

## Purpose

The broad threat model describes principals and trust boundaries. This matrix turns Stage-0 trusted-core architecture into concrete attacker stories that implementation and review can attempt to reproduce.

The goal is not to claim every threat is eliminated. It is to state:

```text
what we protect
who/what may be hostile
which boundary is supposed to stop the attack
what evidence proves the boundary works
```

## Threat scope

Assume potentially hostile or faulty:

- model/planner output;
- task input data/documents/metadata;
- capability/provider implementation;
- provider package publisher;
- legacy application;
- remote service/cloud model;
- peer device after compromise;
- ordinary user mistakes;
- system/process crashes;
- stale policy/approval/provider/registry state;
- malformed/corrupt local non-privileged data.

v0.1 does **not** claim to survive an attacker with unrestricted kernel/root access who can rewrite trusted binaries, database, keys, and all audit history. Where useful, tamper-evidence/durable recovery are designed to expose ordinary corruption/partial manipulation, not defeat omnipotent local root.

## Protected assets

```text
semantic program meaning
Task state/history
Artifact contents/identity/lineage
user/private data
credentials/secrets
policy/approval/grant state
provider/runtime isolation
semantic registry history
provenance history
base-system configuration
external side-effect uniqueness/certainty
```

## Trust boundary shorthand

```text
TB-SIR   strict parser + semantic validator + Registry Snapshot
TB-TASK  Task Manager/CAS persistence
TB-ART   Artifact Store/handle/publication boundary
TB-PROV  provenance journal/hash chain
TB-AUTH  Authority Coordinator + point-of-use trusted brokers
TB-CRED  Credential Broker / secure-store boundary
TB-EXEC  Execution Binding + Provider Supervisor + sandbox
TB-REC   deterministic recovery/reconciliation
TB-PKG   component identity/conformance/update boundary
TB-NET   explicit Network/Service Fabric authority
```

## Claims we must not make from v0.1 alone

Even after Stage 1 passes, do not claim:

- the system is secure against a fully privileged hostile kernel/root attacker;
- all providers are safe because they are sandboxed;
- all external operations have exactly-once semantics;
- provenance cannot be forged by a privileged storage attacker;
- AI-generated code is safe by default;
- identity resolution is globally correct;
- cloud/peer providers are trustworthy by authentication alone;
- arbitrary legacy applications are safely compatible;
- all model prompt injection is "solved"—the stronger claim is that untrusted content cannot directly create OS authority/execution outside the typed/policy boundaries.

## Relationship to independent red-team review

`docs/83-pre-implementation-red-team-and-astra-review-packet.md` asks an independent reviewer to challenge these boundaries.

The reviewer SHOULD add new abuse-case IDs/fixtures rather than only restating the matrix.

A MAJOR/FATAL finding against a `SPIKE_READY` trusted boundary is a reason to reopen the relevant architecture contract before broad implementation continues.

## Principle

> **A security boundary is not real because the diagram says it exists; it becomes credible when a hostile component can repeatedly try to cross it and deterministic tests prove where it stops.**
