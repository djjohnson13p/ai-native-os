# 79 — v0.1 Credential Broker and Secret Mediation

## Purpose

AIOS needs to use existing accounts, APIs, databases, package registries, peer identities, and external services without turning the model, provider process, or Task graph into a secret-distribution mechanism.

The v0.1 Credential Broker therefore separates:

```text
credential identity/handle
secret material
runtime authority
provider invocation
external service operation
```

The central rule is:

> **A provider may be authorized to use a credential for one bounded operation without learning, owning, or being able to reuse the underlying long-lived secret.**

## Relationship to the Authority Coordinator

The Credential Broker never decides permission by itself.

Typical flow:

```text
validated semantic action/request
      ↓
Authority Coordinator
      ↓ policy/approval/grant
scoped `credential.use` / external-action grant
      ↓
Credential Broker
      ↓ resolves opaque handle
short-lived delegated credential OR brokered operation
      ↓
external/local service
```

A valid credential handle does not grant authority. A valid authority grant does not make every credential eligible.

## Credential handle

`credential://...` identifies broker-managed credential metadata, not the secret bytes.

The handle may describe:

- class (OAuth token set, API credential, private key, password reference, database credential, etc.);
- owner principal;
- issuer/service identity;
- scopes/resource constraints;
- storage boundary;
- exportability;
- lifecycle state;
- expiry/rotation metadata.

`specs/credential-handle.schema.json` remains the metadata contract.

## Storage boundary

Actual long-lived secret material stays behind an implementation-specific secure store such as:

```text
local encrypted secret store
OS/kernel credential store
TPM / secure enclave / HSM
organization secret manager
remote secret broker
provider-managed opaque reference
```

AIOS core stores only the metadata/handle needed to mediate safe use when possible.

## v0.1 use modes

The broker should distinguish at least four use modes.

### `BROKERED_OPERATION`

Preferred when practical.

The provider asks the trusted broker to perform a narrow operation using the secret internally.

Example:

```text
sign digest with key X
exchange refresh token for service-scoped access token
open authenticated database session for read-only query
```

Long-lived secret never enters provider memory.

### `DELEGATED_SHORT_LIVED`

The broker obtains or derives a short-lived external token scoped to the exact service/action/resource.

The provider may receive that delegated credential, but:

- lifetime is short;
- scope is narrow;
- delegation is attributable;
- it cannot exceed the source credential + current authority.

### `LOCAL_INJECTION_RESTRICTED`

Some legacy/native tools require credential material in process memory, environment, FD, temporary file, or agent protocol.

When unavoidable, the supervisor uses a tightly constrained injection mechanism under an appropriate execution profile.

The secret is not persisted in Task state/provenance/logs and is removed as soon as practical.

### `EXPORT_WITH_APPROVAL`

Exceptional path for credentials explicitly marked `EXPORTABLE_WITH_APPROVAL`.

This is a high-consequence operation requiring explicit destination/provider/scope disclosure and policy approval.

It must not be a convenience fallback when brokered or delegated use is possible.

## Exportability rules

Credential metadata declares one of:

```text
NON_EXPORTABLE
LOCAL_EXPORT_RESTRICTED
DELEGABLE_HANDLE_ONLY
EXPORTABLE_WITH_APPROVAL
```

Rules:

- `NON_EXPORTABLE`: secret material never leaves its secure boundary; only brokered operations are allowed.
- `LOCAL_EXPORT_RESTRICTED`: secret may enter an approved local workload under strict sandbox/injection policy, never peer/remote.
- `DELEGABLE_HANDLE_ONLY`: provider may receive only a broker/reference capability or derived delegated credential, not the source secret.
- `EXPORTABLE_WITH_APPROVAL`: export may be policy-authorized only to explicitly approved principal/service/destination.

Remote placement cannot silently transform a local-only credential into an exportable one.

## Credential use request

A runtime request should bind credential use to concrete execution facts:

```text
request ID
Task ID
semantic program/node/capability
provider/workload principal
Execution Binding / attempt
Authority grant ID
credential handle
operation/use class
service/destination identity
resource/action scope
requested use mode
expiry/use/cost constraints
```

The request must be consistent with both:

1. the active Authority Grant; and
2. the credential handle's own scope/exportability/state.

## Scope intersection

Effective credential use is the intersection of:

```text
credential native scope/resource limits
∩ user/org policy
∩ current Authority Grant
∩ provider principal / binding
∩ requested service/action/resource
∩ credential exportability
∩ lifecycle validity
∩ current Task state
```

No layer may widen it.

## Point-of-use checks

Immediately before use, the broker validates:

- handle exists and is ACTIVE;
- not-before/expiry conditions;
- issuer/service matches intended target;
- provider/workload principal matches grant/binding;
- Task/attempt matches;
- Authority Grant is active and permits credential use/external action;
- exportability permits the selected use mode/locality;
- requested scopes/resources are subsets;
- credential has not been revoked/rotated into an invalid state;
- usage/rate constraints are not exhausted.

A provider cannot simply retain a previously materialized credential and treat it as future authority.

## Raw secret handling rules

Raw long-lived secret material MUST NOT be placed in:

- AIOS IR;
- Task plans;
- model prompts/context by default;
- semantic Objects/Artifacts unless explicitly modeling encrypted secret backups;
- provenance records;
- normal logs;
- provider manifests;
- package metadata;
- Capability/Authority Grant records;
- network transfer records;
- crash reports.

Debug tooling must redact credential material by construction, not by hoping the model avoids printing it.

## Provider result/log boundary

Provider stdout/stderr and returned structured results are untrusted.

If they contain a value matching a materialized credential or secret fingerprint, the system should redact/quarantine it where practical and emit a security diagnostic.

The architecture should not require scanning every byte to be safe: the stronger protection is to avoid exposing long-lived material in the first place.

## Service authentication vs Task authorization

A credential can authenticate to an external service while AIOS policy separately governs what the Task may request.

Example:

```text
OAuth token has broad mailbox scope
AIOS grant permits mail.send to one recipient for Task T91
```

The provider must still be constrained by AIOS authority even if the external credential is broader than ideal.

Where an external API supports narrower delegated tokens, use them.

## Database credentials

Prefer mediated connection/session capability over raw connection strings/passwords.

A database provider can receive:

```text
session handle
allowed database/schema
read/write class
query/time/row limits
Task/binding identity
```

rather than a reusable administrator password.

## Private keys

For non-exportable private keys, expose semantic operations such as:

```text
sign(digest, algorithm)
decrypt(ciphertext, profile)
perform key agreement
```

subject to authority/policy, instead of exposing private key bytes.

## OAuth/API tokens

Prefer:

```text
source credential handle
→ broker refresh/exchange
→ short-lived least-scope token
→ provider invocation
```

The refresh token remains broker-held.

If token exchange/scoping is unavailable, treat the resulting broader token as higher risk and constrain the provider sandbox/network path accordingly.

## Rotation

Rotation preserves credential-handle logical identity where the semantic account/service identity remains the same, while updating backing secret version/material.

Active provider attempts do not automatically receive new secret material. A request crossing a rotation boundary is revalidated.

## Revocation

Revocation of either:

- the AIOS Authority Grant; or
- the Credential Handle/backing external credential

prevents future brokered use.

Revocation should invalidate cached delegated tokens/session handles where possible.

It cannot undo an already completed external operation.

## Failure handling

Stable broker result classes should distinguish:

```text
ALLOWED_AND_USED
AUTHORITY_DENIED
HANDLE_NOT_FOUND
HANDLE_INACTIVE
EXPIRED
SCOPE_MISMATCH
SERVICE_MISMATCH
EXPORT_NOT_ALLOWED
PROVIDER_BINDING_MISMATCH
DELEGATION_FAILED
SECURE_STORE_UNAVAILABLE
EXTERNAL_AUTH_FAILED
RATE_OR_USE_LIMIT
CANCELLED
OUTCOME_UNKNOWN
```

Do not return raw upstream error payloads as trusted semantics.

## Offline behavior

Local/non-network credential operations such as using a hardware-backed signing key should work offline if policy/grant validation is available locally.

External OAuth refresh/API authentication inherently needs the service/network, but local recovery must not depend on a cloud secret broker unless explicitly configured that way.

## Recovery behavior

After crash:

- never reconstruct secret material from logs/provenance;
- invalidate ephemeral injected/delegated material whose lifetime/ownership cannot be proven;
- revalidate grant + handle + binding before reuse;
- close/reconcile broker-created sessions where practical;
- never replay an externally consequential operation solely because credential use was interrupted.

## v0.1 acceptance tests

1. `NON_EXPORTABLE` key cannot be serialized into provider invocation request;
2. local-restricted credential cannot be used by peer/remote binding;
3. provider with valid credential handle but no Authority Grant is denied;
4. valid grant for credential A cannot use credential B;
5. valid grant for provider A cannot be used by provider B;
6. revoked/expired handle fails at point of use;
7. OAuth refresh/source secret never appears in provider result/provenance/log fixture;
8. delegated short-lived token has no broader scope/lifetime than request/source permits;
9. destination/service mismatch fails closed;
10. Task cancellation invalidates subsequent credential use;
11. rotation requires fresh point-of-use validation;
12. database credential can be represented as mediated session without exposing password;
13. private-key signing works through brokered operation without key export;
14. `EXPORTABLE_WITH_APPROVAL` still requires explicit current approval for exact destination/principal;
15. secure-store outage fails closed rather than asking the model to reconstruct credentials.

## v0.1 non-goals

- implementing every OS password/keychain backend;
- enterprise federation/PKI;
- password autofill/browser integration;
- general secret-sharing protocol;
- remote HSM production support;
- arbitrary provider-to-provider delegation;
- storing user passwords in AIOS-native plaintext/encrypted files as the default design.

## Principle

> **Give software the ability to perform the authorized operation, not possession of the user's secret whenever the external ecosystem makes that possible.**
