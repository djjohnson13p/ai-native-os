# ADR 0031 — v0.1 IR Edge-Case Validation Profile

- Status: **Accepted for the v0.1 / Issue #17 spike**
- Date: 2026-09-15

## Context

The core AIOS IR contract deliberately stays small, but the first trusted validator still needs deterministic rules for authority resource selectors, duplicate authority requests, verifier roles, optional inputs, egress, caching, unused nodes, and fallback broadening.

Leaving these cases to implementation convention would make two validators accept different programs or assign different security meaning.

## Decision

Adopt `docs/68-aios-ir-v0.1-edge-case-semantics.md` as the controlling v0.1 validation profile.

Key decisions:

1. authority `resource` values are symbolic semantic selectors, not host paths/URLs/runtime handles;
2. exact semantic duplicate `(action, resource)` authority requests are invalid even if reason prose differs;
3. `operation.kind=verify` and capability-contract `role=verifier` must match in both directions;
4. optional top-level inputs may feed only optional capability ports directly;
5. input-less nodes are valid only when the contract has no required inputs;
6. unconsumed pure nodes are valid with deterministic warning rather than hard failure; effectful unconsumed nodes may be valid outcomes;
7. `egress=deny` cannot name destinations; `egress=policy` requires explicit destinations and matching `data.egress` authority requests;
8. deterministic/content-addressed cache modes require deterministic execution in v0.1;
9. fallbacks may not broaden ports/effects/authority/egress beyond the node's semantic envelope;
10. duplicate final-output aliases are allowed;
11. metadata/descriptions/reason prose are inert to executable semantics;
12. v0.1 has no general arbitrary literal/constant expression semantics.

## Consequences

### Positive

- deterministic validator behavior across implementations;
- less room for prompt/prose/metadata authority smuggling;
- conservative cache/fallback semantics;
- verifier boundaries remain explicit;
- planner bugs surface as structured diagnostics instead of silent normalization.

### Costs

- some useful richer patterns are deferred to later IR versions;
- fallback compatibility is conservative;
- optional-input/control-flow behavior is intentionally limited;
- remote/egress authoring requires explicit symbolic destination/authority declarations.

## New reason-code families

Issue #17 should support/lock the needed codes, including:

```text
IR_AUTHORITY_DUPLICATE_REQUEST
IR_CAPABILITY_ROLE_MISMATCH
IR_OPTIONAL_INPUT_TO_REQUIRED_PORT
IR_GRAPH_UNUSED_PURE_NODE        # warning
IR_EGRESS_AUTHORITY_MISMATCH
IR_CACHE_EXECUTION_CLASS_MISMATCH
IR_FALLBACK_PORT_MISMATCH
IR_FALLBACK_EFFECT_BROADENING
IR_FALLBACK_AUTHORITY_BROADENING
IR_FALLBACK_EGRESS_BROADENING
```

Existing broader code families may be used internally only if the external machine-code mapping remains deterministic and the fixtures/tests are updated together before merge.

## Revisit condition

A future IR version may add:

- typed literal/constants;
- richer resource-selector structures;
- explicit conditionals/presence types;
- seeded/reproducible nondeterminism caching;
- more flexible fallback refinement proofs.

Those changes require explicit semantic/schema/hash-profile decisions rather than ad-hoc validator exceptions.
