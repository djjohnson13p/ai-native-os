# ADR 0012 — Structural AIOS IR with JSON Bootstrap Representation

- **Status:** Proposed
- **Date:** 2026-09-15

## Context

ADR 0011 establishes that the project should own an AI-native semantic IR before attempting to replace mature general-purpose implementation languages.

The next decision is whether the IR should begin as a textual programming language, a binary format, a graph/object model, or some combination.

The representation must be reliably generated by models, deterministically validated, inspectable in source control, suitable for hashing/signing, and independent of a specific implementation language.

## Decision

For v0.1, define AIOS IR primarily as a **structural typed graph/object model**.

Use JSON plus JSON Schema as the initial inspectable serialization and fixture format.

The JSON syntax is a bootstrap interchange representation, not the permanent semantic identity or necessarily the hot-path runtime encoding.

Key decisions:

1. semantic meaning is defined by the IR specification, not by pretty textual syntax;
2. data-flow references are structural objects rather than code strings;
3. v0.1 programs are directed acyclic graphs with bounded retry/fallback/replan behavior;
4. provider identities, grants, secrets, process IDs, and hardware bindings do not belong in semantic IR;
5. authority declarations in IR are requests only;
6. a deterministic semantic validator is required in addition to JSON Schema;
7. a canonical serialized form will be used for semantic hashing/signing;
8. future textual or binary forms must lower to/preserve the same semantic model.

## Rationale

A structural model reduces ambiguity for both AI generation and deterministic validation.

It allows the system to validate:

- node identity;
- value references;
- type compatibility;
- graph cycles;
- authority requests;
- egress intent;
- execution classes;
- bounded failure behavior;
- verification gates.

without parsing arbitrary general-purpose source code.

JSON is selected for the bootstrap stage because it is easy to inspect, generate, diff, validate, and use across Rust/Python tooling. Performance-sensitive encodings may be introduced later.

## Consequences

### Positive

- models have a constrained machine-readable target;
- human reviewers can inspect early programs easily;
- fixtures can be validated without a compiler toolchain;
- semantics remain language/provider independent;
- the project can gather evidence before designing human-facing syntax;
- future binary encodings can preserve the same graph semantics.

### Negative

- JSON is verbose;
- JSON Schema cannot enforce graph/type/registry semantics by itself;
- large graphs may eventually need a more compact representation;
- a separate normalization/canonicalization step is required;
- developers may initially find a structural form less pleasant than a purpose-built source language.

## Alternatives considered

### Invent a textual language immediately

Rejected for v0.1 because syntax design would precede evidence about the actual semantic model and would create parser/tooling work before the execution architecture is proven.

### Use Rust/Python AST/code as the IR

Rejected because host-language semantics would become accidental operating-system semantics and would not intrinsically model authority, egress, verification, provider independence, or task artifacts.

### Use WASM as the primary IR

Rejected as the primary semantic IR. WASM remains a strong lowering/execution target, but it is too low-level to represent the full AI-native task/policy semantics directly without a parallel metadata system.

### Use a binary graph format immediately

Deferred. A binary format may improve efficiency later, but would make the early architecture harder to inspect and iterate.

## Validation criteria

This ADR should be accepted after a prototype demonstrates that:

- Demonstration A is representable without provider-specific leakage;
- at least five valid and ten invalid/adversarial fixtures are handled deterministically;
- a Rust validator can produce stable reason codes;
- model-generated candidate IR can be repaired from validator feedback more reliably than unconstrained generated code;
- canonical hashing produces stable identities for semantically normalized fixture programs.
