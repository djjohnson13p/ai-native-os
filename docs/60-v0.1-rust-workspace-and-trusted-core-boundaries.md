# 60 — v0.1 Rust Workspace and Trusted-Core Boundaries

## Purpose

Provide a bounded implementation shape for the first Rust work so Codex/developers do not spend the first implementation session inventing repository structure or accidentally mixing trusted semantic validation with provider/model execution.

This is a **prototype workspace plan**, not a permanent language commitment. ADR 0016 remains controlling: bootstrap languages are implementation mechanisms, not the semantic ABI of AIOS.

## Initial repository shape

Recommended first coding layout:

```text
Cargo.toml
Cargo.lock
crates/
  aios-contracts/
  aios-registry/
  aios-ir/
  aios-core/            # created later, initially minimal/empty if needed
cmd/
  aios-ir/
tests/
  fixtures/             # may reference/copy repository examples as appropriate
```

Avoid creating many micro-crates before there is code pressure requiring them.

The responsibilities below preserve the logical boundaries already described in `docs/30-aios-ir-reference-validator-plan.md`; implementation may later split `aios-ir` into model/schema/validate/canonical/effects crates when compile ownership or security review benefits justify it.

## `aios-contracts`

Purpose: strongly typed representations and shared contract primitives.

Initial responsibilities:

- AIOS IR v0.1 typed structures;
- semantic type/capability contract structures;
- registry snapshot structures;
- validation result/diagnostic structures;
- effect summary structures;
- stable reason-code enum/string mapping;
- schema/interface version constants.

Rules:

- no network;
- no provider execution;
- no database access;
- no model integration;
- security-relevant parsed structures should not retain unrestricted `serde_json::Value` escape hatches unless explicitly justified for non-semantic metadata.

## `aios-registry`

Purpose: load and expose an immutable semantic registry snapshot to the validator.

Initial responsibilities:

- load type/capability contract fixture files;
- validate registry structure;
- construct immutable indexes by semantic ID/version;
- compute/verify registry snapshot identity using the selected canonical rules;
- expose read-only lookup APIs;
- reject duplicate/conflicting contract identities.

Rules:

- no provider binary loading;
- no network resolution;
- no dynamic remote schema fetch;
- no policy/authorization decisions;
- registry snapshot used for one validation result is immutable for that validation.

## `aios-ir`

Purpose: trusted deterministic semantic boundary.

Suggested internal modules:

```text
parse
limits
schema
index
references
graph
types
capabilities
effects
failure_policy
normalize
canonical
hash
diagnostics
validate
```

Initial responsibilities:

- strict parsing;
- duplicate-key detection strategy;
- input size/depth/node/port/diagnostic limits;
- structural validation;
- graph/reference validation;
- cycle detection;
- semantic type/capability validation;
- execution-class/effect/authority/egress consistency;
- bounded retry/fallback validation;
- output reachability;
- static effect summary derivation;
- canonical semantic representation;
- tagged semantic hash;
- structured validation result.

Rules:

- **no sockets/network APIs**;
- **no shell/process/provider execution**;
- **no model calls**;
- **no secret resolution**;
- **no arbitrary host file reads beyond explicit input/registry files supplied by CLI/test harness**;
- validation success never implies authorization.

## `cmd/aios-ir`

Purpose: developer CLI proving the library boundary before daemon integration.

Initial commands:

```text
aios-ir validate <program> --registry <path>
aios-ir normalize <program>
aios-ir hash <program> --registry <path>
aios-ir effects <program> --registry <path>
aios-ir explain-error <reason-code>
```

CLI responsibilities:

- parse arguments;
- open explicitly named files/directories;
- call library APIs;
- emit stable JSON/human-readable output;
- return non-zero status for invalid/error conditions.

The CLI must not contain alternate validation semantics separate from the library.

## `aios-core` — later trusted substrate

Do not build the whole control plane inside Issue #17.

When Phase I begins, `aios-core` can progressively host:

```text
Task manager
Artifact store
Provenance store
provider registration
policy/authority coordinator
Execution Binding manager
recovery coordinator
```

These modules depend on validated semantic output rather than reimplementing IR interpretation.

## Dependency direction

For the first spike:

```text
aios-contracts
    ↑
    ├──────── aios-registry
    │             ↑
    └──────── aios-ir
                  ↑
               cmd/aios-ir
```

Desired properties:

- `aios-contracts` has no dependency on `aios-ir` or CLI;
- `aios-registry` does not depend on provider runtime code;
- `aios-ir` may depend on contracts/registry/canonicalization libraries but not future planner/provider/network modules;
- CLI depends on library, never reverse.

Later `aios-core` may depend on validated outputs from `aios-ir`; `aios-ir` must not depend on `aios-core` Task/policy execution.

## External crate selection principles

Prefer mature narrowly scoped crates for generic mechanisms rather than reimplementing them.

Selection criteria:

- maintained/security posture;
- deterministic behavior suitable for trusted boundary;
- no hidden network/runtime behavior;
- ability to enforce strict parsing/unknown fields/limits;
- reasonable dependency tree;
- license compatible with eventual project license;
- fuzzability/property-test support.

Potential categories (not mandated packages):

```text
serde/JSON parsing
JSON Schema validation or generated structural validation
cryptographic hashing
canonical JSON support
CLI parsing
error/diagnostic handling
property/fuzz testing
```

Any parser/canonicalization choice must be verified against AIOS duplicate-key and semantic-hash requirements rather than assumed safe from library popularity.

## Duplicate JSON keys

JSON parser behavior around duplicate object keys is security relevant.

The chosen parse path must detect/reject duplicates such as:

```json
{
  "capability": "artifact.hash@1",
  "capability": "network.send@1"
}
```

It is unacceptable for one validation layer to see the first value while another sees the last.

If the standard typed deserializer cannot reliably detect duplicates before semantic interpretation, use a strict parser/deserializer visitor or preprocessing strategy that can.

## Canonicalization isolation

Implement semantic canonicalization behind a narrow function/API such as conceptually:

```text
ValidatedProgram -> CanonicalSemanticBytes
CanonicalSemanticBytes -> SemanticHash
```

Runtime binding fields, credentials, provider IDs, transient metadata, or filesystem paths must be structurally unable to enter this hash path accidentally.

Hash format should be tagged/versioned, e.g. conceptually:

```text
aios-ir-v0.1:sha256:<hex>
```

Exact encoding is finalized by implementation/tests, not by casual string concatenation in multiple modules.

## Error discipline

Malformed/hostile input is normal input to the validator.

Requirements:

- no panic for invalid user/program/registry data;
- stable reason-code family;
- bounded diagnostic count;
- human message may evolve without changing machine code;
- internal unexpected errors remain distinguishable from semantic invalidity;
- no secret/host path leakage in error messages.

## Resource limits

Limits must be configurable/testable but safe by default.

Initial categories:

```text
serialized input bytes
JSON nesting depth
nodes/program
ports/node
authority requests/node
fallbacks/node
diagnostics/result
registry contract count
string lengths where schema does not already bound them
```

Limit failures get explicit reason codes rather than OOM/timeouts where practical.

## Determinism

Given:

- identical semantic program;
- identical registry snapshot;
- identical validator/canonicalization version;

validation result validity, normalized semantic representation, effect summary, and semantic hash should be deterministic.

Timestamps or host-specific paths do not enter semantic identity.

## Fuzzing boundary

Best initial fuzz targets:

```text
raw parser
strict duplicate-key parser
reference parser
DAG/index builder
fallback closure
canonicalizer
registry loader
```

The fuzz harness must not require network/provider/model execution.

## Persistence boundary

Issue #17 should not add SQLite or Task persistence merely to store validator output.

Return serializable validation results first. Phase I will persist them transactionally through the Task/control-plane layer.

## Logging

Validator library should not rely on logs as correctness output.

Structured diagnostics/results are the contract.

Developer logs/tracing may exist but should avoid dumping user input by default, especially once real data can appear in metadata.

## Feature flags

Avoid architecture-changing feature flags in the first spike.

If optional developer features are useful (e.g. richer tracing), they must not change whether a semantic program is considered valid.

## Definition of done for workspace bootstrap

The workspace is successfully bootstrapped when:

- clean checkout builds with pinned lockfile;
- CLI can validate repository fixture input;
- library tests run without network/provider/model requirements;
- module dependency direction matches this document;
- invalid input returns structured diagnostics rather than panicking;
- no permanent daemon/UI/cloud dependency has been introduced.

## Principle

> **Start with a small trusted library boundary; split it only when evidence improves isolation, reviewability, or build ownership.**
